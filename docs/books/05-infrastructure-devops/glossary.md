# Глоссарий

> Термины и выражения книги «Инфраструктура для DevOps». В скобках — главы, где термин вводится или активно используется.

---

**`.env`** — файл с переменными окружения и секретами приложения. Единая точка конфигурации, которую читают Docker Compose, systemd, shell-скрипты и Python. _(главы 1, 9)_

**`.env.example`** — шаблон `.env` без реальных значений, который коммитится в git и показывает, какие переменные нужны проекту. _(главы 1, 9)_

**`chmod 600`** — права доступа «чтение и запись только владельцу». Обязательны для `.env`, чтобы другие пользователи сервера не прочитали пароли. _(главы 1, 9)_

**`source`** — команда shell, загружающая переменные из файла (например `.env`) в текущее окружение скрипта. _(главы 1, 6)_

**`envsubst`** — утилита, подставляющая значения переменных окружения в шаблон конфига (например Nginx `.template` → `.conf`). _(глава 1)_

**python-dotenv** — Python-библиотека, читающая `.env` через `load_dotenv()` и наполняющая `os.environ`. _(глава 1)_

**`docker compose config`** — команда, выводящая итоговый конфиг с подставленными переменными; показывает секреты, поэтому вывод нельзя копировать публично. _(глава 1)_

**Заголовки безопасности** — HTTP-заголовки от Nginx, защищающие браузер: `X-Content-Type-Options`, `X-Frame-Options`, HSTS, `Referrer-Policy`, CSP. _(главы 2, 9)_

**HSTS (Strict-Transport-Security)** — заголовок, заставляющий браузер всегда использовать HTTPS для сайта. «Улица с односторонним движением»: включил на год — назад не откатишь. _(глава 2)_

**Clickjacking** — атака, при которой жертву обманом заставляют кликать по невидимому встроенному `<iframe>`; защита — заголовок `X-Frame-Options`. _(глава 2)_

**Rate limiting** — ограничение числа запросов с одного IP за единицу времени; защита от брутфорса и простых атак. _(главы 2, 9)_

**`limit_req_zone`** — директива Nginx, определяющая зону памяти и скорость лимита (например `rate=10r/s`) по ключу `$binary_remote_addr`. _(глава 2)_

**`burst`** — размер очереди запросов сверх лимита rate; с `nodelay` они обрабатываются сразу, а не задерживаются. _(глава 2)_

**Gzip-компрессия** — сжатие текстовых ответов (JSON, HTML, CSS) перед отправкой клиенту; экономит до 80–85% трафика. _(главы 2, 9)_

**Таймауты proxy** — `proxy_connect_timeout`, `proxy_read_timeout` и др.: сколько Nginx ждёт backend; слишком малые дают 502/504, слишком большие держат «зависшие» соединения. _(глава 2)_

**Сниппеты Nginx (`include`)** — вынесенные в отдельные файлы блоки конфига (ssl, security-headers, gzip), переиспользуемые между сайтами. _(глава 2)_

**JSON-логи** — формат логов Nginx (`log_format json`), легко парсится системами мониторинга и алертинга. _(глава 2)_

**`nginx -t`** — проверка синтаксиса конфигурации Nginx перед reload; без неё сломанный конфиг кладёт все сайты. _(глава 2)_

**Суперпользователь PostgreSQL (`postgres`)** — роль с полным доступом к серверу БД; использовать её в приложении опасно: SQL-инъекция = полный доступ ко всем базам. _(главы 3, 9)_

**Принцип минимальных привилегий** — приложение получает только те права, что ему нужны (отдельный пользователь БД вместо суперпользователя). _(главы 3, 9)_

**`pg_hba.conf`** — файл PostgreSQL, описывающий кто, к какой базе, с какого адреса и каким методом может подключиться. _(глава 3)_

**`scram-sha-256`** — современный безопасный метод аутентификации по паролю в PostgreSQL; предпочтительнее устаревшего `md5`. _(глава 3)_

**`trust` (метод аутентификации)** — подключение к PostgreSQL вообще без пароля; допустим только в тестах, никогда на продакшне. _(глава 3)_

**`shared_buffers`** — память PostgreSQL под кеш данных, ориентир ~25% от RAM сервера. _(главы 3, 9)_

**`effective_cache_size`** — оценка памяти, доступной под кеш (включая OS cache), ориентир ~75% RAM; влияет на планировщик запросов. _(глава 3)_

**`max_connections`** — максимум одновременных подключений к PostgreSQL; каждое ест память, поэтому держат умеренным (например 100). _(главы 3, 9)_

**`work_mem`** — память на одну операцию сортировки/хеширования; ориентир `RAM / (max_connections × 2)`. _(глава 3)_

**PgBouncer** — пул соединений к PostgreSQL; нужен, когда приложению требуется больше подключений, чем разумно держать напрямую. _(глава 3)_

**`pg_activity`** — интерактивный монитор активных запросов PostgreSQL, «htop для базы». _(глава 3)_

**Миграция БД** — версионированный файл изменений схемы с операциями `upgrade` (применить) и `downgrade` (откатить). _(главы 4, 9)_

**Alembic** — популярный инструмент миграций для Python/SQLAlchemy; умеет автогенерировать миграции по моделям. _(главы 4, 9)_

**`alembic upgrade head`** — применить все миграции до последней; `head` — самая свежая ревизия. _(глава 4)_

**Autogenerate** — режим Alembic, сравнивающий модели SQLAlchemy с реальной схемой БД и создающий миграцию автоматически. _(глава 4)_

**Опасная миграция** — изменение схемы (удаление/переименование колонки, NOT NULL без дефолта), способное уронить приложение; делается поэтапно. _(глава 4)_

**Правило 3-2-1** — стратегия бэкапов: 3 копии данных, 2 разных носителя, 1 копия вне площадки (offsite). _(главы 5, 9)_

**Offsite-копия** — бэкап, хранящийся отдельно от сервера (облако, другой ЦОД); переживает гибель самого сервера. _(главы 5, 6)_

**Полный бэкап (full)** — каждый раз полная копия всех данных: прост в восстановлении, но занимает больше места. _(глава 5)_

**Инкрементальный бэкап** — после первого полного сохраняются только изменения; экономит место, но восстановление требует цепочки бэкапов. _(глава 5)_

**Ротация бэкапов** — автоматическое удаление старых копий (например `find -mtime +7 | rm`), чтобы не переполнить хранилище. _(главы 5, 6)_

**`pg_dump`** — утилита логического бэкапа PostgreSQL; выводит SQL или custom-формат, обычно сжимается gzip. _(главы 6, 7)_

**Custom-формат (`-Fc`)** — сжатый бинарный формат `pg_dump`, восстанавливаемый через `pg_restore`; быстрее для больших баз. _(главы 6, 7)_

**`pg_restore`** — утилита восстановления PostgreSQL из бэкапа в custom-формате. _(глава 7)_

**`set -euo pipefail`** — набор флагов bash: падать при ошибке, при необъявленной переменной и при ошибке в пайпе. Обязателен в скриптах бэкапа, чтобы не получить тихо пустой дамп. _(главы 6, 7)_

**`backup.sh`** — скрипт ежедневного бэкапа: дамп БД, архив файлов, копия конфигов, выгрузка в облако и ротация. _(главы 6, 9)_

**cron / `cron.d`** — планировщик задач Linux; файлы в `/etc/cron.d/` запускают бэкапы, очистку и health-check по расписанию. _(главы 6, 8, 9)_

**rclone** — утилита синхронизации с облачными хранилищами (Backblaze B2, S3); выгружает локальные бэкапы offsite. _(главы 5, 6)_

**Backblaze B2 / S3** — объектные облачные хранилища для offsite-бэкапов; B2 заметно дешевле S3. _(главы 5, 6)_

**`restore.sh`** — скрипт восстановления из бэкапа: проверка целостности, восстановление БД, файлов и конфигов. _(главы 7, 9)_

**`gunzip -t`** — проверка целостности gzip-архива без распаковки; используется перед восстановлением бэкапа. _(глава 7)_

**Disaster recovery** — сценарий «сервер умер → поднимаем с нуля»: новый сервер, код из git, данные и секреты из бэкапов. _(глава 7)_

**Docker мусор** — неиспользуемые образы, контейнеры, тома и кеш сборки; виден в `docker system df` как Reclaimable, чистится `docker system prune`. _(главы 0, 8)_

**Ротация логов Docker** — настройка `daemon.json` (`max-size`, `max-file`), ограничивающая бесконечный рост логов контейнеров. _(глава 8)_

**Лимиты ресурсов** — `deploy.resources.limits` (memory, cpus) в Compose; без них один контейнер может съесть всю память (OOM). _(главы 8, 9)_

**Swap** — файл/раздел подкачки на диске, страхующий систему при нехватке RAM (утечки памяти). _(глава 8)_

**`restart: unless-stopped`** — политика Docker: перезапускать контейнер всегда, кроме случая ручной остановки. _(главы 8, 9)_

**Healthcheck** — проверка работоспособности контейнера (например `pg_isready`); помечает контейнер healthy/unhealthy и управляет зависимостями. _(главы 8, 9)_

**Restart loop** — контейнер, постоянно перезапускающийся из-за падения; диагностируется через логи и `docker inspect`. _(глава 8)_

**`health-check.sh`** — скрипт проверки всего стека: контейнеры, healthcheck БД, ответ приложения, диск, права `.env`. _(глава 9)_

**Production-ready** — состояние сервера, где данные защищены бэкапами, сервис восстанавливается сам, а ресурсы под контролем. _(главы 0, 9)_
