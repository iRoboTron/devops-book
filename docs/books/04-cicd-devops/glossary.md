# Глоссарий

> Термины и выражения книги «CI/CD для DevOps». В скобках — главы, где термин вводится или активно используется.

---

**CI/CD** — общий подход к автоматизации: код от коммита до сервера проходит через конвейер автоматически и одинаково каждый раз. _(глава 0)_

**CI (Continuous Integration)** — непрерывная интеграция: каждый коммит автоматически проверяется тестами, чтобы убедиться что код не сломан. _(главы 0, 4)_

**CD (Continuous Delivery)** — непрерывная доставка: код всегда готов к деплою, но финальный запуск делается вручную нажатием кнопки. _(глава 0)_

**CD (Continuous Deployment)** — непрерывное развёртывание: деплой на сервер происходит автоматически после прохождения всех проверок. _(главы 0, 7)_

**Pipeline (конвейер)** — последовательность автоматических стадий от push до деплоя: тесты → сборка → публикация → деплой. _(главы 0, 7)_

**Workflow** — файл `.github/workflows/*.yml`, описывающий весь пайплайн: когда запускаться и что делать. _(главы 0, 3)_

**Job** — отдельная задача внутри workflow (test, build, deploy), выполняется на своём runner. _(главы 0, 3)_

**Step (шаг)** — отдельная команда или действие внутри job; шаги выполняются последовательно. _(главы 0, 3)_

**Action** — готовый переиспользуемый шаг из маркетплейса, подключаемый через `uses:`, например `actions/checkout@v4`. _(главы 0, 3)_

**Runner** — виртуальная машина GitHub (например `ubuntu-latest`), на которой выполняется job. _(главы 0, 3)_

**Event (событие/триггер)** — то, что запускает workflow: `push`, `pull_request`, `schedule`, тег, ручной запуск. _(главы 0, 3)_

**Trigger (триггер)** — условие запуска пайплайна, задаётся в секции `on:`. _(главы 1, 3)_

**`on:`** — секция workflow, описывающая события-триггеры (push, pull_request, tags, schedule, workflow_dispatch). _(глава 3)_

**`runs-on:`** — директива, указывающая на каком runner выполняется job. _(глава 3)_

**`uses:`** — подключение готового action из маркетплейса. _(глава 3)_

**`run:`** — выполнение произвольной команды в терминале runner. _(глава 3)_

**`needs:`** — зависимость между jobs: job ждёт завершения указанных; без `needs:` jobs идут параллельно. _(главы 3, 7)_

**`name:`** — человекочитаемая подпись шага или workflow в логах. _(глава 4)_

**workflow_dispatch** — триггер ручного запуска workflow кнопкой «Run workflow» в интерфейсе. _(глава 3)_

**schedule (cron)** — триггер запуска по расписанию в формате cron. _(глава 3)_

**actions/checkout** — action, который делает `git clone` репозитория на runner; почти всегда первый шаг. _(глава 3)_

**actions/setup-python** — action для установки нужной версии Python и кэширования pip. _(главы 3, 4)_

**Matrix (матрица)** — `strategy.matrix`: запуск job параллельно для каждой комбинации параметров (версии Python, ОС). _(глава 4)_

**pytest** — фреймворк для запуска тестов Python в пайплайне. _(глава 4)_

**pytest-cov** — плагин pytest для измерения покрытия кода тестами (`--cov`). _(глава 4)_

**Coverage (покрытие)** — доля кода, выполненного тестами; считается через pytest-cov. _(глава 4)_

**Cache (кэш зависимостей)** — сохранение установленных пакетов между запусками; `cache: 'pip'` ускоряет установку. _(глава 4)_

**Status check** — результат job, отображаемый в PR; имя status check = имя job. _(главы 1, 4)_

**Branch protection (защита ветки)** — правило, запрещающее прямой push в `main` и требующее PR с прошедшими проверками. _(главы 1, 4)_

**Pull Request (PR)** — предложение смержить ветку в `main`; на PR автоматически запускается CI. _(глава 1)_

**GitHub Flow** — простая стратегия ветвления: стабильная `main` плюс короткоживущие feature-ветки. _(глава 1)_

**Feature-ветка** — ветка от `main` для разработки фичи; мержится через PR. _(глава 1)_

**merge** — слияние ветки в `main` с созданием merge-коммита, сохраняет полную историю. _(глава 1)_

**rebase** — перенос коммитов поверх актуальной ветки для линейной истории; нельзя на общих ветках. _(глава 1)_

**Tag (тег git)** — метка на конкретном коммите; push тега `v*` может запускать отдельный пайплайн. _(главы 1, 6)_

**SemVer (семантическое версионирование)** — формат версии `MAJOR.MINOR.PATCH`. _(глава 1)_

**Git hook** — скрипт в `.git/hooks/`, запускаемый git автоматически при действиях (commit, push). _(глава 2)_

**pre-commit** — клиентский хук, проверяющий код до создания коммита; при ошибке коммит отменяется. _(глава 2)_

**commit-msg** — хук проверки текста сообщения коммита. _(глава 2)_

**pre-push** — хук, запускающий тесты до отправки коммитов на сервер. _(глава 2)_

**post-receive** — серверный хук, запускаемый после получения push; простейший способ автодеплоя. _(глава 2)_

**Bare-репозиторий** — git-репозиторий без рабочей директории (`git init --bare`), используется на сервере для деплоя. _(глава 2)_

**Secret (секрет)** — зашифрованное значение (ключ, пароль, токен) в хранилище GitHub; в логах маскируется как `***`. _(глава 5)_

**Variable (переменная)** — несекретное значение (URL, имя, флаг) в настройках; используется через `${{ vars.X }}`. _(глава 5)_

**`${{ secrets.X }}`** — синтаксис подстановки секрета в workflow. _(глава 5)_

**GITHUB_TOKEN** — автоматический токен, создаваемый GitHub на время каждого запуска workflow; даёт доступ к репозиторию и Packages. _(глава 6)_

**github-контекст** — переменные о событии: `github.sha`, `github.ref_name`, `github.actor`, `github.repository`. _(глава 5)_

**Environment (окружение)** — группа с отдельными секретами и правилами (staging, production), может требовать approval. _(главы 5, 8)_

**Required reviewers (approval)** — правило environment: деплой требует ручного подтверждения человеком. _(главы 5, 8)_

**Container Registry (реестр образов)** — хранилище Docker-образов; CI публикует туда, сервер скачивает. _(глава 6)_

**ghcr.io** — GitHub Container Registry, бесплатный встроенный реестр образов. _(глава 6)_

**docker/login-action** — action для логина в реестр образов из workflow. _(глава 6)_

**docker/build-push-action** — action для сборки и публикации Docker-образа (`push: true`). _(глава 6)_

**docker/metadata-action** — action для автоматического формирования тегов и меток образа. _(глава 6)_

**Image tag (тег образа)** — метка образа; для деплоя используют `github.sha`, дополнительно `latest` или имя ветки. _(глава 6)_

**Layer cache (кэш слоёв)** — переиспользование неизменившихся слоёв Docker; `cache-from`/`cache-to: type=gha`. _(глава 6)_

**appleboy/ssh-action** — action для выполнения команд на сервере по SSH из workflow. _(главы 5, 7)_

**Artifact (артефакт)** — результат сборки, передаваемый дальше по пайплайну; здесь это Docker-образ в реестре. _(главы 6, 7)_

**Deploy (деплой)** — доставка готового образа на сервер: `docker compose pull` + `up -d`. _(глава 7)_

**Health check** — проверка `curl -f /health` после деплоя, подтверждающая что приложение реально работает. _(главы 7, 8)_

**Rolling update** — обновление без `down`: `up -d --no-deps app` пересоздаёт контейнер с минимальным даунтаймом. _(глава 8)_

**`--no-deps`** — флаг docker compose: пересоздать только указанный сервис, не трогая зависимости (БД, Redis). _(глава 8)_

**Rollback (откат)** — возврат к предыдущей версии образа из `.prev_tag` при провале health check. _(глава 8)_

**Downtime (даунтайм)** — время недоступности приложения при перезапуске; rolling update его минимизирует. _(глава 8)_

**Blue-green деплой** — два окружения (Blue/Green): новая версия разворачивается рядом, затем Nginx переключает трафик. _(глава 8)_

**Badge (бейдж статуса)** — картинка в README, показывающая статус workflow (зелёный — ок, красный — сломано). _(главы 3, 9)_
