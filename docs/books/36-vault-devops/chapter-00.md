# Глава 0: Зачем нужен Vault — проблема хранения секретов

## Что вы узнаете

- Какие проблемы создаёт хранение секретов «как-нибудь».
- Что такое секрет и почему его нельзя хранить в Git или переменных окружения CI.
- Какие задачи решает Vault и когда он избыточен.
- Место Vault в DevOps-стеке.

---

## 1. Что такое секрет

**Секрет** — это любая строка, которая даёт доступ к ресурсу или системе. Её раскрытие ведёт к компрометации.

| Тип секрета | Пример | Последствия утечки |
|---|---|---|
| Пароль БД | `postgresql://admin:S3cr3t@prod-db:5432/myapp` | Доступ ко всем данным |
| API-ключ Stripe | `sk_live_26PH7VQ8...` | Списание денег через API |
| Приватный ключ TLS | `-----BEGIN RSA PRIVATE KEY-----` | MITM, перехват трафика |
| OAuth client secret | `G0cDk8s...` | Выдача себя за приложение |
| SSH-ключ | `id_rsa` | Полный доступ к серверам |
| Cloud credentials | `AWS_ACCESS_KEY_ID + AWS_SECRET_ACCESS_KEY` | Использование ресурсов облака |

> ☠️ **Осторожно:** отличие секрета от пароля — секрет живёт в автоматизированной среде и читается машиной. Утечка секрета обычно означает утечку **всей системы**, а не одной учётной записи.

## 2. Как секреты хранятся сейчас (и почему это плохо)

### Сценарий 1: секреты в коде

```python
# config.py
DATABASE_URL = "postgresql://admin:S3cr3t@prod-db:5432/myapp"
```

Проблема: попал в `git commit` → попал в историю → даже после удаления строки секрет остаётся в `git log`. Утилиты вроде `truffleHog` находят такие строки автоматически.

### Сценарий 2: секреты в `.env`

```
# .env
DB_PASSWORD=S3cr3t
```

`git add .` → `.env` нет в `.gitignore` → коммит → GitHub. Даже если заметили сразу — секрет уже в истории репозитория.

### Сценарий 3: секреты в переменных окружения CI/CD

```yaml
# GitHub Actions / GitLab CI
env:
  DB_PASSWORD: S3cr3t
```

- Видны всем, у кого есть доступ к CI.
- Попадают в логи сборки: `Error: connection failed with password S3cr3t...`
- При форке репозитория — экспорт через логарифмирование.

### Сценарий 4: Kubernetes Secrets (base64)

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-secret
data:
  password: cGFzc3dvcmQ=
```

Base64 — не шифрование, а кодирование. `kubectl get secret db-secret -o yaml` → `base64 -d` → чистый пароль. По умолчанию Kubernetes хранит Secrets в etcd без шифрования.

### Жизненный цикл секрета

```
Без Vault:

  секрет → .env файл → git commit → утечка
  секрет → меняем вручную → 15 серверов → один забыли → каскадный сбой
  сотрудник уволился → ключи остались → никто не отозвал

С Vault:

  секрет → vault kv put → зашифрованное хранилище
  приложение → vault read → секрет в памяти → TTL истекает
  уволился → vault token revoke → доступ закрыт за 1 секунду
  утекло → vault rotate → новый секрет — старый мёртв
```

## 3. Что решает Vault

| Проблема | Решение Vault |
|---|---|
| Секреты в Git | Централизованное хранилище с шифрованием на стороне сервера |
| Нет аудита — кто и когда читал секрет | Audit log каждого обращения (syslog / file / socket) |
| Ротация паролей вручную | Dynamic secrets — автоматическая генерация + ротация |
| Долгоживущие пароли (живут годами) | Lease + TTL — секрет истекает автоматически |
| Нет контроля доступа (все видят всё) | Policies (HCL) — granular ACL: кто, к какому secret, что может |
| Уволился сотрудник — ключи остались | Revoke token — немедленный отзыв всех его токенов и lease |
| TLS-сертификаты выпускаются вручную | PKI engine — автовыпуск сертификатов с коротким TTL |
| Хранение ключей шифрования в конфигах | Transit engine — данные шифруются Vault, ключи не покидают сервер |
| Секреты раскиданы по 10 сервисам | Единый источник истины — Vault, агенты синхронизируют локально |

### Когда Vault избыточен

- **Один разработчик, pet-проект** — `dotenv` + `git-crypt` или `sops` достаточно.
- **Команда из 2–3 человек, не в проде** — можно жить на GitHub Secrets + SOPs.
- **Нет автоматизации**, секреты вводят руками при деплое — Vault создаст лишнюю сложность.

**Альтернативы Vault по сценариям:**

| Уровень | Инструмент | Когда брать |
|---|---|---|
| Локальный .env | `dotenv` + `.gitignore` | Разработка, pet-проекты |
| Шифрование в Git | `git-crypt`, `mozilla/sops` | Небольшая команда, файлы конфигов |
| CI/CD | GitHub Secrets / GitLab CI Variables | Только в пайплайнах |
| Облако | AWS Secrets Manager / GCP Secret Manager / Azure Key Vault | Всё в одном облаке, нет on-prem |
| Универсальный | Vault | Несколько сред, on-prem, multi-cloud, compliance |

> **Dev vs Production:** для разработки достаточно `.env + sops`. Vault внедряют когда секретов > 20, сервисов > 5, и нужен audit trail.

---

## Типичные ошибки

- ❌ **Vault — не замена `.env` для local dev.** Заставлять разработчика запускать Vault локально, чтобы прочитать пароль от Redis — плохая практика. Local dev: `dotenv`. Vault: staging + production.
- ❌ **Vault ≠ шифрование данных в БД.** Transit engine шифрует **значения** (строчки), но не заменяет TDE или шифрование на уровне диска.
- ❌ **Думать что «раз в Vault, то навсегда».** Токены протухают, секреты перевыпускаются, хранилище бэкапится отдельно.
- ❌ **Хранить root-токен в коде.** Root-токен — ключ от всех ключей. Хранить его где попало — сводить весь смысл Vault к нулю.

## Попробуйте сами

1. **Найдите секрет в репозитории:** `git log --all --oneline | head -5 && git show HEAD | grep -iE "password|secret|key"`. Посмотрите, не уплыло ли чего в историю.
2. **Декодируйте base64:** `echo "cGFzc3dvcmQ=" | base64 -d` — убедитесь что Kubernetes Secret не спасает.
3. **Напишите карту своих секретов** — таблицу из 3 столбцов: где секрет сейчас, какой уровень защиты, кто имеет доступ. Оцените риски.
