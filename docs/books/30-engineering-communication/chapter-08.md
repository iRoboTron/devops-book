# Глава 8: Документация как разговор с будущим собой

> **Цель:** писать документы, которые помогают действовать, а не просто существуют.

---

## 8.1 Почему документация нужна даже одному человеку

Через месяц ты забудешь:

- почему выбрал такой порт;
- где лежит backup;
- какую команду запускать после обновления;
- что означает странная переменная;
- как восстановить сервис после падения.

Документация — это помощь будущему себе.

---

## 8.2 Типы документов

| Документ | Зачем |
|---|---|
| README | понять и запустить проект |
| setup guide | установить с нуля |
| runbook | действовать при проблеме |
| changelog | видеть изменения |
| decision record | помнить, почему выбрали решение |
| incident report | не повторять аварию |

---

## 8.3 README

Хороший README отвечает:

```text
Что это?
Как запустить?
Какие зависимости?
Какие переменные окружения?
Как проверить?
Как деплоить?
Где логи?
Что делать при проблеме?
```

Плохой README:

```text
# app
npm install
npm start
```

Лучше:

```markdown
# App

## Что это
Сервис для ...

## Требования
- Docker
- PostgreSQL

## Запуск
cp .env.example .env
docker compose up -d

## Проверка
curl http://localhost:3000/healthz

## Логи
docker logs app --tail=100
```

---

## 8.4 Decision record

Когда принимаешь важное решение, запиши:

```markdown
# Решение: закрыть Grafana через WireGuard

## Контекст
## Варианты
## Решение
## Последствия
## Когда пересмотреть
```

Это защищает от вопроса через полгода: "почему мы так сделали?"

---

## 8.5 Практика

Напиши README для маленького сервиса. Минимум:

- что это;
- как запустить;
- env variables;
- как проверить;
- где логи;
- как остановить.
