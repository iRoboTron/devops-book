# Глоссарий

> Термины и выражения книги «GitOps: ArgoCD и продвинутый CI/CD». В скобках — главы, где термин вводится или активно используется.

---

**GitOps** — подход к доставке, где Git хранит желаемое состояние инфраструктуры, а агент в кластере непрерывно приводит реальность к этому описанию. _(главы 2, 3)_

**Source of truth (источник правды)** — единственное авторитетное место, описывающее, как должна выглядеть система; в GitOps это Git-репозиторий. _(главы 2, 3)_

**Declarative (декларативный подход)** — описание желаемого результата («должно быть так»), а не последовательности команд; противоположность императивному `kubectl apply` вручную. _(глава 3)_

**Desired state (желаемое состояние)** — то, как система должна выглядеть согласно манифестам в Git. _(главы 2, 3)_

**Actual state (фактическое состояние)** — то, как система выглядит в кластере прямо сейчас. _(главы 2, 3)_

**Reconciliation (сверка)** — непрерывный цикл, в котором контроллер сравнивает desired и actual state и устраняет различия. _(главы 2, 3)_

**Drift (дрейф)** — расхождение между состоянием в кластере и описанием в Git, например после ручного `kubectl scale`. _(глава 2)_

**Sync (синхронизация)** — операция приведения кластера к состоянию из Git: ArgoCD применяет манифесты. _(главы 2, 3, 4)_

**Synced** — статус Application, когда состояние кластера совпадает с Git. _(главы 3, 4)_

**OutOfSync** — статус Application, когда Git и кластер различаются и требуется синхронизация. _(главы 3, 4)_

**Healthy** — состояние ресурсов Application, когда Pod, Service и прочее работают штатно. _(глава 3)_

**Degraded** — состояние, когда манифесты применены, но рабочие нагрузки (Pod/Service) в плохом состоянии. _(главы 3, 4)_

**Self-Heal (selfHeal)** — режим ArgoCD, при котором ручные изменения в кластере автоматически откатываются к состоянию из Git. _(глава 2)_

**Prune** — удаление ArgoCD из кластера ресурсов, которых больше нет в Git, чтобы кластер точно соответствовал репозиторию. _(глава 3)_

**Auto-sync (automated)** — политика, при которой ArgoCD синхронизирует изменения из Git без ручного нажатия Sync. _(главы 2, 3)_

**Pull-based deploy (pull-модель)** — модель доставки, где агент внутри кластера сам тянет манифесты из Git. _(глава 2)_

**Push-based deploy (push-модель)** — модель доставки, где внешний CI применяет изменения в кластер по credentials. _(глава 2)_

**ArgoCD** — GitOps-контроллер для Kubernetes, синхронизирующий кластер с Git и показывающий статус в UI/CLI. _(главы 3, 4)_

**Flux** — альтернативный ArgoCD GitOps-инструмент с тем же pull-подходом, реализующий reconciliation через набор контроллеров. _(глава 2)_

**Application (CRD)** — кастомный ресурс ArgoCD (`argoproj.io/v1alpha1`), описывающий source (откуда брать) и destination (куда применять). _(главы 3, 4)_

**ApplicationSet** — ресурс ArgoCD, генерирующий множество Application из шаблона, например по окружениям dev/prod. _(приложение A)_

**application-controller** — компонент ArgoCD, выполняющий цикл reconciliation и выставляющий статус Synced/OutOfSync. _(глава 3)_

**repo-server** — компонент ArgoCD, который тянет репозиторий и рендерит итоговые манифесты (Helm/Kustomize). _(глава 3)_

**argocd-server** — компонент ArgoCD, предоставляющий UI, CLI и API. _(глава 3)_

**source / destination** — поля Application: `source` указывает репозиторий, ветку и путь; `destination` — кластер и namespace. _(глава 3)_

**targetRevision** — ветка, тег или коммит в Git, которые ArgoCD считает желаемым состоянием. _(глава 3)_

**repoURL** — адрес Git-репозитория с манифестами, который отслеживает Application. _(глава 3)_

**app-code** — репозиторий с исходным кодом, Dockerfile и тестами; меняют разработчики. _(глава 2)_

**app-infra** — репозиторий с Helm values и манифестами K8s; обновляет CI. _(главы 2, 4)_

**Два репозитория (разделение)** — практика держать код и инфраструктуру раздельно, чтобы коммиты CI не смешивались с коммитами разработчиков. _(глава 2)_

**ArgoCD Image Updater** — дополнение, которое само отслеживает новые теги образа в registry и обновляет Application без `sed`-правок. _(глава 4)_

**Image tag (тег образа)** — метка образа в registry; в книге используется SHA коммита, чтобы образ был однозначно привязан к коду. _(главы 1, 4)_

**Registry (реестр образов)** — хранилище Docker-образов (ghcr.io и др.), куда CI пушит собранный образ. _(главы 1, 4)_

**CI pipeline (пайплайн)** — автоматическая цепочка test → build → push в GitLab CI или GitHub Actions. _(глава 1)_

**GitLab CI** — система CI/CD на основе `.gitlab-ci.yml` со стадиями и job. _(глава 1)_

**GitHub Actions** — система CI/CD на основе workflow-файлов в `.github/workflows`. _(глава 1)_

**Полный цикл (0 ручных шагов)** — поток git push → CI → обновление infra-repo → ArgoCD → кластер без участия человека. _(глава 4)_

**Diff** — сравнение Git и кластера, показывающее, какие ресурсы изменятся при следующем sync. _(глава 3)_

**Rollback (откат)** — возврат приложения к предыдущей ревизии через `argocd app rollback`. _(главы 3, 4)_

**git revert rollback** — откат в GitOps через коммит, отменяющий изменения; кластер подтягивает его как обычный коммит, и история остаётся целостной. _(глава 4)_

**Revision (ревизия)** — конкретная точка в истории деплоев Application, к которой можно откатиться (`argocd app history`). _(главы 3, 4)_

**Progressive Delivery** — постепенная выкатка новой версии с контролем метрик вместо мгновенной замены всего сразу. _(глава 5)_

**Argo Rollouts** — контроллер для Canary и Blue-Green стратегий поверх Kubernetes. _(глава 5)_

**Rollout (CRD)** — ресурс Argo Rollouts, заменяющий Deployment и описывающий стратегию постепенной выкатки. _(глава 5)_

**Canary** — стратегия, при которой новая версия получает растущую долю трафика (20% → 50% → 100%) с паузами для наблюдения. _(глава 5)_

**setWeight** — шаг Canary, задающий процент трафика на новую версию. _(глава 5)_

**pause** — шаг Canary, останавливающий выкатку на заданное время для проверки метрик. _(глава 5)_

**Blue-Green** — стратегия с двумя средами (active и preview) и ручным переключением трафика через promote. _(глава 5)_

**Promote (продвижение)** — команда, переводящая Canary/Blue-Green на следующий шаг или на полный трафик. _(глава 5)_

**Abort (прерывание)** — команда, отменяющая выкатку и возвращающая весь трафик на стабильную версию. _(глава 5)_

**AnalysisRun** — объект Argo Rollouts с результатами анализа метрик во время выкатки; его fail может застопорить Rollout. _(приложение A)_
