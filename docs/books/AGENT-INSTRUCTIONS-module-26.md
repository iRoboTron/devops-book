## Контекст проекта

Читатель прошёл DevOps 1.0, настроил сервер, применил hardening. Теперь он хочет убедиться что всё работает как ожидается.

**Что его беспокоит:**
- Непонятно «дырявый» ли сервер прямо сейчас
- Слышал про «пентест», но это звучит как что-то для корпораций
- Не знает какие инструменты использовать и что искать
- Боится что Docker-образы содержат уязвимости
- Хочет делать такую проверку регулярно, а не один раз

**Что он хочет после этой книги:**
Уметь систематически проверить свой сервер: периметр, web, контейнеры, конфигурация. Оформить отчёт для себя. Делать это раз в квартал как часть обслуживания.

## Главная идея

Аудит — это не взлом. Это проверка своего сервера теми же инструментами которыми пользуются атакующие — но с разрешения и на своём железе.

```
Аудит vs Пентест:

Аудит:                     Пентест:
«Что открыто у меня?»      «Могу ли я взломать цель?»
Проверяю своё              Разрешение на чужое
Нахожу, документирую       Нахожу, эксплуатирую, отчитываюсь
Делаю регулярно            Разовое мероприятие
```

**Ключевое понимание:**
- nmap — это «посмотреть на свой сервер снаружи». Это легально и полезно для своего сервера.
- Большинство «взломов» — это незакрытые CVE и дефолтные настройки. Аудит их находит.
- Отчёт для себя важнее идеального инструментария.

## Структура книги

### Глава 0: Что такое аудит и зачем он нужен

**Цель:** понять разницу аудита, пентеста и hardening.

Объяснить три связанных понятия:

| Действие | Вопрос | Кто делает | Как часто |
|---|---|---|---|
| Hardening | «Как защитить?» | Администратор | При настройке |
| Аудит | «Насколько защищено?» | Администратор сам | Регулярно |
| Пентест | «Можно ли взломать?» | Специалист по ИБ | По заказу |

Правовая рамка:
- Сканирование своего сервера — абсолютно легально
- Сканирование чужих IP без разрешения — нарушение закона в большинстве стран
- Всё что в книге — только на своём оборудовании

Цикл аудита:
```
Запустить инструменты
    ↓
Собрать результаты
    ↓
Понять что значит каждая находка
    ↓
Приоритизировать: критично / важно / информационно
    ↓
Исправить критичные
    ↓
Задокументировать
    ↓
Повторить через 3 месяца
```

### Глава 1: nmap — посмотреть на свой сервер снаружи

**Цель:** читатель умеет просканировать свой сервер и понять результат.

Установка:
```bash
sudo apt install nmap
```

Базовое сканирование своего IP:
```bash
# Простое сканирование популярных портов
nmap <ВАШ_СЕРВЕР_IP>

# Пример вывода:
# PORT     STATE SERVICE
# 22/tcp   open  ssh
# 80/tcp   open  http
# 443/tcp  open  https
# 8080/tcp open  http-proxy  ← вот это не должно быть открыто!
```

Расширенное сканирование:
```bash
# Все 65535 портов (медленнее но полнее)
nmap -p- <IP>

# С определением версий сервисов
nmap -sV <IP>

# С проверкой операционной системы (может требовать sudo и быть шумнее)
nmap -O <IP>

# Сохранить результат
nmap -sV <IP> -oN nmap-results.txt
```

Разбирать каждый флаг с объяснением.

Интерпретация результатов:
```
open   → порт открыт и принимает соединения
closed → порт закрыт, сервис не запущен
filtered → firewall блокирует (нет ответа)
```

Что искать в результатах:
- Неожиданные open порты — сервисы которые не должны быть видны
- Версии с известными CVE
- Дефолтные сервисы на стандартных портах

**Практика:** просканировать свой сервер, сравнить результат с тем что должно быть открыто.

Перед практикой явно зафиксировать scope: один свой IP или домен. Не сканировать диапазоны, соседние IP провайдера и чужие домены.

### Глава 2: Проверка SSL/TLS конфигурации

**Цель:** HTTPS настроен правильно, нет слабых шифров.

Онлайн-инструменты (для проверки из внешней сети):
- SSL Labs: `ssllabs.com/ssltest/` — подробный анализ, оценка A/B/F
- testssl.sh — локальный инструмент

```bash
# testssl.sh — полная проверка конфигурации
docker run --rm -ti drwetter/testssl.sh https://yourdomain.com

# Или установить локально
apt install testssl.sh
testssl.sh yourdomain.com
```

Что проверять:
- Версии TLS: TLS 1.2 и 1.3 — норм, TLS 1.0/1.1 — проблема
- Слабые шифры (RC4, DES, 3DES)
- Perfect Forward Secrecy
- HSTS заголовок
- Срок действия сертификата

Пример исправления в Nginx:
```nginx
# Разрешить только современные протоколы
ssl_protocols TLSv1.2 TLSv1.3;

# Безопасные шифры
# В реальном конфиге нельзя оставлять многоточие.
# Лучше взять полный актуальный пример из Mozilla SSL Configuration Generator.
ssl_prefer_server_ciphers off;

# HSTS
add_header Strict-Transport-Security "max-age=63072000" always;
```

HSTS не включать механически на тестовых доменах. Объяснить, что браузер запоминает принудительный HTTPS, и ошибка в настройке может временно заблокировать удобный доступ к сайту.

SSL Labs отправляет домен на внешний сервис проверки. Для публичного домена это нормально, для приватного внутреннего сервиса лучше использовать локальный `testssl.sh`.

### Глава 3: HTTP заголовки безопасности

**Цель:** веб-сервер отдаёт правильные security headers.

Проверить текущие заголовки:
```bash
# С curl
curl -I https://yourdomain.com

# Или с httpx (если установлен)
curl -s -D - https://yourdomain.com -o /dev/null | grep -i "security\|x-frame\|content-sec\|strict"
```

Обязательные заголовки и почему:

| Заголовок | Назначение | Пример значения |
|---|---|---|
| `X-Frame-Options` | Защита от clickjacking | `DENY` |
| `X-Content-Type-Options` | Запрет угадывания MIME | `nosniff` |
| `Strict-Transport-Security` | Форсировать HTTPS | `max-age=31536000` |
| `X-XSS-Protection` | Устаревший заголовок для старых браузеров | обычно не нужен |
| `Referrer-Policy` | Контроль referrer | `strict-origin-when-cross-origin` |
| `Content-Security-Policy` | Контроль источников | зависит от приложения |

Добавить в Nginx:
```nginx
add_header X-Frame-Options "DENY" always;
add_header X-Content-Type-Options "nosniff" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
```

Проверить результат: securityheaders.com или повторный curl.

Content-Security-Policy не копировать вслепую. Для Nextcloud, Grafana и других сложных приложений строгая CSP может сломать интерфейс.

### Глава 4: nikto — базовое сканирование веб-сервера

**Цель:** автоматическая проверка типичных веб-уязвимостей.

```bash
sudo apt install nikto

# Сканировать свой сервер
nikto -h https://yourdomain.com

# Сохранить результат
nikto -h https://yourdomain.com -o nikto-report.txt -Format txt
```

Интерпретация вывода:
```
+ Server leaks inforamtion via "X-Powered-By" HTTP response header
  → раскрывает технологию. Убрать: proxy_hide_header X-Powered-By;

+ The X-XSS-Protection header is not defined
  → добавить заголовок

+ /phpmyadmin/: phpMyAdmin directory found
  → это критично если phpMyAdmin открыт всем
```

Важно объяснить: nikto генерирует много шума (false positives). Каждую находку надо проверить вручную, не паниковать от количества.

### Глава 5: trivy — сканирование Docker-образов

**Цель:** Docker-образы не содержат известных CVE.

```bash
# Установка
sudo apt install trivy
# или
curl -sfL https://raw.githubusercontent.com/aquasecurity/trivy/main/contrib/install.sh | sh

# Сканировать образ
trivy image nginx:latest

# Пример вывода:
# nginx:latest (debian 12.5)
# ========================
# Total: 25 (UNKNOWN: 0, LOW: 12, MEDIUM: 8, HIGH: 4, CRITICAL: 1)
#
# CRITICAL: CVE-2024-XXXX — описание уязвимости
```

Сканировать все запущенные контейнеры:
```bash
# Список образов
docker images --format "{{.Repository}}:{{.Tag}}"

# Сканировать каждый
for img in $(docker images --format "{{.Repository}}:{{.Tag}}"); do
  echo "=== $img ==="
  trivy image --severity HIGH,CRITICAL "$img"
done
```

Интерпретация severity:
- CRITICAL: исправить немедленно, обновить образ
- HIGH: обновить в ближайшее время
- MEDIUM/LOW: планово

Когда обновлять образы:
```bash
# Посмотреть устаревшие образы
docker images --format "table {{.Repository}}\t{{.Tag}}\t{{.CreatedAt}}"

# Обновить образ
docker pull nginx:latest
docker compose up -d nginx  # применить новый образ
```

### Глава 6: lynis — системный аудит (в контексте аудита)

**Цель:** использовать lynis не как hardening-инструмент, а как аудитный.

Напоминание из книги 25 + новое:
```bash
sudo lynis audit system --quiet
# Показывает только предупреждения, без verbose

# Сохранить полный отчёт
sudo lynis audit system --report-file /var/log/lynis/$(date +%Y%m%d)-report.dat
```

Отслеживать динамику:
- Сохранять результаты с датой
- Сравнивать hardening index между проверками
- Список активных suggestion-ов как backlog задач

### Глава 7: Проверка логов как источника информации

**Цель:** читатель умеет находить аномалии в логах.

Что искать в SSH логах:
```bash
# Топ IP с неудачными попытками
grep "Failed password" /var/log/auth.log | \
  awk '{print $11}' | sort | uniq -c | sort -rn | head -20

# Успешные входы
grep "Accepted" /var/log/auth.log

# Вход под root (должно быть пусто если PermitRootLogin no)
grep "Accepted.*root" /var/log/auth.log
```

Что искать в Nginx логах:
```bash
# Попытки сканирования
grep -E "\.php|\.env|admin|wp-login|phpmyadmin" /var/log/nginx/access.log | \
  tail -20

# 4xx и 5xx ответы
awk '$9 >= 400' /var/log/nginx/access.log | \
  awk '{print $9}' | sort | uniq -c | sort -rn

# Топ IP по запросам
awk '{print $1}' /var/log/nginx/access.log | \
  sort | uniq -c | sort -rn | head -10
```

Аномалии которые стоит расследовать:
- IP которого нет в fail2ban banned но много ошибок
- Успешный вход SSH в неожиданное время
- Запросы к несуществующим путям которые совпадают с известными уязвимостями

### Глава 9: Итоговый проект — квартальный аудит

**Цель:** провести полный аудит своего сервера и оформить отчёт.

1. **Периметр:** nmap -sV свой IP → таблица открытых портов
2. **SSL:** testssl.sh или SSL Labs → оценка и список проблем
3. **Заголовки:** curl -I → проверить security headers
4. **Web:** nikto → выбрать 3-5 важных находки
5. **Docker:** trivy по всем образам → список CRITICAL/HIGH
6. **Система:** lynis → hardening index и suggestion-ы
7. **Логи:** проверить auth.log и nginx access.log за последнюю неделю
8. **Отчёт:** заполнить шаблон, приоритизировать находки
9. **Исправить** найденные критичные проблемы
10. **Запланировать** следующий аудит

## Особые требования

### Критерии готовности

Книга должна закончиться не набором сканов, а отчётом и планом исправлений. Обязательно проверить:

- scope аудита записан до запуска инструментов;
- результаты сохранены в папку с датой, например `audits/2026-05-06/`;
- для каждой находки есть доказательство: команда, файл отчёта или строка лога;
- false positive разобраны отдельно;
- critical/high находки имеют конкретное действие;
- следующий аудит запланирован.

### Правовая рамка
В каждой главе где запускается сканирование — напоминать: только свой сервер. Один раз явно объяснить почему сканирование чужих IP незаконно.

### Про false positives
nikto и другие инструменты генерируют много шума. Учить читателя не паниковать, а разбирать каждую находку.

### Не делать
- Не давать команды для атаки на чужие системы
- Не описывать эксплуатацию уязвимостей
- Не делать из книги «Hacking for Beginners»
- Не углубляться в OWASP Top 10 детально — это для следующего уровня
