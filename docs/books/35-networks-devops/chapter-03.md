- Как смотреть порты через `ss`

## 3.1. TCP: надёжность через установку соединения

TCP (Transmission Control Protocol) — это протокол с установкой соединения. Прежде чем передавать данные, клиент и сервер обмениваются тремя сообщениями — **тройным рукопожатием (three-way handshake)**.

```
Клиент                          Сервер
  │                               │
  │──── SYN (seq=x) ────────────► │
  │◄─── SYN-ACK (seq=y, ack=x+1) ─│
  │──── ACK (ack=y+1) ───────────► │
  │          [соединение открыто]   │
  │          ░ передача данных ░    │
  │──── FIN ────────────────────► │
  │◄─── ACK ──────────────────── │
  │◄─── FIN ──────────────────── │
  │──── ACK ────────────────────► │
```

### Как это работает

1. **Клиент → Сервер: SYN** — клиент отправляет пакет с флагом SYN и начальным порядковым номером `seq=x`.
2. **Сервер → Клиент: SYN-ACK** — сервер отвечает SYN-ACK: подтверждает получение (`ack=x+1`) и отправляет свой начальный номер (`seq=y`).
3. **Клиент → Сервер: ACK** — клиент подтверждает SYN сервера (`ack=y+1`). Соединение установлено.

После этого начинается передача данных с подтверждением каждого пакета (или группы пакетов). Если подтверждение не пришло — таймер ретрансмиссии, пакет отправляется снова.

### Завершение соединения (four-way handshake)

1. Одна сторона отправляет **FIN**.
2. Другая отвечает **ACK** и потом отправляет свой **FIN**.
3. Первая сторона подтверждает **ACK**.

Каждое направление закрывается независимо — отсюда 4 шага.

### Ключевые свойства TCP

| Свойство | Значение |
|---|---|
| Надёжность | Гарантирует доставку, порядок, отсутствие дубликатов |
| Установка соединения | Да (3-way handshake) |
| Скорость | Ниже, чем UDP (заголовки, подтверждения) |
| Использование | HTTP, HTTPS, SSH, SMTP, FTP, базы данных |

## 3.2. UDP: скорость без гарантий

UDP (User Datagram Protocol) не устанавливает соединение. Вы просто отправляете датаграмму на адрес получателя — и всё. Нет подтверждений, нет ретрансмиссии, нет гарантии порядка.

```
  ┌──────────────────────┐
  │      UDP пакет       │
  │  src port │ dst port │
  │  length   │ checksum │
  │       data ...       │
  └──────────────────────┘
```

### Когда выбирать UDP вместо TCP

| Протокол / случай | Почему UDP |
|---|---|
| DNS (запросы) | Один запрос — один ответ. Переспросить при таймауте |
| DHCP | Широковещательный запрос, TCP не подходит |
| VoIP / RTP | Теряем пакет — теряем 20 мс речи. Ждать ретрансмиссию нельзя |
| Видео-стриминг (WebRTC) | Пропуск кадра лучше задержки |
| QUIC / HTTP/3 | Google перевёл HTTP на UDP с контролем на уровне приложения |
| Syslog | Потеря лога допустима, задержка — нет |
| NTP | Точное время, минимум задержки |

```bash
# чем отличается поведение TCP и UDP на примере DNS
# TCP-запрос — устанавливается соединение, передача, закрытие
# UDP-запрос — одна датаграмма туда, одна обратно
dig +tcp google.com   # принудительно TCP
dig google.com        # по умолчанию UDP
```

### Сравнение TCP и UDP

| Критерий | TCP | UDP |
|---|---|---|
| Установка соединения | Да | Нет |
| Надёжность | Гарантирована | Не гарантирована |
| Порядок пакетов | Сохраняется | Не гарантируется |
| Заголовок | 20–60 байт | 8 байт |
| Ретрансмиссия | Есть | Нет |
| Контроль перегрузки | Есть | Нет |
| Подходит для | Веб, почта, БД, SSH | DNS, VoIP, видео, NTP |

## 3.3. Порты

Порт — это 16-битное число от 0 до 65535. В комбинации с IP-адресом он определяет, какому процессу на хосте предназначены данные.

### Диапазоны портов

| Диапазон | Название | Описание |
|---|---|---|
| 0–1023 | Well-known (системные) | Требуют `sudo` для открытия |
| 1024–49151 | Registered | Может открывать обычный пользователь |
| 49152–65535 | Dynamic / Ephemeral | Временные порты для клиентов |

### Известные порты

| Порт | Протокол | Сервис |
|---|---|---|
| 22 | TCP | SSH |
| 53 | TCP/UDP | DNS |
| 80 | TCP | HTTP |
| 443 | TCP | HTTPS |
| 3306 | TCP | MySQL |
| 5432 | TCP | PostgreSQL |
| 6379 | TCP | Redis |
| 8080 | TCP | HTTP (альтернатива) |
| 9090 | TCP | Prometheus / OpenMetrics |
| 9200 | TCP | Elasticsearch |

```bash
# посмотреть, какой процесс слушает порт 80
sudo ss -tlnp | grep ':80\b'
```

## 3.4. Сокет

Сокет (socket) — это комбинация **IP-адрес : порт**. Пара сокетов (клиентский и серверный) образует соединение.

```
Сокет клиента:      192.168.1.100:54321
Сокет сервера:      10.0.0.10:443
Соединение:         (192.168.1.100:54321) ⇄ (10.0.0.10:443)
```

Одна пара — одно соединение. Сервер на порту 443 может держать десятки тысяч соединений — каждое со своим клиентским сокетом.

```bash
# посмотреть все установленные соединения
ss -tnp
# State    Recv-Q  Send-Q  Local Address:Port    Peer Address:Port    Process
# ESTAB    0       0       192.168.1.100:22       10.0.0.1:45000       users:(("sshd",pid=1234))
# ESTAB    0       0       192.168.1.100:443      10.0.0.2:51000       users:(("nginx",pid=5678))
```

Каждая строка — одно соединение между двумя сокетами.

## 3.5. Состояния TCP

TCP-соединение проходит через несколько состояний. Их понимание критично для диагностики сети.

### Основные состояния

| Состояние | Значение | Что делать |
|---|---|---|
| `LISTEN` | Сервер ждёт входящие соединения на порту | Норма |
| `SYN-SENT` | Клиент отправил SYN, ждёт ответ | Норма, если кратко |
| `SYN-RECV` | Сервер получил SYN, отправил SYN-ACK | Норма |
| `ESTABLISHED` | Соединение установлено, передача данных | Норма |
| `FIN-WAIT-1` | Сторона инициировала закрытие | Норма |
| `FIN-WAIT-2` | Сторона получила ACK на свой FIN, ждёт FIN от другой | Норма (кратко) |
| `CLOSE-WAIT` | Получен FIN от другой стороны, своя сторона ещё не закрыла сокет | Если много — приложение не зовёт `close()` |
| `TIME-WAIT` | Соединение закрыто, ждём 2MSL (~60 с) перед очисткой | Норма. Много — при высокой нагрузке |
| `LAST-ACK` | Сторона отправила FIN, ждёт ACK | Норма (кратко) |

### Когда беспокоиться

**Много TIME-WAIT — нормально.**
На высоконагруженном сервере (nginx, haproxy) могут быть десятки тысяч TIME-WAIT. Это не проблема — ядро очищает их через 60 секунд. Если не хватает портов — есть `net.ipv4.tcp_tw_reuse`.

```bash
# сводка по состояниям
ss -s
# Total: 1234 (kernel 2345)
# TCP:   567 (estab 89, closed 345, orphaned 0, synrecv 0, timewait 78/0), ports 45
```

**Много CLOSE-WAIT — проблема.**
Если видите десятки соединений в CLOSE-WAIT — приложение не закрывает сокеты (баг). Растут дескрипторы, в какой-то момент новые соединения невозможны.

```bash
# найти процессы с CLOSE-WAIT
ss -tnp state close-wait
```

### Типичное состояние сервера

```bash
ss -tlnp
# State    Recv-Q  Send-Q  Local Address:Port    Peer Address:Port    Process
# LISTEN   0       128     0.0.0.0:22            0.0.0.0:*           users:(("sshd",pid=1234))
# LISTEN   0       128     0.0.0.0:80            0.0.0.0:*           users:(("nginx",pid=5678))
# LISTEN   0       128     0.0.0.0:443           0.0.0.0:*           users:(("nginx",pid=5678))
```

- `0.0.0.0:22` — слушает на всех интерфейсах (IPv4).
- `0.0.0.0:*` — от любого клиента.
- `Recv-Q 0` — очередь приёма пуста (данных нет, или всё обработано).
- `Send-Q 128` — размер backlog (максимальная длина очереди необработанных SYN).

```bash
# слушающие UDP сокеты
ss -ulnp
# State    Recv-Q  Send-Q  Local Address:Port    Peer Address:Port    Process
# UNCONN   0       0       0.0.0.0:53            0.0.0.0:*           users:(("systemd-resolve",pid=789))
# UNCONN   0       0       0.0.0.0:67            0.0.0.0:*           users:(("dhclient",pid=1011))
```

У UDP нет состояния `LISTEN` — только `UNCONN` (unconnected).

## 3.6. ss — смотреть сокеты

Команда `ss` (socket statistics) читает информацию о сокетах прямо из ядра. Она быстрее и информативнее устаревшего `netstat`.

```bash
# слушающие TCP-сокеты (с процессом)
ss -tlnp

# установленные TCP-соединения
ss -tnp

# все UDP-сокеты
ss -ulnp

# все сокеты (все протоколы)
ss -anp

# сводка по протоколам и состояниям
ss -s

# фильтр по порту
ss -tnp '( dport = :443 or sport = :443 )'

# фильтр по состоянию
ss -tnp state established

# исключить listen
ss -tnp state not listen

# соединения с конкретным хостом
ss -tnp dst 10.0.0.1

# Unix-сокеты
ss -xlp
```

### Расшифровка флагов

| Флаг | Значение |
|---|---|
| `-t` | TCP |
| `-u` | UDP |
| `-l` | Listening (только слушающие) |
| `-n` | Не резолвить DNS (числовой вывод) |
| `-p` | Показать процесс (требует `sudo`) |
| `-a` | Все (и listen, и established) |
| `-s` | Сводка |
| `-x` | Unix-сокеты |
| `-4` | Только IPv4 |
| `-6` | Только IPv6 |

## 3.7. nc — проверить порт

`nc` (netcat) — швейцарский нож для проверки сетевой доступности.

```bash
# проверить TCP-порт (открыт ли)
nc -zv 192.168.1.10 80

# с таймаутом (3 секунды)
nc -zv -w 3 192.168.1.10 80

# проверить UDP-порт (осторожно — UDP stateless)
nc -zuv 192.168.1.10 53

# открыть порт для теста
nc -l 9999

# подключиться (второй терминал)
nc 127.0.0.1 9999
# теперь всё, что печатаете в одном окне — появляется в другом
```

> ☠️ **Осторожно:** `nc -zuv` для UDP может давать ложноположительные результаты. UDP — без установки соединения, и отсутствие ответа ≠ порт закрыт. Файрвол может просто дропать пакеты.

### Разница между Connection refused и timed out

```bash
nc -zv 192.168.1.10 81
# nc: connect to 192.168.1.10 port 81 (tcp) failed: Connection refused
```

- **Connection refused** — сервер получил SYN и ответил RST (ничего не слушает на этом порту). Пакет дошёл.

```bash
nc -zv -w 3 10.0.0.200 80
# nc: connect to 10.0.0.200 port 80 (tcp) timed out: Operation now in progress
```

- **Timed out** — пакет не дошёл или ответ не вернулся. Причины: фаервол дропает, нет маршрута, хост выключен.

---

## Типичные ошибки

1. **Connection refused vs timed out.** Connection refused = порт точно закрыт (или не тот IP). Timed out = пакет не дошёл (фаервол, нет маршрута). Не путайте эти сценарии.

2. **Сервис слушает на 127.0.0.1, а вы проверяете через внешний IP.** Если `ss -tlnp` показывает `127.0.0.1:8080`, а не `0.0.0.0:8080` — сервис доступен только с localhost. С другого хоста будет Connection refused. Исправляется в конфиге приложения (например, `bind 0.0.0.0`).

3. **CLOSE-WAIT — проблема приложения.** Если видите десятки или сотни сокетов в CLOSE-WAIT — ищите баг в коде: сокет не закрывается после завершения работы. Растут файловые дескрипторы → отказ в новых соединениях.

4. **Сервис на порту есть, а не отвечает.** `ss -tlnp` показывает процесс на порту, но `nc -zv` выдаёт таймаут. Возможная причина: сервис подвис (accept не вызывается), либо фаервол блокирует входящие соединения (`iptables` / `nftables`).

## Попробуйте сами

1. **Исследуйте сокеты своего хоста.** Выполните `ss -tlnp`, `ss -ulnp`, `ss -s`. Найдите, какие сервисы слушают порты. Сколько соединений в ESTABLISHED? Есть ли TIME-WAIT?

2. **Проверьте порт через nc.** Откройте в одном окне `nc -l 9999`. Во втором окне выполните `nc -zv 127.0.0.1 9999` и `nc -zv 127.0.0.1 9998`. Первый должен ответить connected, второй — Connection refused. Подключитесь ко второму окну: `nc 127.0.0.1 9999` и отправьте сообщение.

3. **Симуляция CLOSE-WAIT.** Напишите простой скрипт на bash, который открывает TCP-соединение, читает первые 100 байт и завершается не закрывая сокет. Посмотрите `ss -tnp state close-wait`. Если не получается — просто откройте `nc google.com 80`, отправьте `GET / HTTP/1.0\r\n\r\n` и закройте только входящую часть (Ctrl+D) — увидите состояние.
