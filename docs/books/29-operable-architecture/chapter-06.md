# Глава 6: Миграции базы данных

> **Цель:** понять самый частый источник болезненных релизов.

---

## 6.1 Почему БД сложнее кода

Код можно откатить на предыдущую версию. С БД сложнее: данные уже изменились, таблица уже мигрировала, колонка уже удалена.

Поэтому rollback приложения не всегда означает rollback системы.

---

## 6.2 Типы миграций

| Тип | Пример | Риск |
|---|---|---|
| schema migration | добавить колонку | блокировки, несовместимость |
| data migration | заполнить новые поля | долго, ошибки данных |
| destructive migration | удалить колонку | ломает старый код |
| index migration | добавить индекс | может грузить БД |

---

## 6.3 Expand / contract

Идея: не ломать старую версию сразу. Вместо одного большого изменения схема меняется постепенно — через несколько релизов. Каждый релиз должен быть совместим с предыдущей версией приложения.

Полный пример: `users.full_name → first_name / last_name`

---

### Релиз 1 — добавляем новые колонки (expand)

```sql
-- Безопасно: добавляем nullable-колонки.
-- Старый код работает без изменений, он просто не знает об этих колонках.
ALTER TABLE users ADD COLUMN first_name VARCHAR(100);
ALTER TABLE users ADD COLUMN last_name VARCHAR(100);
```

Деплоим. Старая версия приложения продолжает читать и писать только `full_name`. Новые колонки пустые — это нормально.

---

### Релиз 2 — новый код пишет в обе схемы

```python
# Псевдокод — новая версия приложения
def create_user(full_name: str):
    first, *rest = full_name.split(" ", 1)
    last = rest[0] if rest else ""
    db.execute(
        """
        INSERT INTO users (full_name, first_name, last_name)
        VALUES (:full_name, :first_name, :last_name)
        """,
        {"full_name": full_name, "first_name": first, "last_name": last},
    )
```

На этом шаге приложение пишет одновременно в старое поле `full_name` и в новые `first_name` / `last_name`. Если нужно откатиться на предыдущий релиз — откатываемся, старый код видит `full_name` и работает.

---

### Релиз 3 — заполняем исторические данные (backfill)

```sql
-- Заполняем строки, которые были созданы до Релиза 2
-- и у которых first_name ещё NULL.
UPDATE users
   SET first_name = split_part(full_name, ' ', 1),
       last_name  = split_part(full_name, ' ', 2)
 WHERE first_name IS NULL;

-- Для больших таблиц делаем батчами, чтобы не заблокировать таблицу:
-- UPDATE users SET ... WHERE id BETWEEN 1 AND 10000 AND first_name IS NULL;
-- UPDATE users SET ... WHERE id BETWEEN 10001 AND 20000 AND first_name IS NULL;
-- ...
```

После этого шага все строки содержат данные в новой схеме. Проверяем:

```sql
SELECT COUNT(*) FROM users WHERE first_name IS NULL;
-- должно вернуть 0
```

---

### Релиз 4 — удаляем старую колонку (contract)

```sql
-- Теперь безопасно: новый код уже не использует full_name,
-- все данные перенесены, backfill проверен.
ALTER TABLE users ALTER COLUMN first_name SET NOT NULL;
ALTER TABLE users ALTER COLUMN last_name  SET NOT NULL;
ALTER TABLE users DROP COLUMN full_name;
```

---

### Почему нельзя удалить `full_name` в Релизе 1

Именно это и приводит к типичным инцидентам в продакшене:

1. Разработчик делает в одном PR и миграцию `DROP COLUMN full_name`, и новый код, который читает `first_name`.
2. Миграция применяется до деплоя нового кода (это стандартная практика "migrations first").
3. Старый код, который ещё запущен на серверах, пытается прочитать `full_name`.
4. PostgreSQL возвращает ошибку `column "full_name" does not exist`.
5. Все запросы к сервису падают с 500. Инцидент.

Expand/contract гарантирует, что в любой момент времени хотя бы одна работающая версия кода совместима с текущей схемой БД.

---

## 6.4 Перед миграцией

Проверь:

- есть backup;
- restore проверялся;
- известен размер таблицы;
- миграция тестировалась на копии;
- понятно, сколько она займёт;
- есть план rollback или forward-fix.

---

## 6.5 Практика

Разбери миграцию:

```text
Нужно заменить поле address на city, street, house.
```

Заполни:

| Релиз | Что меняем | Почему безопасно |
|---|---|---|
| 1 | добавить новые поля | старый код не ломается |
| 2 | писать в обе схемы | совместимость |
| 3 | backfill | данные перенесены |
| 4 | удалить старое | после проверки |

Проверка: ни один шаг не должен ломать старую работающую версию без плана.
