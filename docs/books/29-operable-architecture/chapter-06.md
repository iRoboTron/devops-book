# Глава 6. Данные, миграции и совместимость

Данные — самая ценная часть большинства систем.

Код можно переписать. Сервер можно заменить. Контейнер можно пересобрать. Но если потеряны данные пользователей, заявок, документов или платежей — это уже серьёзная авария.

Поэтому архитектура для эксплуатации всегда задаёт вопрос:

> Что произойдёт с данными во время изменения системы?

---

## 6.1. Почему миграции опаснее обычного кода

Обычный код часто можно откатить:

- вернуть предыдущий Docker-образ;
- отменить коммит;
- переключить трафик на старую версию.

С данными сложнее.

Если миграция:

- удалила колонку;
- изменила формат значений;
- объединила таблицы;
- испортила часть записей;
- запустилась два раза;

то простой rollback приложения может уже не помочь.

Главное правило:

> Миграция данных должна проектироваться так же внимательно, как изменение продакшен-инфраструктуры.

---

## 6.2. Плохая миграция

Представим таблицу пользователей:

```sql
users(id, name, email)
```

Команда решила разделить имя на имя и фамилию:

```sql
ALTER TABLE users DROP COLUMN name;
ALTER TABLE users ADD COLUMN first_name TEXT;
ALTER TABLE users ADD COLUMN last_name TEXT;
```

Проблемы:

- старое приложение сломается;
- данные из `name` потеряны;
- невозможно быстро откатиться;
- если миграция прервётся, состояние базы будет непонятным.

Это пример изменения, которое удобно разработчику, но опасно для эксплуатации.

---

## 6.3. Подход expand/contract

Безопаснее использовать подход **expand/contract**.

Идея простая:

1. **Expand** — добавить новое, не ломая старое.
2. **Migrate** — постепенно перенести данные.
3. **Switch** — переключить приложение на новый формат.
4. **Contract** — удалить старое только после проверки.

---

## 6.4. Пример безопасной миграции

Было:

```sql
users(id, name, email)
```

Нужно получить:

```sql
users(id, first_name, last_name, email)
```

### Шаг 0. Подготовка

Перед миграцией нужно:

- сделать свежий бэкап;
- проверить, что бэкап можно восстановить;
- оценить размер таблицы;
- понять, сколько времени займёт миграция;
- проверить миграцию на копии базы;
- подготовить план отката.

Важно:

> SQL ниже — учебный пример. На реальной базе команды нужно адаптировать под версию СУБД, объём данных, индексы, блокировки и политику бэкапов.

### Шаг 1. Добавить новые колонки

```sql
ALTER TABLE users ADD COLUMN first_name TEXT;
ALTER TABLE users ADD COLUMN last_name TEXT;
```

Старое приложение продолжает работать, потому что колонка `name` осталась.

### Шаг 2. Научить приложение писать в оба формата

Новая версия приложения при сохранении пользователя пишет:

- старое поле `name`;
- новые поля `first_name` и `last_name`.

Пример на псевдокоде:

```python
full_name = first_name + " " + last_name

save_user({
    "name": full_name,
    "first_name": first_name,
    "last_name": last_name,
})
```

Теперь старая и новая версии приложения совместимы с базой.

### Шаг 3. Перенести старые данные

```sql
UPDATE users
SET
  first_name = split_part(name, ' ', 1),
  last_name = substring(name from position(' ' in name) + 1)
WHERE first_name IS NULL;
```

На большой таблице лучше делать батчами, чтобы не заблокировать базу надолго.

Пример идеи батчевой обработки:

```sql
UPDATE users
SET first_name = split_part(name, ' ', 1)
WHERE first_name IS NULL
  AND id BETWEEN 1 AND 10000;
```

### Шаг 4. Проверить качество переноса

```sql
SELECT COUNT(*) FROM users WHERE first_name IS NULL;
SELECT COUNT(*) FROM users WHERE name IS NULL;
```

Также нужно проверить необычные случаи:

- имя без пробела;
- двойная фамилия;
- пустая строка;
- пользователь с одним словом вместо полного имени;
- разные языки и символы.

### Шаг 5. Переключить чтение

После проверки приложение начинает читать из `first_name` и `last_name`.

Но колонку `name` пока не удаляем.

Почему?

Потому что может понадобиться быстрый rollback приложения.

### Шаг 6. Удалить старое поле позже

Только после периода наблюдения:

- ошибок нет;
- метрики нормальные;
- rollback уже не нужен;
- бэкап есть;
- команда согласовала удаление.

Тогда можно выполнить:

```sql
ALTER TABLE users DROP COLUMN name;
```

## 6.5. Backward compatibility

Backward compatibility — это способность новой системы работать со старым форматом.

Пример:

- старая версия API возвращала `name`;
- новая версия возвращает `first_name` и `last_name`;
- клиенты ещё не обновились.

Плохой вариант:

```json
{
  "first_name": "Ivan",
  "last_name": "Petrov"
}
```

Если старый клиент ждёт `name`, он сломается.

Лучше временно возвращать оба варианта:

```json
{
  "name": "Ivan Petrov",
  "first_name": "Ivan",
  "last_name": "Petrov"
}
```

Старые клиенты работают, новые используют новые поля.

---

## 6.6. Forward compatibility

Forward compatibility — это способность старой части системы не ломаться, если появились новые данные.

Пример:

Старый обработчик получил JSON с неизвестным полем:

```json
{
  "id": 1,
  "email": "user@example.com",
  "telegram": "@user"
}
```

Хороший обработчик игнорирует неизвестное поле, если оно ему не нужно.

Плохой обработчик падает, потому что не ожидал `telegram`.

---

## 6.7. Версионирование API

Если изменение нельзя сделать совместимым, API нужно версионировать.

Пример:

```text
/api/v1/users
/api/v2/users
```

Но версии — это не бесплатное решение.

Минусы:

- нужно поддерживать несколько API;
- сложнее документация;
- больше тестов;
- клиенты могут годами не переходить на новую версию.

Поэтому сначала стоит попробовать совместимое изменение.

---

## 6.8. Миграции и деплой

Опасный вариант:

1. удалить старую колонку;
2. выкатить новый код;
3. надеяться, что всё работает.

Безопаснее:

1. добавить новые поля;
2. выкатить код, который пишет в оба формата;
3. перенести старые данные;
4. выкатить код, который читает новый формат;
5. подождать и проверить;
6. удалить старое.

Такой подход особенно важен, если:

- деплой идёт без остановки сервиса;
- несколько экземпляров приложения работают одновременно;
- есть фоновые задачи;
- есть мобильные клиенты, которые обновляются не сразу;
- данные нельзя потерять.

---

## 6.9. Rollback и roll-forward

Есть два подхода к исправлению неудачного релиза.

### Rollback

Вернуть предыдущую версию.

Плюсы:

- быстро;
- понятно;
- хорошо работает для кода.

Минусы:

- может не сработать после миграции данных;
- старая версия может быть несовместима с новой схемой базы.

### Roll-forward

Не откатываться назад, а быстро выпустить исправление вперёд.

Плюсы:

- полезно, если откат невозможен;
- можно сохранить новую схему.

Минусы:

- требует быстрой и дисциплинированной команды;
- легко ухудшить проблему, если причина не понята.

Вывод:

> Чем больше изменение затрагивает данные, тем важнее заранее понимать стратегию rollback/roll-forward.

---

## 6.10. Бэкапы перед миграциями

Перед серьёзной миграцией нужен не просто файл с бэкапом, а уверенность, что он работает.

Плохой подход:

> «У нас где-то настроены бэкапы».

Хороший подход:

1. создать свежий бэкап;
2. восстановить его на тестовом окружении;
3. проверить количество записей;
4. проверить запуск приложения на восстановленной базе;
5. только потом трогать продакшен.

Для критичных сервисов полезно иметь чек-лист:

```markdown
# Перед миграцией

- [ ] Известно, какие таблицы меняются.
- [ ] Есть свежий бэкап.
- [ ] Бэкап восстановлен на тестовом окружении.
- [ ] Есть план rollback/roll-forward.
- [ ] Оценено время выполнения.
- [ ] Понятно, будут ли блокировки.
- [ ] Команда знает окно работ.
- [ ] Есть ответственный за наблюдение после релиза.
```

## 6.11. Практический пример: миграция email на отдельную таблицу

Было:

```text
users
- id
- email
```

Нужно:

```text
users
- id

user_emails
- id
- user_id
- email
- is_primary
```

Зачем это нужно: у пользователя может быть несколько email-адресов.

### Безопасный план

1. Создать новую таблицу `user_emails`.
2. Научить приложение при изменении email писать и в `users.email`, и в `user_emails`.
3. Скопировать существующие email в новую таблицу.
4. Проверить количество записей.
5. Переключить чтение на новую таблицу.
6. Подождать несколько релизов.
7. Удалить старое поле `users.email`.

### Проверки

```sql
SELECT COUNT(*) FROM users WHERE email IS NOT NULL;
SELECT COUNT(*) FROM user_emails WHERE is_primary = true;
```

Количество должно совпадать или различия должны быть объяснены.

### Что может пойти не так

| Проблема | Почему опасно | Что сделать |
|---|---|---|
| дубликаты email | нарушится логика входа | добавить unique-ограничения аккуратно |
| пустые email | миграция пропустит пользователей | заранее найти грязные данные |
| большая таблица | долгие блокировки | переносить батчами |
| старый код пишет только `users.email` | данные расходятся | временно писать в оба места |

## Вывод

Работа с данными — одна из главных проверок зрелости инженера.

Архитектура для эксплуатации требует, чтобы изменения данных были:

- совместимыми;
- проверяемыми;
- обратимыми там, где это возможно;
- понятными для команды;
- безопасными для пользователей.

Если вы умеете проектировать миграции так, чтобы система продолжала работать, вы уже думаете не только как разработчик, но и как инженер эксплуатации.
