# Глава 0: Почему приложение должно быть удобно эксплуатировать

> **Запомни:** "код работает" и "сервис готов к продакшену" — разные состояния.

---

## 0.1 Два одинаковых сайта в браузере

В браузере два сайта могут выглядеть одинаково. Но внутри один можно обновить за минуту, а второй при каждом релизе ломает базу и требует автора кода.

Первый сайт:

- запускается одной командой;
- имеет `.env.example`;
- пишет понятные логи;
- отдаёт `/healthz`;
- имеет backup и rollback;
- миграции БД предсказуемы.

Второй сайт:

- запускается только "как помнит разработчик";
- настройки зашиты в код;
- логи выглядят как `error happened`;
- нет healthcheck;
- миграции запускаются руками;
- rollback неизвестен.

Разница — в operability.

---

## 0.2 Что такое operability

Operability — это насколько легко сервис:

- запустить;
- настроить;
- обновить;
- остановить без потерь;
- наблюдать;
- диагностировать;
- восстановить;
- передать другому человеку.

Это архитектурное свойство. Его нельзя полностью "добавить потом" одним скриптом.

---

## 0.3 Почему DevOps-инженеру нужна архитектура

DevOps не обязан писать весь код приложения. Но он должен видеть, где архитектура создаёт эксплуатационный риск.

Примеры:

| Решение в коде | Последствие в эксплуатации |
|---|---|
| загрузки хранятся в контейнере | файлы теряются при пересоздании |
| нет timeout | запросы висят бесконечно |
| миграция удаляет колонку сразу | старый код падает при rollback |
| нет request id | сложно связать логи |
| healthcheck всегда 200 | инфраструктура думает, что всё хорошо |
