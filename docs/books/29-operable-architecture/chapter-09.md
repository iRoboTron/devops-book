# Глава 9: Логи, метрики и трассировка как архитектурное решение

> **Цель:** проектировать наблюдаемость заранее, а не добавлять её после первой аварии.

---

## 9.1 Плохой и хороший лог

Плохой лог:

```text
error happened
```

Он почти бесполезен. Непонятно, где ошибка, у кого, при каком запросе.

Хороший лог:

```json
{"level":"error","request_id":"abc123","action":"create_order","error":"payment_timeout","duration_ms":3012}
```

Теперь можно искать по `request_id`, понимать действие и видеть тип ошибки.

---

## 9.2 Structured logs

Structured logs — логи в формате, который удобно фильтровать.

Полезные поля:

| Поле | Зачем |
|---|---|
| timestamp | когда случилось |
| level | info/warn/error |
| service | какой сервис |
| request_id | связать строки одного запроса |
| user_id | если безопасно и законно |
| action | что делали |
| error | тип ошибки |
| duration_ms | сколько заняло |

Не логируй пароли, токены, cookies, приватные ключи и лишние персональные данные.

## 9.3 Метрики RED и USE

Для web-сервиса удобно RED:

| Метрика | Вопрос |
|---|---|
| Rate | сколько запросов? |
| Errors | сколько ошибок? |
| Duration | сколько длится? |

Для ресурсов удобно USE:

| Метрика | Вопрос |
|---|---|
| Utilization | насколько занят ресурс? |
| Saturation | есть ли очередь? |
| Errors | есть ли ошибки? |

---

## 9.4 Trace

Trace помогает понять путь запроса через несколько сервисов:

```text
frontend -> api -> payment -> database
```

Для маленького монолита полноценная трассировка может быть лишней. Но request_id полезен почти всегда.

---

## 9.5 Практика

Перепиши логи:

| Плохо | Лучше |
|---|---|
| error | `level=error action=login reason=db_timeout` |
| failed | `level=warn action=send_email email_id=... retry=2` |

Проверка: по хорошему логу можно ответить: что случилось, где, с каким запросом, насколько серьёзно.
