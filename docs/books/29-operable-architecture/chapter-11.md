# Глава 11. Итоговый проект: эксплуатационный разбор системы

Итоговый проект этой книги — сделать **эксплуатационный разбор системы**.

Это документ, который отвечает на вопрос:

> Насколько удобно эту систему поддерживать, обновлять, восстанавливать и развивать?

Разбор можно сделать для:

- сайта;
- Telegram-бота;
- Nextcloud;
- учебной платформы;
- CRM;
- API;
- внутреннего сервиса организации.

---

## 11.1. Что нужно выбрать

Выберите одну систему.

Лучше брать не абстрактную систему, а что-то похожее на реальность:

- сайт с базой данных;
- бот с PostgreSQL;
- Nextcloud с файлами пользователей;
- приложение на Docker Compose;
- сервис с очередью задач;
- небольшой монолит, который нужно постепенно улучшать.

---

## 11.2. Структура документа

Создайте файл `OPERABILITY-REVIEW.md`.

Заполните разделы:

1. Назначение системы.
2. Пользователи и критичные сценарии.
3. Схема компонентов.
4. Stateful/stateless части.
5. Точки отказа.
6. Деплой и rollback.
7. Данные и миграции.
8. Конфигурация и секреты.
9. Наблюдаемость.
10. Бэкапы и восстановление.
11. Масштабирование.
12. Риски.
13. План улучшений.

## 11.4. Полностью заполненный пример: Nextcloud на Docker Compose

Важно: пример ниже — учебный разбор типовой установки Nextcloud на Docker Compose. Это не универсальная инструкция для всех вариантов Nextcloud и не замена официальной документации. Если используется Nextcloud AIO, managed-хостинг или пакет хостинг-провайдера, часть решений будет другой.

### 1. Назначение

Nextcloud используется как файловое хранилище организации.

Пользователи:

- сотрудники загружают и скачивают документы;
- администратор управляет пользователями;
- руководитель ожидает, что файлы не потеряются;
- внешние участники получают ссылки на документы.

Если система недоступна:

- сотрудники не могут открыть нужные документы;
- срываются рабочие процессы;
- часть файлов начинают пересылать через мессенджеры;
- появляются риски потери данных и утечки.

### 2. Критичные сценарии

| Сценарий | Почему важен |
|---|---|
| вход пользователя | без входа нельзя работать |
| загрузка файла | основная функция сервиса |
| скачивание файла | пользователи должны получать документы |
| шаринг по ссылке | нужен для совместной работы |
| синхронизация клиента | важна для постоянной работы |
| восстановление файла | защита от ошибок пользователя |

### 3. Компоненты

```text
Пользователь
    ↓ HTTPS
Nginx / reverse proxy
    ↓
Nextcloud app container
    ↓
PostgreSQL / MariaDB
    ↓
Файловое хранилище

Дополнительно:
- Redis для блокировок и кэша
- cron container для фоновых задач
- backup job
- monitoring
```

### 4. Stateful/stateless

| Компонент | Тип | Почему |
|---|---|---|
| reverse proxy | stateless | хранит в основном конфигурацию |
| Nextcloud app | частично stateless | код можно пересоздать, но config важен |
| database | stateful | хранит пользователей, метаданные, настройки |
| file storage | stateful | хранит файлы пользователей |
| Redis | обычно временное состояние | потеря неприятна, но не как потеря БД/файлов |
| cron | stateless | выполняет фоновые задачи |

Главный вывод:

> В Nextcloud критичны не только файлы, но и база данных. Бэкап одних файлов без базы может оказаться бесполезным.

### 5. Точки отказа

| Точка отказа | Что будет | Как снизить риск |
|---|---|---|
| база данных | Nextcloud не работает или теряет метаданные | бэкапы, мониторинг, проверка восстановления |
| файловое хранилище | пользователи теряют доступ к файлам | RAID/репликация/снапшоты/бэкапы |
| reverse proxy | сервис не открывается | проверка конфигурации, monitoring, быстрый rollback |
| диск сервера | загрузка и синхронизация ломаются | алерт на 80/85/90%, план расширения |
| cron не работает | фоновые задачи копятся | отдельная проверка cron jobs |
| Redis недоступен | проблемы с блокировками/производительностью | мониторинг и корректная настройка |
| TLS-сертификат истёк | браузеры ругаются, доступ нарушен | автопродление и алерт заранее |

### 6. Деплой и rollback

Для Docker Compose деплой может выглядеть так:

1. сделать бэкап БД и важных конфигов;
2. прочитать release notes Nextcloud и приложений;
3. проверить совместимость PHP/БД/Redis;
4. обновить staging или копию;
5. выполнить обновление;
6. проверить вход, загрузку, скачивание, синхронизацию;
7. только потом обновлять production.

Rollback Nextcloud не всегда простой, потому что обновление может менять схему базы.

Поэтому перед обновлением обязательно:

- snapshot сервера или volume;
- dump базы;
- копия config;
- понимание, как вернуться назад;
- окно работ.

### 7. Данные и миграции

Критичные данные:

- файлы пользователей;
- база данных Nextcloud;
- `config.php`;
- пользовательские приложения и их настройки;
- ключи шифрования, если включено шифрование;
- конфигурация reverse proxy.

Особенно важно:

> Бэкап файлов и бэкап базы должны быть согласованы по времени. Иначе база может ссылаться на файлы в одном состоянии, а файловое хранилище будет в другом.

### 8. Конфигурация и секреты

Что нельзя хранить случайно и без контроля:

- пароль базы данных;
- admin password;
- secret в `config.php`;
- ключи шифрования;
- SMTP credentials;
- токены внешних интеграций.

Минимальные меры:

- `.env` не хранить в публичном репозитории;
- доступ к серверу только по SSH-ключам;
- резервная копия секретов хранится в парольном менеджере;
- при увольнении человека доступы отзываются;
- список администраторов регулярно проверяется.

### 9. Наблюдаемость

Нужно видеть не только «контейнер запущен», но и «сервис реально работает».

Проверки:

```bash
curl -I https://cloud.example.com/status.php
```

```bash
docker compose ps
```

```bash
docker compose logs --tail 100 app
```

Что мониторить:

- HTTP status;
- время ответа;
- место на диске;
- ошибки Nextcloud;
- состояние базы;
- выполнение cron;
- возраст последнего бэкапа;
- срок действия TLS-сертификата.

### 10. Бэкапы и восстановление

Минимальный набор:

| Что | Как часто | Как проверять |
|---|---|---|
| база данных | ежедневно или чаще | восстановить на тесте |
| файлы пользователей | ежедневно/снапшоты | выборочное восстановление файла |
| config.php | после изменений | сравнить наличие и права |
| compose/env | после изменений | поднять на тестовом сервере |
| секреты | при изменении | проверить доступ у ответственного |

Восстановление нужно тренировать.

Плохой вариант:

> «Бэкапы есть, но мы никогда не пробовали их восстановить».

Хороший вариант:

> «Раз в месяц восстанавливаем тестовый Nextcloud из бэкапа и проверяем вход, файл и шаринг».

### 11. Масштабирование

Что можно масштабировать относительно проще:

- reverse proxy;
- отдельные фоновые задачи;
- ресурсы сервера;
- вынести Redis отдельно;
- улучшить диск.

Что сложнее:

- горизонтально масштабировать сам Nextcloud app без правильной общей файловой системы;
- масштабировать базу без опыта;
- переносить файлы на S3/объектное хранилище;
- делать отказоустойчивость без тестов восстановления.

Практичный подход для небольшой организации:

1. сначала мониторинг, бэкапы и документация;
2. потом отдельный Redis и аккуратный cron;
3. потом улучшение дисков/хранилища;
4. только после этого сложная HA-архитектура.

### 12. Риски

| Риск | Вероятность | Влияние | Действие |
|---|---|---|---|
| нет проверенного восстановления | средняя | критическое | ежемесячный restore-test |
| диск закончится | высокая | высокое | алерты 80/85/90%, план расширения |
| обновление сломает приложения | средняя | высокое | staging и чтение release notes |
| секреты лежат в файлах без контроля | средняя | высокое | парольный менеджер и правила доступа |
| один админ знает всё | высокая | высокое | документация и второй ответственный |
| cron не работает | средняя | среднее | мониторинг фоновых задач |
| нет плана incident response | высокая | среднее | runbook и контакты |

### 13. План улучшений

**Срочно:**

- описать текущую схему;
- проверить наличие бэкапов базы, файлов и config;
- сделать тестовое восстановление;
- добавить алерты на диск и доступность;
- сохранить секреты в парольный менеджер.

**Важно:**

- сделать staging для обновлений;
- описать runbook «Nextcloud не открывается»;
- настроить проверку cron;
- документировать процедуру обновления;
- проверить права администраторов.

**Позже:**

- рассмотреть отдельный сервер БД или managed DB, если это совместимо с выбранной установкой, бюджетом и требованиями;
- рассмотреть объектное хранилище для файлов, если текущий диск становится узким местом;
- продумать HA-архитектуру, если простой сервиса недопустим;
- автоматизировать регулярный restore-test.

## 11.5. Как отличить хороший разбор от слабого

Слабый разбор:

> «Нужно сделать бэкапы, мониторинг, безопасность и масштабирование».

Проблема: это общие слова.

Хороший разбор:

> «Сейчас нет проверки восстановления. Если база повредится, мы не знаем, поднимется ли Nextcloud из бэкапа. До 20 мая нужно восстановить копию на тестовом сервере и проверить вход, загрузку файла и шаринг».

Хороший разбор всегда конкретный:

- что именно сломается;
- кого это затронет;
- как заметим;
- как восстановим;
- что сделать первым;
- кто отвечает.

## 11.6. Практика

### Задание 1

Сделайте эксплуатационный разбор своего сервиса по шаблону.

Минимум:

- схема;
- stateful/stateless;
- 5 точек отказа;
- 5 рисков;
- план улучшений.

### Задание 2

Для выбранной системы ответьте:

1. Что будет, если закончится диск?
2. Что будет, если база не запустится?
3. Что будет, если последний деплой сломает сервис?
4. Что будет, если уйдёт единственный администратор?
5. Что будет, если бэкап окажется битым?

### Задание 3

Напишите runbook для самой страшной точки отказа вашей системы.

1. Какие компоненты вашей системы stateful?
2. Какие данные нужно бэкапить вместе?
3. Можно ли быстро откатить обновление?
4. Какие метрики покажут проблему до жалобы пользователей?

6. Какие секреты есть в системе?
7. Кто знает, как восстановить сервис?
8. Что нужно улучшить первым?

## Вывод

Эксплуатационный разбор — это способ увидеть систему глазами человека, который будет отвечать за неё ночью, во время аварии или после неудачного обновления.

Хорошая архитектура — это не самая модная архитектура. Хорошая архитектура:

- понятна;
- наблюдаема;
- восстанавливаема;
- безопасна для изменений;
- документирована;
- учитывает реальные риски.

Если система красивая на схеме, но её нельзя восстановить из бэкапа, она не готова к реальной эксплуатации.
