# Глоссарий

> Термины и выражения книги «Эксплуатируемая архитектура». В скобках — главы, где термин вводится или активно используется.

---

**Operability (эксплуатируемость)** — архитектурное свойство сервиса: насколько легко его запустить, настроить, обновить, наблюдать, диагностировать, остановить без потерь и восстановить. Нельзя полностью «добавить потом» одним скриптом. _(глава 0)_

**Operability review (эксплуатационный разбор)** — документ, который оценивает, насколько удобно систему поддерживать, обновлять, восстанавливать и развивать: схема, состояние, точки отказа, риски, план улучшений. _(главы 0, 11)_

**Монолит** — приложение, которое деплоится как одна единица. Для маленькой команды часто лучший старт; риск — отсутствие внутренних границ. _(глава 1)_

**Модульный монолит** — один деплой с понятными внутренними модулями, которые не лезут в чужие внутренности. Порядок без сложности микросервисов. _(глава 1)_

**Микросервисы** — несколько сервисов, которые можно независимо разрабатывать, деплоить и масштабировать. Цена — сеть, распределённые ошибки, мониторинг, версии API. _(глава 1)_

**Распределённый монолит** — антипаттерн: сервисов много, но они жёстко завязаны друг на друга и общую базу. Худшее из двух миров. _(глава 1)_

**Stateless** — компонент, который не хранит важное состояние внутри себя; его можно остановить, пересоздать и заменить новой версией без потери данных. _(главы 2, 10)_

**Stateful** — компонент, хранящий данные, которые нельзя просто потерять (БД, uploads, очередь, сессии); требует backup и проверки восстановления. _(глава 2)_

**Конфигурация (config)** — настройки сервиса (адрес БД, порт, уровень логов), которые должны меняться без изменения кода ради переносимости между окружениями. _(глава 3)_

**Переменные окружения (env vars)** — способ передать сервису настройки извне, не зашивая их в код; основа переносимости одного образа между dev/stage/prod. _(глава 3)_

**Секреты (secrets)** — чувствительные данные (пароли БД, API-токены, ключи, session secret), которые нельзя коммитить в Git, печатать в логи и которые нужно ротировать. _(глава 3)_

**Secret manager** — отдельное хранилище секретов с контролем доступа и ротацией вместо хранения паролей в коде или открытых файлах. _(глава 3)_

**Окружения (dev/stage/prod)** — раздельные среды: dev с тестовыми ключами, stage почти как prod без реальных пользователей, prod с реальными данными. _(глава 3)_

**Healthcheck (проверка здоровья)** — простой способ спросить у сервиса «ты жив?»; должен быть лёгким, быстрым и не зависеть от тяжёлых внешних вызовов. _(главы 0, 4)_

**Liveness (проба живости)** — проверка, что процесс не завис навсегда; при провале оркестратор перезапускает контейнер. _(глава 4)_

**Readiness (готовность)** — проверка, что сервис готов принимать трафик (БД, миграции готовы); при провале экземпляр временно снимают с балансировки без перезапуска. _(главы 4, 5)_

**`/healthz`** — endpoint, отвечающий «процесс жив»; используется человеком, Docker и мониторингом. _(глава 4)_

**`/readyz`** — endpoint, отвечающий «сервис готов принимать трафик»; используется балансировщиком и оркестратором. _(глава 4)_

**Graceful shutdown (аккуратная остановка)** — по сигналу SIGTERM приложение перестаёт принимать новые запросы, доводит текущие до конца, закрывает соединения и завершается до timeout. _(глава 5)_

**SIGTERM** — сигнал «вежливо завершись», который Docker, systemd или Kubernetes посылают процессу перед остановкой. _(глава 5)_

**Миграция (migration)** — изменение схемы или данных в базе; опаснее обычного кода, потому что простой rollback приложения после неё может не помочь. _(глава 6)_

**Expand/contract** — паттерн безопасной миграции: сначала расширить схему (expand), перенести данные, переключить чтение, и только потом удалить старое (contract). _(главы 6, приложение A, B)_

**Backward compatibility (обратная совместимость)** — способность новой системы работать со старым форматом и старыми клиентами (например, временно отдавать и `name`, и `first_name`). _(глава 6)_

**Forward compatibility (прямая совместимость)** — способность старой части системы не ломаться при появлении новых, неизвестных ей полей данных. _(глава 6)_

**Версионирование API** — поддержка нескольких версий API (`/api/v1`, `/api/v2`), когда изменение нельзя сделать совместимым; цена — больше поддержки и тестов. _(глава 6)_

**Rollback (откат)** — возврат к предыдущей версии; быстро и понятно для кода, но может не сработать после миграции данных. _(главы 6, 10)_

**Бэкап (backup)** — резервная копия данных; важен не сам файл, а проверенная восстановимость на тестовом окружении перед серьёзной миграцией. _(главы 6, 11)_

**Restore drill (тренировка восстановления)** — регулярная проверка, что из бэкапа действительно поднимается рабочая система, а не просто «бэкапы где-то есть». _(главы 2, 11)_

**Timeout** — ограничение времени ожидания внешнего вызова; без него запрос может зависнуть навсегда и забить ресурсы. _(главы 7, приложение A)_

**Retry (повтор)** — повторная попытка операции при временной ошибке; опасен без backoff, лимита попыток и идемпотентности. _(главы 7, 8)_

**Exponential backoff (экспоненциальная задержка)** — увеличение паузы между повторами (1с → 2с → 4с → 8с), чтобы дать падающей системе восстановиться. _(главы 7, 8)_

**Jitter** — случайная добавка к паузе повтора, чтобы клиенты не повторяли запросы одновременно и не создавали всплеск нагрузки. _(глава 7)_

**Circuit breaker (предохранитель)** — паттерн, который размыкает вызовы к падающей зависимости, защищая и вызывающего, и саму зависимость; имеет состояния closed, open, half-open. _(главы 7, приложение B)_

**Fallback (запасной вариант)** — упрощённый или заранее заготовленный ответ, который отдаётся, когда зависимость недоступна, вместо ожидания или падения. _(глава 7)_

**Bulkhead (переборка)** — изоляция части ресурсов, чтобы сбой одной зависимости не утянул за собой всю систему. _(главы 7, приложение B)_

**Graceful degradation (мягкая деградация)** — способность сервиса продолжать работать в урезанном режиме при отказе части зависимостей вместо полного падения. _(главы 7, 8)_

**Idempotency (идемпотентность)** — свойство операции: повторное выполнение не создаёт неправильный результат (статус `paid` остаётся `paid`, а не списывает деньги дважды). _(глава 8)_

**Очередь задач (queue)** — место, куда приложение кладёт задания для выполнения позже воркером; основа асинхронной архитектуры. _(глава 8)_

**Worker** — процесс, который забирает задачи из очереди и выполняет их вне пользовательского запроса. _(глава 8)_

**Dead letter queue (DLQ)** — очередь для задач, которые не удалось выполнить после нескольких попыток; нужна, чтобы не терять их и не повторять бесконечно. _(глава 8)_

**Outbox pattern** — запись бизнес-данных и события в одной транзакции БД, после чего отдельный воркер надёжно перекладывает событие в очередь; защищает от потери событий. _(глава 8)_

**Observability (наблюдаемость)** — проектируемое заранее свойство видеть, что происходит внутри системы, через логи, метрики и трассировку. _(глава 9)_

**Structured logs (структурированные логи)** — логи в машиночитаемом формате (например JSON) с полями, по которым удобно фильтровать и искать. _(главы 9, приложение A)_

**Request ID** — идентификатор запроса, связывающий все строки логов одного запроса; помогает собрать цепочку даже в монолите. _(главы 0, 9)_

**Trace (трассировка)** — сквозное отслеживание пути запроса через несколько сервисов по общему trace/request id. _(глава 9)_

**RED-метрики** — Rate, Errors, Duration: сколько запросов, сколько ошибок, сколько длятся — базовый набор для web-сервиса. _(глава 9)_

**Алерт (alert)** — автоматическое уведомление при выходе метрики за порог (например самая старая задача в очереди ждёт больше 10 минут). _(главы 8, 11)_

**Rolling deploy** — обновление экземпляров по очереди; безопасно для stateless-приложений при совместимости версий и наличии readiness. _(глава 10)_

**Blue-green deploy** — одновременная работа текущей (blue) и новой (green) версий с переключением трафика на балансировщике; даёт быстрый rollback. _(глава 10)_

**Canary deploy** — выпуск новой версии сначала для малой доли трафика (5%) с последующим расширением при отсутствии ошибок. _(глава 10)_

**Feature flag (флаг функции)** — переключатель, позволяющий включать и выключать функциональность без нового деплоя; флаги нужно вовремя чистить. _(глава 10)_

**Точка отказа / SPOF (single point of failure)** — компонент, отказ которого выводит из строя весь сервис (часто БД или файловое хранилище); требует бэкапов, мониторинга, репликации. _(главы 0, 11)_

**Runbook** — пошаговая инструкция действий при конкретной аварии (например «сервис не открывается»), подготовленная заранее. _(глава 11)_

**Масштабирование (scaling)** — увеличение пропускной способности; stateless-части масштабируются горизонтально легко, stateful (БД, файлы) — сложнее. _(главы 2, 11)_

**12-Factor App** — набор принципов проектирования приложений, удобных для запуска в разных окружениях (config, logs, disposability и др.). _(приложение B)_
