# Глава 8: Очереди и фоновые задачи

> **Цель:** понять, когда очередь помогает, а когда добавляет лишнюю сложность.

---

## 8.1 Зачем нужна очередь

Не все задачи нужно выполнять прямо во время HTTP-запроса.

Примеры для фона:

- отправить email;
- обработать изображение;
- сгенерировать отчёт;
- отправить уведомление Telegram;
- импортировать большой CSV.

Пользователь не должен ждать 30 секунд, пока сервер генерирует отчёт.

---

## 8.2 Как выглядит схема

```text
web app -> кладёт задачу в очередь -> worker забирает -> выполняет -> пишет результат
```

Очередь даёт буфер, но не делает систему магически бесконечной.

---

## 8.3 Варианты реализации

| Вариант | Когда подходит | Плюсы | Минусы |
|---|---|---|---|
| systemd timer | периодические задачи | просто | не очередь |
| PostgreSQL как очередь | малый проект | нет новой инфраструктуры | ограниченная гибкость |
| Redis + RQ | Python-проекты | просто | Redis становится важнее |
| Celery + Redis/RabbitMQ | сложные задачи | мощно | сложнее эксплуатация |

---

## 8.3а Сравнение с точки зрения эксплуатации

| Инструмент | Сложность эксплуатации | Когда подходит | Что потерять при падении |
|---|---|---|---|
| **RQ + Redis** | Средняя. Нужно держать Redis живым, мониторить воркеры, настроить rq-dashboard или аналог. | Python-проект, задачи можно потерять или повторить, команда знает Redis. | Все задачи в памяти Redis. При падении без AOF/RDB — потеря очереди. |
| **Celery + Redis** | Высокая. Celery сам по себе сложный фреймворк: beat, flower, несколько воркеров, версионирование задач. Типичный источник "магических" ошибок. | Нужны приоритеты, расписания, retry с backoff, роутинг задач между воркерами. | То же что RQ + Redis, плюс риск потери задач при неправильной конфигурации acks. |
| **PostgreSQL SKIP LOCKED** | Низкая. Таблица задач — обычная таблица. Backup уже есть, мониторинг уже есть, откат — обычный SQL. | Нагрузка умеренная (до тысяч задач в минуту), важна надёжность, нет отдельной команды по Redis. | Ничего — данные в PostgreSQL, они переживут перезапуск и входят в обычный backup. |
| **systemd timer** | Минимальная. Это просто cron. Управляется через `systemctl`, логи в journald. | Периодические задачи по расписанию (не очередь): очистка, отчёты, синхронизация. | Задача не запустилась, если сервер был выключен в момент срабатывания. |

> **Совет:** для маленького проекта начни с **PostgreSQL SKIP LOCKED** или **systemd timer** — не нужна дополнительная инфраструктура. Redis добавляет ещё один stateful-компонент, который нужно бэкапить, мониторить и чинить в 3 часа ночи. Переходи к Redis/Celery только когда PostgreSQL реально становится узким местом.

## 8.4 Idempotency

Идемпотентная задача может выполниться повторно без вреда.

Плохо:

```text
worker отправил деньги
упал до записи статуса
задача повторилась
деньги отправились второй раз
```

Хорошо:

```text
операция имеет idempotency key
повторная попытка понимает, что действие уже выполнено
```

---

## 8.5 Что мониторить

- длину очереди;
- возраст самой старой задачи;
- ошибки worker;
- количество retry;
- dead-letter queue;
- время обработки.

---

## 8.6 Практика

Выбери долгую операцию:

| Операция | Синхронно или очередь? | Почему | Риск |
|---|---|---|---|
| отправка email | очередь | пользователь не ждёт | потерять задачу |
| маленькая проверка формы | синхронно | быстро | нет |

Проверка: если задача может выполняться долго или повторяться, подумай об очереди и идемпотентности.
