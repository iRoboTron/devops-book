# Глава 8. Очереди, фоновые задачи и асинхронность

Не всё в системе нужно делать прямо во время запроса пользователя.

Пользователь нажал кнопку — и система может:

- сразу ответить «заявка принята»;
- а письмо отправить чуть позже;
- отчёт сформировать в фоне;
- видео обработать отдельной задачей;
- уведомления отправить через очередь.

Это и есть асинхронная архитектура.

Главная идея:

> Быстрый пользовательский запрос не должен ждать долгую или ненадёжную операцию, если без этого можно обойтись.

---

## 8.1. Синхронный подход

Синхронный подход:

1. пользователь отправляет форму;
2. приложение сохраняет заявку;
3. приложение отправляет письмо;
4. приложение отправляет сообщение в Telegram;
5. приложение ждёт ответы внешних сервисов;
6. только потом пользователь получает ответ.

Проблема:

- почтовый сервис тормозит — пользователь ждёт;
- Telegram API недоступен — весь запрос падает;
- внешний сервис ответил ошибкой — заявка может не сохраниться;
- время ответа становится большим.

---

## 8.2. Асинхронный подход

Асинхронный подход:

1. пользователь отправляет форму;
2. приложение сохраняет заявку;
3. приложение кладёт задачу в очередь;
4. пользователь сразу получает ответ;
5. worker позже отправляет письмо и Telegram-уведомление.

Схема:

```text
Пользователь → Web/API → База данных
                     ↓
                  Очередь
                     ↓
                  Worker
                     ↓
             Email / Telegram / отчёты
```

Плюсы:

- пользователь быстрее получает ответ;
- внешние сбои меньше влияют на основной запрос;
- задачи можно повторять;
- нагрузку можно распределять;
- длинные операции не блокируют web-сервер.

Минусы:

- архитектура сложнее;
- появляется очередь;
- появляются worker'ы;
- нужно следить за задержкой задач;
- возможны дубликаты выполнения.

---

## 8.3. Что можно выносить в фон

Хорошие кандидаты:

- отправка email;
- отправка Telegram-уведомлений;
- генерация PDF;
- обработка изображений;
- импорт больших файлов;
- пересчёт статистики;
- синхронизация с внешним API;
- отправка webhook'ов;
- очистка старых данных;
- резервное копирование.

Плохие кандидаты:

- проверка пароля при входе;
- списание денег, если пользователь должен сразу видеть результат;
- операции, где без результата нельзя продолжить;
- критичная проверка прав доступа.

Правило:

> В фон можно выносить то, что не мешает сразу дать пользователю честный ответ.

---

## 8.4. Очередь задач

Очередь — это место, куда приложение кладёт задания для выполнения позже.

Пример задания:

```json
{
  "type": "send_email",
  "user_id": 123,
  "template": "welcome"
}
```

Worker забирает задачу и выполняет её.

Популярные варианты:

- Redis Queue;
- RabbitMQ;
- Kafka;
- Celery;
- Sidekiq;
- BullMQ;
- встроенные очереди фреймворков.

---

## 8.5. Как выбрать очередь

Не существует «лучшей очереди для всего». Есть подходящий инструмент под задачу.

### Redis-based queue

Подходит для:

- простых фоновых задач;
- небольших и средних проектов;
- отправки уведомлений;
- задач, где допустима простая инфраструктура.

Плюсы:

- проще внедрить;
- быстро работает;
- много готовых библиотек.

Минусы:

- нужно аккуратно настроить persistence;
- не лучший выбор для сложной событийной архитектуры;
- при плохой настройке можно потерять задачи.

### RabbitMQ

Подходит для:

- надёжной доставки сообщений;
- маршрутизации;
- нескольких типов consumer'ов;
- систем, где важны acknowledgements и retries.

Плюсы:

- зрелый брокер;
- гибкая маршрутизация;
- понятная модель очередей.

Минусы:

- сложнее Redis;
- нужно понимать exchange, queue, routing key;
- требует администрирования.

### Kafka

Подходит для:

- больших потоков событий;
- аналитики;
- event streaming;
- систем, где события нужно хранить и перечитывать.

Плюсы:

- высокая пропускная способность;
- хранение истории событий;
- удобно для потоковой обработки.

Минусы:

- сложная эксплуатация;
- избыточна для простого «отправить email»;
- требует дисциплины в схемах событий.

### Простое правило выбора

| Ситуация | Что выбрать |
|---|---|
| маленький проект, уведомления, отчёты | Redis queue / встроенная очередь |
| важна надёжная маршрутизация сообщений | RabbitMQ |
| огромный поток событий и аналитика | Kafka |
| проект учебный или простой | начать с самого простого варианта |

Главная ошибка новичка — ставить Kafka там, где хватило бы обычной очереди задач.

## 8.6. Повторы задач

Внешние сервисы иногда падают. Поэтому worker должен уметь повторять задачу.

Пример:

- первая попытка отправки письма — ошибка;
- через 1 минуту повтор;
- через 5 минут повтор;
- через 30 минут повтор;
- потом задача уходит в dead letter queue.

Такой подход называется retry with backoff.

Плохой вариант:

> Повторять задачу каждую секунду бесконечно.

Почему плохо:

- можно перегрузить внешний сервис;
- можно забить очередь;
- можно получить бан;
- сложно понять, что происходит.

Лучше:

```text
1-я попытка: сразу
2-я попытка: через 1 минуту
3-я попытка: через 5 минут
4-я попытка: через 30 минут
5-я попытка: отправить в DLQ
```

---

## 8.7. Dead letter queue

Dead letter queue, или DLQ, — это очередь для задач, которые не удалось выполнить после нескольких попыток.

Она нужна, чтобы:

- не терять проблемные задачи;
- не повторять их бесконечно;
- разбирать ошибки вручную;
- видеть системные проблемы.

Пример:

```json
{
  "task": "send_email",
  "user_id": 123,
  "error": "invalid email address",
  "attempts": 5
}
```

Если email неправильный, повторять задачу бессмысленно. Её нужно отправить в DLQ и показать администратору.

---

## 8.8. Idempotency

Idempotency означает:

> Повторное выполнение операции не создаёт неправильный результат.

Пример идемпотентной операции:

```text
Установить статус заказа = paid
```

Если выполнить два раза, статус всё равно `paid`.

Пример неидемпотентной операции:

```text
Списать 100 рублей с карты
```

Если выполнить два раза, деньги спишутся дважды.

Для фоновых задач идемпотентность критически важна, потому что задачи могут повторяться.

---

## 8.9. Практический пример: заявка и уведомление

Пользователь оставляет заявку на сайте.

Что нужно:

1. сохранить заявку;
2. отправить email администратору;
3. отправить Telegram-уведомление;
4. обновить статистику.

Плохой вариант:

```text
HTTP request
  → save request
  → send email
  → send Telegram
  → update stats
  → response to user
```

Если Telegram тормозит, пользователь ждёт.

Хороший вариант:

```text
HTTP request
  → save request
  → enqueue notifications
  → response to user

worker
  → send email
  → send Telegram
  → update stats
```

Пользователь сразу получает честный ответ:

> «Заявка принята. Мы свяжемся с вами».

А уведомления уходят в фоне.

## 8.10. Outbox pattern

Есть тонкая проблема.

Что если приложение:

1. сохранило заявку в базу;
2. попыталось положить задачу в очередь;
3. упало между этими действиями?

Заявка есть, а уведомления нет.

Outbox pattern решает это так:

1. заявка сохраняется в базу;
2. в той же транзакции создаётся запись в таблице `outbox`;
3. отдельный worker читает `outbox` и отправляет события в очередь;
4. после успешной отправки помечает событие как отправленное.

Схема:

```text
Web/API → Database transaction
          ├─ insert application
          └─ insert outbox event

Outbox worker → Queue → Notification worker
```

Плюс: заявка и событие создаются атомарно.

Минус: архитектура сложнее.

Когда это нужно:

- деньги;
- заказы;
- юридически важные заявки;
- критичные уведомления;
- интеграции, где нельзя терять события.

Когда можно проще:

- учебный проект;
- некритичная статистика;
- уведомление, которое можно восстановить вручную.

## 8.11. Очереди и эксплуатация

Очередь нужно не только поставить, но и наблюдать.

Важные метрики:

| Метрика | Что означает |
|---|---|
| queue length | сколько задач ждёт |
| oldest job age | сколько ждёт самая старая задача |
| processing rate | сколько задач обрабатывается в минуту |
| error rate | сколько задач падает |
| retry count | сколько повторов |
| DLQ size | сколько задач ушло в ручной разбор |

Плохая ситуация:

> Очередь растёт, но никто этого не видит.

Хорошая ситуация:

> Если самая старая задача ждёт больше 10 минут, приходит алерт.

---

## 8.12. Практическое дерево решений

Перед добавлением очереди ответьте на вопросы.

### Вопрос 1. Пользователю нужен результат прямо сейчас?

- Да → оставляем синхронно или делаем короткую синхронную проверку.
- Нет → можно вынести в фон.

### Вопрос 2. Можно ли выполнить задачу повторно?

- Да → делаем retry.
- Нет → добавляем idempotency key или ручное подтверждение.

### Вопрос 3. Потеря задачи критична?

- Да → нужен outbox, durable queue, мониторинг DLQ.
- Нет → можно начать проще.

### Вопрос 4. Задачи могут копиться быстрее, чем обрабатываются?

- Да → нужны метрики очереди, масштабирование worker'ов, backpressure.
- Нет → достаточно базового мониторинга.

## 8.13. Частые ошибки

### Ошибка 1. Вынести в фон и забыть

Если задача ушла в очередь, это не значит, что она выполнена.

Нужно видеть:

- сколько задач в очереди;
- сколько упало;
- сколько ждёт слишком долго.

### Ошибка 2. Не делать идемпотентность

Если worker повторит задачу, не должно случиться катастрофы.

Для платежей, заказов и заявок нужен уникальный ключ операции.

### Ошибка 3. Бесконечные повторы

Бесконечный retry может создать вторую аварию.

Нужны:

- лимит попыток;
- backoff;
- DLQ;
- алерт.

### Ошибка 4. Ставить слишком сложный брокер

Если проект маленький, сложная инфраструктура может навредить больше, чем помочь.

Сначала решайте задачу, а не демонстрируйте технологию.

## Вывод

Очереди и фоновые задачи делают систему устойчивее, если использовать их осознанно.

Они помогают:

- ускорить ответы пользователю;
- переживать сбои внешних сервисов;
- повторять неудачные операции;
- обрабатывать нагрузку постепенно.

Но они добавляют сложность. Поэтому сильный инженер не просто говорит «поставим очередь», а отвечает:

- что именно уйдёт в фон;
- что будет при ошибке;
- можно ли повторить задачу;
- как заметить застревание;
- что делать с DLQ.

Тогда асинхронность становится не модной технологией, а инструментом надёжной архитектуры.
