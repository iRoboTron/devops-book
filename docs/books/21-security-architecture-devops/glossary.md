# Глоссарий

> Термины и выражения книги «Архитектура безопасности: от домашней лаборатории до крупной организации». В скобках — главы, где термин вводится или активно используется.

---

**Defense in depth (эшелонированная защита)** — стратегия из нескольких независимых слоёв контроля, чтобы пробой одного не означал полную компрометацию. На каждом масштабе слои те же, меняются лишь инструменты. _(главы 4, 7)_

**Zero trust (нулевое доверие)** — модель, в которой доверие не выдаётся по факту нахождения внутри сети, а проверяется на каждом запросе по identity, состоянию устройства и политике. _(глава 4)_

**Threat model (модель угроз)** — структурированный ответ на вопросы: какие есть активы, какие у них границы доверия и какие классы атак наиболее вероятны. Основа приоритизации защиты. _(главы 0, 9)_

**Asset (актив)** — то, что защищаем: данные, сервис, доступ, идентификационные данные. Архитектурное мышление начинается с перечня активов. _(главы 0, 3, 9)_

**Trust zone (зона доверия)** — логически или физически выделенная область с одинаковым уровнем доверия: public, internal, management, backup, guest. _(главы 0, 1, 3)_

**Trust boundary (граница доверия)** — место, где меняется уровень доверия и должен стоять контроль: между интернетом и DMZ, между app и management. _(главы 0, 4, 8)_

**Control objective (цель контроля)** — то, что должно быть верно по итогу: «БД недоступна из интернета», «admin-доступ только через VPN». Формулируется до выбора инструмента. _(глава 0)_

**Control (контроль)** — конкретный механизм, реализующий цель контроля: firewall-правило, TLS, MFA, сегментация. _(главы 0, 4, 9)_

**Attack surface (поверхность атаки)** — совокупность точек, через которые система может быть атакована: открытые порты, auth endpoints, публичные панели, интеграции. Защитник стремится её минимизировать. _(главы 2, 3, 9)_

**Blast radius (радиус поражения)** — масштаб ущерба при компрометации одного узла. Сегментация и зоны доверия уменьшают blast radius. _(главы 1, 3, 6)_

**Lateral movement (горизонтальное перемещение)** — продвижение атакующего от скомпрометированного узла к другим внутри сети. Плоская сеть упрощает его, сегментация — ограничивает. _(глава 3)_

**Segmentation (сегментация)** — разделение сети и систем на изолированные зоны с контролем потоков между ними. _(главы 1, 3, 6)_

**Flat network (плоская сеть)** — сеть без сегментации, где все устройства в одной зоне доверия; компрометация одного узла открывает путь ко всем. _(главы 1, 3)_

**Least privilege (минимальные привилегии)** — выдача доступа только в объёме, необходимом для задачи, и не больше. Ключевой принцип zero trust и IAM. _(глава 4)_

**IAM (Identity and Access Management)** — управление идентификацией и доступом: кто есть кто и к чему имеет право. В enterprise — централизованный сервис. _(главы 4, 7)_

**SSO (Single Sign-On)** — единый вход: одна аутентификация даёт доступ к нескольким сервисам через централизованный identity-провайдер. _(главы 4, 7)_

**MFA (многофакторная аутентификация)** — подтверждение личности несколькими независимыми факторами (пароль + токен/устройство). _(главы 4, 7)_

**PAM (Privileged Access Management)** — управление привилегированным доступом: контроль, аудит и ограничение действий администраторов. _(глава 7)_

**IAM federation (федерация идентификации)** — связывание identity-систем нескольких доменов или организаций для единого управления доступом. _(глава 4)_

**RBAC (Role-Based Access Control)** — управление доступом по ролям: права назначаются роли, а пользователь получает роль. _(глава 4)_

**ABAC (Attribute-Based Access Control)** — управление доступом по атрибутам субъекта, ресурса и контекста (отдел, время, состояние устройства). _(глава 4)_

**Management path / management zone (путь и зона управления)** — отдельный канал и зона для административного доступа, изолированные от пользовательского трафика. _(главы 1, 2, 3)_

**Bastion (бастион)** — выделенный укреплённый хост — единственная точка входа для администрирования внутренних систем. _(глава 7)_

**Gateway (шлюз)** — единая точка входа в инфраструктуру, на которой сходятся firewall, маршрутизация и разделение зон. _(глава 3)_

**DMZ (демилитаризованная зона)** — буферная зона для публичных сервисов, изолированная и от интернета, и от внутренней сети. _(главы 3, 4)_

**Reverse proxy (обратный прокси)** — сервис перед приложением, который терминирует TLS, фильтрует и направляет входящий трафик (например nginx). _(глава 2)_

**TLS discipline (дисциплина TLS)** — практика, при которой TLS терминируется в одной осознанной точке (reverse proxy), а не хаотично в каждом приложении. _(глава 2)_

**WAF (Web Application Firewall)** — фильтр прикладного уровня перед веб-приложением, блокирующий типовые веб-атаки. _(главы 4, 6)_

**EDR (Endpoint Detection and Response)** — класс решений для обнаружения и реагирования на угрозы на конечных узлах. _(глава 4)_

**SIEM (Security Information and Event Management)** — централизованный сбор, корреляция и анализ событий безопасности. _(главы 4, 6, 7)_

**SOC (Security Operations Center)** — команда и процесс мониторинга, обнаружения и реагирования на инциденты. _(глава 4)_

**IDS/IPS (системы обнаружения/предотвращения вторжений)** — мониторинг трафика на признаки атак (IDS) с возможностью их блокировки (IPS). _(глава 6)_

**Central logging (централизованный сбор логов)** — отправка логов с хостов в общий контур, чтобы расследование не останавливалось на локальном journald. _(главы 3, 4, 7)_

**Inventory / CMDB (инвентарь активов)** — учёт хостов, сервисов, доменов и их владельцев; без него архитектура неуправляема. _(главы 3, 4, 7)_

**Owner (владелец)** — ответственный за актив, контроль или процесс: кто обновляет, мониторит и расследует. Без owner компонент становится бесхозным риском. _(главы 3, 4, 5, 7)_

**Shared responsibility (разделение ответственности)** — письменное распределение зон ответственности между платформой, продуктовой командой и security. _(глава 4)_

**Shared services / platform (общие платформенные сервисы)** — централизованные сервисы (IAM, logging, backup), используемые многими командами. _(глава 4)_

**Patch cadence (ритм обновлений)** — регулярный предсказуемый цикл установки патчей; хаотичное ручное обновление выводит хост из цикла. _(глава 7)_

**Vulnerability management (управление уязвимостями)** — процесс выявления, приоритизации и устранения известных уязвимостей (CVE). _(главы 4, 7)_

**CVE (Common Vulnerabilities and Exposures)** — публичный идентификатор известной уязвимости. _(глава 6)_

**Change management (управление изменениями)** — формализованный процесс внесения и согласования изменений в инфраструктуре. _(глава 4)_

**Lifecycle (жизненный цикл актива)** — стадии от ввода в эксплуатацию до вывода (decommission), включая owner, назначение и процедуру retirement. _(глава 7)_

**Secrets hygiene (гигиена секретов)** — правильное хранение, права доступа и ротация секретов; секреты не должны лежать в Git. _(главы 5, 6)_

**Secrets rotation (ротация секретов)** — регулярная плановая смена ключей и паролей для ограничения ущерба от утечки. _(глава 6)_

**Backup policy (политика бэкапов)** — определение того, что, как часто и с каким приоритетом бэкапится, кто владелец и как восстанавливается. _(главы 3, 7)_

**Test restore (проверка восстановления)** — реальный откат из snapshot или бэкапа; без него неизвестно, работает ли recovery вообще. _(глава 1)_

**Recovery baseline (базовый уровень восстановления)** — минимальный набор бэкапов и процедур, позволяющий восстановить сервис и данные за разумное время. _(глава 9)_

**RTO/RPO (Recovery Time / Point Objective)** — целевое время восстановления (RTO) и допустимая потеря данных по времени (RPO). _(глава 3)_

**Snapshot (снимок состояния)** — точка сохранения VM перед опасными изменениями для быстрого отката. _(главы 1, приложение B)_

**First split point (первая точка разделения)** — компонент, который первым выносится на отдельный узел при росте односерверной архитектуры (обычно БД). _(глава 2)_

**Tradeoff (компромисс)** — осознанный выбор между риском, стоимостью, сложностью и скоростью; архитектура безопасности — это серия tradeoff-решений. _(глава 5)_

**Operational cost / ops burden (операционная цена)** — стоимость поддержки решения: обновления, мониторинг, расследование. Сложность без компетенции сама становится риском. _(главы 5, 8)_

**Self-hosted vs managed (своё размещение vs управляемый сервис)** — выбор между полным контролем и собственной нагрузкой (self-hosted) и меньшим ops burden ценой vendor-зависимости (managed). _(глава 5)_

**Vendor lock-in (привязка к поставщику)** — зависимость от конкретного вендора, затрудняющая миграцию; учитывается через export path. _(глава 5)_

**TCO (Total Cost of Ownership)** — полная стоимость владения решением с учётом эксплуатации, а не только закупки. _(глава 5)_

**Security roadmap (дорожная карта безопасности)** — приоритизированный план мер по риску и зрелости: must have, next, later. _(глава 6)_

**Maturity level (уровень зрелости)** — стадия развития безопасности; advanced tooling оправдан только после закрытия базовых мер. _(главы 6, 8)_

**Secure by design / secure baseline (безопасность по умолчанию)** — изначально заложенный в архитектуру набор контролей вместо латания постфактум. _(главы 1, 2)_

**Reference architecture (эталонная архитектура)** — типовая защищаемая схема для конкретного масштаба и риска, которую можно сравнить и обосновать. _(главы 8, приложение B)_

**Defensible architecture (защитимая архитектура)** — решение, которое можно обосновать инженерными аргументами и восстановить с нуля (terraform/ansible) с данными на месте. _(глава 9)_

**Lab-only (только в лаборатории)** — правило: все проверки выполняются только на своих VM и сервисах, никогда против чужих систем. _(все главы, приложение B)_
