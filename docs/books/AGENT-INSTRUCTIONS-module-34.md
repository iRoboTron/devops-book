## Контекст проекта

Читатель — DevOps-инженер или разработчик который умеет работать с Git «как-то», но:

- избегает merge конфликтов и не знает как их разрешать;
- делает `git push --force` не задумываясь о последствиях;
- не знает разницы между fetch и pull;
- не настраивал SSH-ключи и пользуется HTTPS с паролем;
- работает только в main, без веток;
- видел GitFlow и GitOps но не понимает зачем;
- не умеет читать `git log --graph`.

**Что он хочет после книги:**
Уверенно работать с Git в команде: создавать ветки, разрешать конфликты, понимать rebase vs merge, настроить SSH, открывать Pull Request, знать как CI/CD связан с Git.

## Правило маркировки опасных команд

```markdown
> ☠️ **Осторожно:** [что именно удаляется/ломается и почему нельзя отменить]
```

Применять к:
- `git reset --hard` — удаляет незакоммиченные изменения
- `git push --force` — перезаписывает историю на remote
- `git clean -fd` — удаляет неотслеживаемые файлы

## Антипаттерны подачи

**Плохо:** «просто введите команду»
**Хорошо:** объяснить что делает флаг и почему

**Плохо:** «GitFlow — лучшая практика»
**Хорошо:** GitFlow избыточен для большинства — честно говорить когда он нужен, а когда нет

**Плохо:** давать `git push --force` без объяснения
**Хорошо:** `--force-with-lease` безопаснее, объяснить разницу

## Главная идея

Git — это не система резервного копирования. Это язык коммуникации в команде.

```text
Без Git:
"Что поменяли в пятницу?" — никто не знает.
"Верни как было" — поиск в почте и чатах.
CI/CD: откуда брать код для деплоя?

С Git:
git log nginx.conf  — кто, когда, зачем
git revert abc1234  — откатить конкретное изменение
CI/CD читает ветку main и деплоит автоматически
```
