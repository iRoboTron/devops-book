# Глава 12: Пароли разработчика: GitHub, SSH, токены, `.env`

> **Запомни:** для разработчика пароли — это не только вход на сайт, но и SSH-ключи, tokens, `.env` и секреты CI/CD.

---

## 12.1 Чем доступы разработчика отличаются от обычных

Обычный аккаунт даёт доступ к сайту.

Аккаунт разработчика может дать доступ к:

- исходному коду;
- production-серверу;
- домену;
- cloud-инфраструктуре;
- CI/CD;
- базе данных;
- секретам пользователей;
- токенам деплоя.

Поэтому GitHub или GitLab часто критичнее соцсети.

---

## 12.2 GitHub account

Для GitHub минимум:

- уникальный пароль;
- MFA;
- recovery codes;
- актуальный email;
- проверка SSH keys;
- проверка Personal Access Tokens;
- проверка connected applications.

Если GitHub используется для работы, это критичный аккаунт.

---

## 12.3 SSH keys

SSH-ключ — это пара:

```text
private key
public key
```

Public key можно добавлять на серверы и GitHub.

Private key нельзя отдавать никому.

Обычно private key лежит:

```text
~/.ssh/id_ed25519
```

Если кто-то получил private key и passphrase к нему нет, он может получить доступ туда, где ключ разрешён.

---

## 12.4 Passphrase на SSH-ключ

SSH-ключ можно защитить passphrase.

Плюс:

- украденный файл ключа сложнее использовать.

Минус:

- passphrase надо вводить;
- автоматизация может стать сложнее.

Для личного ключа passphrase обычно нужна.

Для deploy key и CI/CD сценариев решение зависит от контекста, но ключ должен иметь минимальные права.

---

## 12.5 Personal Access Tokens

Personal Access Token похож на пароль, но обычно:

- выдаётся для конкретного сервиса;
- может иметь ограниченные права;
- может иметь срок жизни;
- может быть отозван.

Правило:

> Token должен иметь минимальные права, достаточные для задачи.

Плохо:

```text
token with full access forever
```

Лучше:

```text
token for repo read only, expires in 30 days
```

---

## 12.6 Где хранить tokens

Варианты:

- менеджер паролей;
- secret storage CI/CD;
- environment variables;
- `.env` локально;
- systemd environment file;
- cloud secret manager.

Не хранить:

- в коде;
- в README;
- в публичном issue;
- в shell history;
- в скриншоте;
- в обычной заметке.

## 12.7 `.env`

Файл `.env` часто содержит:

```text
DATABASE_URL=
SECRET_KEY=
API_TOKEN=
SMTP_PASSWORD=
```

Он удобен, но опасен.

Правила:

- `.env` должен быть в `.gitignore`;
- в репозитории может быть `.env.example`;
- реальные значения не коммитятся;
- доступ к `.env` ограничен;
- при утечке secrets надо менять.

Пример `.env.example`:

```env
DATABASE_URL=postgresql://user:password@localhost:5432/app
SECRET_KEY=change-me
API_TOKEN=put-your-token-here
```

Это шаблон, не реальные секреты.

---

## 12.8 Проверка `.gitignore`

В тестовом проекте:

```bash
printf ".env\n" >> .gitignore
git status --short
```

Что делает команда:

- добавляет строку `.env` в `.gitignore`;
- `git status --short` показывает, что Git видит.

Если `.env` отсутствует в выводе `git status` — всё правильно.

### Если `.env` уже попал в репозиторий

Бывает, что `.env` добавили в Git до того, как написали `.gitignore`. В этом случае добавить строку в `.gitignore` недостаточно — Git уже отслеживает этот файл.

Нужно удалить его из отслеживания, не удаляя с диска:

```bash
git rm --cached .env
git add .gitignore
git commit -m "Stop tracking .env"
```

Что делает `git rm --cached`:
- говорит Git «перестань отслеживать этот файл»;
- файл остаётся на диске, данные не теряются;
- в следующем коммите `.env` не будет, а `.gitignore` защитит от повторного добавления.

**Критическое правило:**

> Если `.env` с реальными секретами попал в публичный репозиторий — считай его скомпрометированным, даже если удалишь потом. Git-история сохраняет всё. Меняй все пароли, токены и ключи, которые туда попали.

## 12.9 CI/CD secrets

CI/CD секреты нужны для:

- deploy;
- доступа к registry;
- cloud API;
- уведомлений;
- signing.

Правила:

- не печатать секреты в лог;
- давать минимальные права;
- ротировать при уходе сотрудника;
- ограничивать environments;
- проверять, какие workflows имеют доступ к secrets.

---

## 12.10 Что делать при утечке token

Порядок:

1. отозвать token;
2. создать новый с минимальными правами;
3. проверить логи использования;
4. проверить, куда token был закоммичен;
5. удалить из истории, если нужно, но не считать это достаточным;
6. поменять связанные секреты;
7. записать причину инцидента;
8. добавить проверку, чтобы не повторилось.

Важно:

> Если token попал в публичный репозиторий, считай его скомпрометированным.

---

## 12.11 Практика: тестовый PAT

Используй тестовый token с минимальными правами.

Шаги:

1. создай token с коротким сроком жизни;
2. дай минимальные права;
3. сохрани его в менеджер паролей;
4. используй для тестовой операции;
5. отзови token;
6. проверь, что он больше не работает.

Не используй production-token для учебной практики.

---

## 12.12 Практика: `.env` и `.gitignore`

Создай тестовый проект:

```bash
mkdir password-demo-project
cd password-demo-project
git init
printf ".env\n" > .gitignore
printf "SECRET_KEY=demo-do-not-use\n" > .env
printf "SECRET_KEY=change-me\n" > .env.example
git status --short
```

Ожидаемо:

```text
?? .env.example
?? .gitignore
```

`.env` не должен появиться.

После практики можно удалить тестовый проект.
