# Глава 7: Self-hosted менеджер паролей

> **Запомни:** self-hosted — это не "безопаснее", а "ты сам отвечаешь за большее количество деталей".

---

## 7.1 Что значит self-hosted

Self-hosted означает:

```text
Ты сам запускаешь сервис
Ты сам хранишь данные
Ты сам обновляешь сервер
Ты сам делаешь backup
```

Для менеджера паролей это особенно серьёзно.

Если плохо поднять блог, сломается блог.
Если плохо поднять password manager, под риском все доступы.

---

## 7.2 Почему self-hosted кажется привлекательным

Обычно причины такие:

- "не хочу отдавать пароли облаку";
- "хочу контролировать данные";
- "хочу бесплатно";
- "хочу научиться";
- "у меня уже есть VPS";
- "я DevOps, справлюсь".

Часть причин нормальные. Но нужно честно увидеть цену.

---

## 7.3 Что добавляется к ответственности

Если ты поднимаешь Vaultwarden или похожий сервис, тебе нужно:

- сервер;
- домен или локальное имя;
- HTTPS;
- reverse proxy;
- firewall;
- обновления;
- backup базы;
- backup attachments, если используются;
- мониторинг;
- логи;
- recovery-план;
- защита admin panel;
- понимание, кто имеет доступ к серверу.

Это уже не "поставил приложение".

---

## 7.4 Когда self-hosted не надо

Не стоит начинать с self-hosted, если:

- ты никогда не настраивал сервер;
- не умеешь делать backup;
- не знаешь, как восстановить backup;
- не обновляешь систему;
- хочешь сразу хранить реальные банковские и рабочие пароли;
- публичный VPS защищён слабо;
- нет второго способа доступа при аварии.

В таком случае managed cloud manager обычно безопаснее.

---

## 7.5 Когда self-hosted оправдан

Self-hosted может быть оправдан:

- как учебная lab;
- для домашней сети без публикации в интернет;
- для маленькой команды с техническим администратором;
- когда есть требования к контролю данных;
- когда backup и обновления уже привычны;
- когда есть отдельный план disaster recovery.

Главное слово: **проверено**.

Не "я настроил", а "я восстановил из backup на новой VM".

---

## 7.6 Безопасная учебная схема

Для начала используй VM из первой части курса или отдельную локальную VM.

Схема:

```text
Твой компьютер
  -> локальная сеть
  -> VM с Vaultwarden
```

На этом этапе:

- не публикуй сервис в интернет;
- не переноси реальные пароли;
- используй тестового пользователя;
- проверь backup и восстановление.

---

## 7.7 Минимальная модель Vaultwarden

Vaultwarden обычно запускают как контейнер.

```text
Контейнер Vaultwarden
  -> data directory (./vw-data)
  -> SQLite база внутри data
  -> attachments
  -> reverse proxy, если нужен HTTPS
```

### Минимальный учебный запуск (только локальная VM)

Создай файл `docker-compose.yml`:

```yaml
# Только для учебной локальной VM.
# Не публикуй без настройки HTTPS и firewall.
services:
  vaultwarden:
    image: vaultwarden/server:latest
    container_name: vaultwarden
    volumes:
      - ./vw-data:/data
    ports:
      - "127.0.0.1:8080:80"
    environment:
      - SIGNUPS_ALLOWED=true
    restart: unless-stopped
```

Что здесь важно:

- `127.0.0.1:8080:80` — сервис доступен только с самой VM, не из интернета;
- `./vw-data:/data` — данные хранятся в папке рядом с файлом;
- `SIGNUPS_ALLOWED=true` — для учебного теста, отключи в реальном сценарии.

Запуск:

```bash
docker compose up -d
```

После запуска сервис доступен на `http://127.0.0.1:8080`.

**Самая важная часть — данные, а не контейнер.**

Если удалить контейнер, но сохранить `./vw-data`, восстановление возможно.
Если удалить `./vw-data`, контейнер не поможет — данные потеряны.

---

## 7.8 Backup в self-hosted

Для self-hosted password manager backup обязателен.

Backup должен включать:

- базу данных;
- attachments;
- конфигурацию;
- `.env` или переменные окружения, если они нужны для запуска;
- инструкцию восстановления.

Backup должен быть:

- регулярным;
- защищённым;
- проверенным;
- доступным при поломке сервера.

---

## 7.9 Обновления

Self-hosted сервис нужно обновлять.

Но обновление без backup опасно.

Правильный порядок:

1. прочитать release notes, если есть критичные изменения;
2. сделать backup;
3. обновить;
4. проверить вход;
5. проверить создание записи;
6. проверить логи;
7. оставить старый backup до уверенности.

---

## 7.10 Логи

Логи помогают понять:

- сервис запустился или нет;
- есть ошибки базы;
- есть подозрительные попытки входа;
- работает ли reverse proxy;
- не упёрся ли диск.

Но логи не должны раскрывать секреты.

Не логируй пароли, tokens, recovery codes.

---

## 7.11 Практика: self-hosted только на тестовых данных

Эта практика для своей VM или домашней lab.

### Задача 1: описать ответственность

До установки напиши:

```text
Кто обновляет сервер?
Где backup?
Как восстановиться?
Кто имеет SSH-доступ?
Как проверить HTTPS?
Что делать при потере VM?
```

Если ответов нет, реальные пароли переносить нельзя.

### Задача 2: тестовый запуск

Запусти Vaultwarden в закрытой сети или локальной VM.

Цель не в том, чтобы дать универсальную команду для всех систем, а в том, чтобы понять компоненты:

```text
vaultwarden container
data volume
admin settings
test user
backup
restore
```

### Задача 3: тестовый пользователь

Создай пользователя:

```text
demo@example.local
```

Добавь только тестовые записи.

### Задача 4: backup

Останови сервис или используй рекомендованный способ backup для выбранной установки.

Скопируй data directory в отдельное место.

Проверь, что backup содержит не пустую папку, а реальные данные.

### Задача 5: восстановление

На новой VM или в новой папке:

- разверни сервис;
- подставь backup;
- войди тестовым пользователем;
- проверь записи.

Если восстановление не получилось, self-hosted ещё не готов для реальных паролей.

---

## 7.12 Self-hosted и интернет

Публиковать password manager в интернет можно только если ты понимаешь:

- DNS;
- HTTPS;
- reverse proxy;
- firewall;
- обновления;
- rate limiting;
- monitoring;
- backup;
- security headers;
- доступ к admin panel.

Если эти слова пока туманны, держи lab локальной.

---

## 7.13 Managed vs self-hosted

| Критерий | Managed cloud | Self-hosted |
|---|---|---|
| Установка | Простая | На тебе |
| Обновления | Сервис | На тебе |
| Backup инфраструктуры | Сервис + твой export | На тебе |
| Контроль данных | Меньше | Больше |
| Цена ошибки | Ниже для новичка | Очень высокая |
| Обучение | Меньше | Отличное |
| Семья | Проще | Сложнее |

Вывод:

- для большинства людей managed лучше;
- для обучения self-hosted полезен;
- для реальных паролей self-hosted требует зрелой эксплуатации.
