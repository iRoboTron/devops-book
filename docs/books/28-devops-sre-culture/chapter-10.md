# Глава 10: Итоговый проект — надёжность маленького сервиса

> **Цель:** оформить один свой проект как управляемый сервис.

---

## 10.1 Что нужно получить

Создай документ `SERVICE-RELIABILITY.md`.

Он должен отвечать:

- что делает сервис;
- кто пользователь;
- что будет при падении;
- какие SLI/SLO выбраны;
- какой error budget;
- как деплоить;
- как откатиться;
- как узнать о проблеме;
- где runbook;
- какой toil надо убрать.

## 10.2a Заполненный пример: Бот уведомлений Telegram

Ниже — как выглядит заполненный `SERVICE-RELIABILITY.md` для реального маленького сервиса.

```markdown
# Service reliability profile — Бот уведомлений Telegram

## Что делает сервис

Python-бот читает события из SQLite-базы и отправляет пользователям Telegram-уведомления
по расписанию (раз в час). Работает как systemd-сервис на одном VPS (Ubuntu 22.04, 1 CPU,
1 GB RAM). Кода ~400 строк.

## Пользователи

3 человека (автор + 2 знакомых). Уведомления некритичные: пропущенное уведомление
создаёт неудобство, но не влечёт потери денег или данных.

## Влияние падения

| Сценарий | Последствие |
|---|---|
| Бот молчит < 2 часов | Пользователь не замечает |
| Бот молчит 2–12 часов | Пользователь пишет в личку |
| Бот молчит > 12 часов | Нужно расследование и объяснение |
| SQLite-база повреждена | Потеря части истории уведомлений |

## Важные зависимости

| Зависимость | Тип | Что будет если упадёт |
|---|---|---|
| Telegram Bot API | Внешний | Бот не может отправлять сообщения |
| SQLite-файл `/var/bot/data.db` | Локальный | Нет данных для отправки |
| Системные часы (cron/systemd timer) | Локальный | Уведомления не запускаются |
| Интернет-соединение VPS | Инфраструктура | Потеря связи с Telegram API |

## SLI / SLO

| SLI | Как измеряется | SLO |
|---|---|---|
| Успешная отправка за час | `grep "sent OK" /var/log/bot.log \| wc -l` (должно быть > 0 каждые 60 мин) | ≥ 95% запусков успешны за 30 дней |
| Задержка отправки | Разница между `scheduled_at` и `sent_at` в БД | ≤ 5 минут в 90% случаев |
| Доступность процесса | `systemctl is-active tg-bot` раз в 5 мин | Процесс работает 99% времени |

## Error budget

Период: 30 дней (43 200 минут)
SLO: 99% uptime процесса
Допустимое плохое время: 432 минуты (~7 часов 12 минут в месяц)
Потрачено в текущем месяце: ~40 минут (1 перезапуск после OOM)
Остаток: ~392 минуты

## Деплой

Как сейчас:
1. `git pull` на VPS в директории `/opt/tg-bot/`
2. `pip install -r requirements.txt` (если изменились зависимости)
3. `sudo systemctl restart tg-bot`
4. Проверить: `journalctl -u tg-bot -n 30`

Как проверить:
```bash
# Статус процесса
systemctl status tg-bot

# Последние строки лога
journalctl -u tg-bot --since "5 minutes ago"

# Проверить отправку вручную
python /opt/tg-bot/send_test.py
```

Как откатиться:
```bash
cd /opt/tg-bot
git log --oneline -5          # найти предыдущий рабочий коммит
git checkout <commit-hash>    # откатиться
sudo systemctl restart tg-bot
journalctl -u tg-bot -n 20   # убедиться что работает
```

## Runbook

Файл: `/opt/tg-bot/docs/runbook.md`

Основные сценарии:
- Бот не отправляет → проверить `systemctl status tg-bot`, затем `journalctl -u tg-bot -n 50`
- OOM kill → увеличить swap (`fallocate -l 512M /swapfile`) или оптимизировать запросы к БД
- Telegram 429 (rate limit) → добавить `time.sleep(1)` между отправками, дождаться сброса лимита
- SQLite locked → убить зависший процесс: `fuser /var/bot/data.db`

## Toil backlog

| Ручная задача | Как часто | Как убрать |
|---|---|---|
| `git pull` + `systemctl restart` вручную | При каждом деплое (~1 раз в 2 нед.) | GitHub Actions → SSH deploy script |
| Проверять `journalctl` вручную | Раз в неделю | Настроить Uptime Kuma или аналог |
| Делать `sqlite3 data.db .dump` бэкап вручную | Раз в месяц (когда вспоминаю) | Systemd timer + rsync на другой сервер |
| Обновлять токен бота вручную в `.env` | Раз в год | Хранить в секрете (Vault / environment) |

## Улучшения

### За 1 день
- Настроить автоматический бэкап SQLite через systemd timer раз в сутки
- Добавить алерт в Telegram самому себе при падении процесса (`OnFailure=` в юните)

### За 1 неделю
- Написать deploy-скрипт и подключить через GitHub Actions (push → автодеплой)
- Настроить Uptime Kuma на том же VPS для мониторинга процесса

### За 1 месяц
- Перевести хранение расписания из SQLite в простой YAML-файл (меньше риска corruption)
- Добавить retry-логику при ошибке Telegram API (до 3 попыток с backoff)
- Написать smoke-test который запускается после каждого деплоя
```
