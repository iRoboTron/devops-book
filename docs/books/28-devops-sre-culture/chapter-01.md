# Глава 1: Что такое DevOps на самом деле

> **Цель:** перестать путать DevOps с Docker, Kubernetes и названием вакансии.

---

## 1.1 Dev и Ops

Dev — это разработка: написать функцию, исправить баг, изменить интерфейс.

Ops — это эксплуатация: чтобы сервис работал на сервере, обновлялся, восстанавливался и был понятен в аварии.

Проблема начинается, когда эти части живут отдельно:

```text
разработчик: у меня работает
админ: у меня падает
пользователь: мне всё равно, почините
```

DevOps пытается убрать стену между "написать" и "запустить".

---

## 1.2 DevOps как культура

Культура здесь не про корпоративные плакаты. Это набор привычек:

- делать маленькие изменения;
- проверять автоматически;
- деплоить повторяемо;
- видеть метрики и логи;
- быстро получать обратную связь;
- разбирать инциденты без охоты на виноватого;
- улучшать процесс после ошибок.

Инструменты помогают, но не заменяют мышление.

---

## 1.3 Инструменты без мышления не спасают

Можно иметь Kubernetes и всё равно деплоить хаотично. Можно иметь простой Docker Compose и хороший процесс.

| Подход | Как выглядит | Плюсы | Минусы | Главный риск |
|---|---|---|---|---|
| Ручной деплой | человек копирует файлы | быстро начать | ошибки, забытые шаги | неповторяемость |
| Deploy script | одна команда | меньше ручного труда | скрипт надо поддерживать | скрытая магия |
| CI/CD | проверка и доставка из Git | повторяемо | нужна настройка | ложное чувство безопасности |
| Platform approach | готовые пути для команды | удобно многим | дорого и сложно | бюрократия |

Человеческий вывод: новичку нужен не "сразу Kubernetes", а повторяемый путь от commit до работающего сервиса.

---

## 1.4 Feedback loop

Feedback loop — это скорость, с которой ты узнаёшь, что изменение хорошее или плохое.

```text
быстрая обратная связь -> дешёвая ошибка
медленная обратная связь -> дорогая ошибка
```

Если ошибка находится у тебя в редакторе — это дешево. Если через неделю у пользователя — дорого.

Весь смысл DevOps-культуры — замкнуть этот цикл и сделать каждый виток короче: выводы из эксплуатации возвращаются в код, а не теряются.

```mermaid
flowchart LR
    A["Код\nизменение"] --> B["Проверка\nтесты + lint"]
    B --> C["Деплой\nповторяемо"]
    C --> D["Мониторинг\nметрики + логи"]
    D --> E["Инцидент\nили сигнал"]
    E --> F["Выводы\npostmortem"]
    F -->|"улучшение процесса"| A

    style A fill:#2d2d2d,color:#fff
    style C fill:#1a5276,color:#fff
    style D fill:#1e8449,color:#fff
    style E fill:#6e2f1a,color:#fff
    style F fill:#7d6608,color:#fff
```

Медленная обратная связь — это длинный путь от E обратно к A. Быстрая — короткий.

## 1.5 Практика

Возьми ручной процесс деплоя и разложи:

| Шаг | Сейчас вручную? | Можно автоматизировать? | Как проверить? |
|---|---|---|---|
| скопировать файлы | да | rsync/script | checksum/version |
| перезапустить сервис | да | systemd/deploy script | status/curl |
| проверить сайт | да | smoke test | HTTP 200 |

Проверка: выбери один самый частый ручной шаг и опиши, как сделать его повторяемым.
