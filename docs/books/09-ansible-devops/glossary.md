# Глоссарий

> Термины и выражения книги «Ansible для DevOps». В скобках — главы, где термин вводится или активно используется.

---

**Ansible** — система управления конфигурацией и автоматизации, которая приводит серверы к описанному состоянию по SSH, без установки агентов. _(глава 0)_

**Agentless (без агента)** — модель Ansible, при которой на управляемых серверах не работает постоянный процесс: нужны только SSH и Python. _(глава 0)_

**Push-модель** — control node сам инициирует подключение и отправляет задачи на серверы, в отличие от pull-моделей, где агент сам тянет конфигурацию. _(глава 0)_

**Control node (управляющий узел)** — машина, с которой запускается Ansible: ноутбук или CI-раннер. На ней лежат playbook, inventory и ключи. _(главы 0, 7)_

**Managed host (управляемый хост)** — сервер, который Ansible настраивает по SSH. В книге это `web1` — сервер для Flask за Nginx. _(главы 0, 1)_

**Idempotency (идемпотентность)** — свойство, при котором повторный запуск playbook не меняет уже приведённую к нужному состоянию систему: второй запуск даёт `changed=0`. _(главы 0, 2, 4, 9)_

**Inventory** — список серверов и их параметров, который сообщает Ansible, куда подключаться. Чаще всего файл `inventory/hosts.yml`. _(глава 1)_

**Static inventory (статический inventory)** — inventory, заданный вручную в файле с фиксированными IP. С него рекомендуется начинать. _(глава 1)_

**Dynamic inventory (динамический inventory)** — inventory, генерируемый автоматически, например из `terraform output`, чтобы не копировать IP вручную. _(глава 1)_

**Group (группа)** — именованный набор хостов в inventory (например `web`), к которому можно адресовать задачи и переменные. _(главы 1, 3)_

**`all`** — встроенная группа, охватывающая все хосты inventory. _(главы 1, 2)_

**`ansible_host`** — переменная хоста с реальным IP или DNS, отделяющая логическое имя хоста от его адреса. _(глава 1)_

**`ansible_user`** — пользователь, под которым Ansible подключается к серверу по SSH. _(глава 1)_

**`ansible.cfg`** — файл конфигурации Ansible по умолчанию: путь к inventory, SSH-ключ, настройки become и host key checking. _(глава 1)_

**`host_key_checking`** — настройка проверки SSH host key. На новых учебных серверах часто отключается, в production остаётся включённой. _(глава 1)_

**`ansible all -m ping`** — базовая проверка связи: Ansible заходит по SSH, запускает Python и получает `pong`. Не ICMP-ping. _(глава 1)_

**`pong`** — успешный ответ модуля `ping`, означающий рабочее SSH-подключение и доступный Python на сервере. _(глава 1)_

**UNREACHABLE** — статус, когда хост недоступен по SSH: проблема с сетью, IP, ключом или пользователем — ещё до выполнения задач. _(главы 1, 2)_

**Ad-hoc команда** — быстрая разовая команда `ansible <группа> -m <модуль>` без playbook, удобная для диагностики. _(глава 2)_

**Module (модуль)** — единица работы Ansible (`apt`, `service`, `copy`, `file`, `template`), которая знает желаемое состояние и умеет быть идемпотентной. _(главы 0, 2)_

**`apt`** — модуль управления пакетами в Debian/Ubuntu; `state: present` ставит, `state: absent` удаляет. _(главы 0, 2)_

**`service` / `systemd`** — модули управления сервисами: запуск, остановка, перезагрузка, автозапуск (`enabled`). _(главы 2, 4)_

**`copy`** — модуль копирования статического файла на сервер. _(главы 2, 4)_

**`file`** — модуль управления файлами и директориями: путь, состояние, владелец, права. _(главы 2, 4)_

**`command` vs `shell`** — `command` выполняет команду без оболочки, `shell` нужен для pipe и redirect. Модуль всегда предпочтительнее обоих. _(глава 2)_

**`ansible-doc`** — встроенная документация по модулям с параметрами и примерами. _(глава 2)_

**`changed`** — статус задачи, означающий, что Ansible внёс изменение в систему. _(главы 2, 4)_

**`ok`** — статус задачи, означающий, что система уже в нужном состоянии и менять ничего не пришлось. _(главы 2, 4)_

**Variable (переменная)** — именованное значение, убирающее хардкод из задач: `domain`, `app_port`, `deploy_user`. _(глава 3)_

**Variable precedence (приоритет переменных)** — порядок, в котором источник с более высоким приоритетом переопределяет нижний (от `role defaults` до `-e`). _(глава 3)_

**`group_vars`** — переменные, общие для всех хостов группы (например `group_vars/web.yml`). _(глава 3)_

**`host_vars`** — переменные только для одного конкретного хоста; переопределяют `group_vars`. _(глава 3)_

**Facts (факты)** — данные о хосте, которые Ansible собирает автоматически (`ansible_hostname`, `ansible_os_family`, RAM, CPU). _(главы 3, 5)_

**`setup`** — модуль, собирающий и показывающий facts хоста; поддерживает `filter`. _(глава 3)_

**`register`** — сохранение результата задачи в переменную для использования в следующих шагах. _(главы 3, 8)_

**`when`** — условие выполнения задачи на основе факта, переменной или результата `register`. _(главы 3, 8)_

**`debug`** — модуль вывода переменных и сообщений для отладки. _(главы 3, 9)_

**`extra-vars` (`-e`)** — переменные командной строки с самым высоким приоритетом; удобны в CI и для разовых запусков. _(глава 3)_

**Playbook** — YAML-файл с описанием желаемого состояния серверов; обычно главный `site.yml`. _(глава 4)_

**Play** — блок playbook, связывающий набор хостов (`hosts:`) с задачами и handlers. _(глава 4)_

**Task (задача)** — отдельный шаг play: вызов модуля с параметрами и (желательно) `name`. _(глава 4)_

**Handler** — особая задача, запускаемая один раз в конце play и только по сигналу `notify`. _(главы 4, 6)_

**`notify`** — механизм, который при изменении (`changed`) ставит handler в очередь на выполнение. _(главы 4, 6)_

**`become` / sudo** — повышение привилегий для выполнения задач от root (`become: true`, флаг `-b`). _(главы 1, 2, 4)_

**Tags (теги)** — метки задач, позволяющие запускать или пропускать части playbook (`--tags`, `--skip-tags`). _(глава 4)_

**`--check` (dry-run)** — режим показа изменений без их применения; с `--diff` показывает разницу файлов. _(глава 4)_

**Verbose (`-v` / `-vvv`)** — уровни подробного вывода для отладки SSH, переменных и задач. _(главы 4, 9)_

**`--limit`** — ограничение запуска playbook на конкретные хосты. _(глава 4)_

**`ansible-playbook`** — команда запуска playbook (`ansible-playbook site.yml`). _(главы 0, 4)_

**Template (шаблон)** — конфиг с переменными в формате Jinja2 (`.j2`), из которого Ansible рендерит готовый файл. _(глава 5)_

**Jinja2** — язык шаблонов: `{{ variable }}`, `{% if %}`, `{% for %}`, фильтры вроде `| default(val)`. _(глава 5)_

**`template` (модуль)** — копирует на сервер файл, отрендеренный из `.j2` с подстановкой переменных и facts. _(глава 5)_

**Role (роль)** — переиспользуемый набор задач, handlers, шаблонов и переменных со стандартной структурой папок. _(глава 6)_

**`ansible-galaxy init`** — команда создания скелета роли со всеми директориями. _(глава 6)_

**`defaults` (роли)** — переменные роли с низким приоритетом, которые легко переопределить извне. _(глава 6)_

**`vars` (роли)** — переменные роли с высоким приоритетом для внутренних констант. _(глава 6)_

**`meta/main.yml`** — файл метаданных роли, где задаются зависимости (`dependencies`). _(глава 6)_

**Ansible Galaxy** — репозиторий готовых ролей сообщества (`ansible-galaxy install`, например `geerlingguy.nginx`). _(глава 6)_

**Ansible Vault** — инструмент шифрования секретов (паролей, ключей), позволяющий безопасно коммитить зашифрованные файлы. _(глава 7)_

**`ansible-vault encrypt` / `edit` / `view`** — команды для шифрования, редактирования и просмотра защищённых файлов. _(глава 7)_

**`encrypt_string` (vault_string)** — шифрование одного значения для вставки прямо в YAML рядом с обычными переменными. _(глава 7)_

**`.vault_pass`** — файл с паролем Vault; всегда в `.gitignore` и никогда не попадает в репозиторий. _(глава 7)_

**`--ask-vault-pass` / `--vault-password-file`** — способы передать пароль Vault при запуске playbook. _(глава 7)_

**`loop`** — повтор задачи по списку или списку словарей вместо дублирования одинаковых задач. _(глава 8)_

**`block` / `rescue` / `always`** — конструкция обработки ошибок, аналог `try / catch / finally`. _(глава 8)_

**`until` / `retries` / `delay`** — повтор задачи до выполнения условия с заданным числом попыток и паузой между ними. _(глава 8)_

**`uri`** — модуль HTTP-запросов, часто используемый для health-проверки приложения после деплоя. _(глава 8)_

**`changed_when` / `failed_when`** — переопределение того, когда задача считается изменившей систему или провалившейся. _(главы 9, 3)_

**`assert`** — модуль проверки условий (например минимума RAM), останавливающий playbook с понятной ошибкой. _(глава 9)_

**Molecule** — фреймворк тестирования ролей в изолированном окружении (обычно Docker) по циклу create → converge → verify → destroy. _(глава 9)_

**`converge` / `verify`** — этапы Molecule: применение роли и проверка результата. _(глава 9)_
