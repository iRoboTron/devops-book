## Контекст проекта

Читатель прошёл DevOps 1.0. У него есть сервер с публичным IP. Он умеет настраивать ufw, SSH, Nginx.

**Что его раздражает прямо сейчас:**
- Сервисы на сервере (Nextcloud, Grafana, внутренние инструменты) либо открыты всем, либо закрыты даже ему
- Нет удобного способа безопасно работать с сервером с разных мест
- Слышал про VPN, но OpenVPN выглядит сложно, а про WireGuard не знает
- Хочет зайти на домашний сервер с телефона или из кафе без открытия портов всем подряд

**Что он хочет после этой книги:**
Зашифрованный туннель между его устройствами и сервером. Телефон, ноутбук, домашний компьютер — всё в одной частной сети. Сервисы видны только через VPN, не из открытого интернета.

## Главная идея

WireGuard — это современный VPN, который настраивается за 30 минут.

```
Без WireGuard:              С WireGuard:
Nextcloud открыт всем       Nextcloud видно только тебе
→ или закрыт всем           → туннель шифрует трафик
→ страшно открывать          → с телефона как будто дома
```

**Ключевое понимание:**
- WireGuard — это peer-to-peer: нет клиента и сервера в классическом смысле, есть peers
- Каждый peer имеет пару ключей: приватный (только у него) и публичный (у всех)
- Соединение устанавливается только если обе стороны знают ключи друг друга
- WireGuard проще OpenVPN в 10 раз — конфиг на 10 строк вместо 50

## Структура книги

### Глава 0: Зачем VPN и почему WireGuard

**Цель:** читатель понимает проблему и почему именно WireGuard.

Объяснить:
- Что такое VPN в одном предложении: зашифрованный туннель, через который трафик идёт как будто ты в частной сети
- Сценарии когда нужен VPN:
  - работа с сервером из публичного Wi-Fi
  - закрыть внутренние сервисы от интернета
  - объединить несколько машин в одну сеть
  - удалённый доступ к домашней сети

Почему WireGuard, а не OpenVPN или IPsec:

| Критерий | WireGuard | OpenVPN | IPsec |
|---|---|---|---|
| Сложность настройки | Очень низкая | Средняя | Высокая |
| Строк конфига | ~10 | ~50 | ~100+ |
| Скорость | Высокая | Средняя | Средняя |
| Встроен в Linux | С 5.6 (2020) | Нет | Нет |
| Мобильные клиенты | Есть | Есть | Есть |

**Ключевая идея:** WireGuard встроен в ядро Linux. Это не сторонний sofware — это часть ОС.

### Глава 1: Как работает WireGuard — минимальная теория

**Цель:** читатель понимает модель ключей и peers, не углубляясь в криптографию.

Объяснить:
- Каждый участник (peer) имеет пару ключей:
  ```
  Приватный ключ → только у тебя, никому не показывать
  Публичный ключ → можно передать любому peer
  ```
- Соединение = ты знаешь публичный ключ другого + он знает твой
- Нет "сервера" в классическом смысле — есть peer который слушает входящие подключения
- IP-адреса в VPN-сети (`10.0.0.x`) — отдельные от реальных IP

Генерация ключей:
```bash
# Приватный ключ
wg genkey | tee privatekey

# Публичный ключ из приватного
cat privatekey | wg pubkey | tee publickey

# Или в одну строку
wg genkey | tee /etc/wireguard/server_private.key | \
  wg pubkey > /etc/wireguard/server_public.key
```

### Глава 2: Установка на сервере

**Цель:** WireGuard установлен и готов к настройке.

```bash
# Ubuntu 22.04 / 24.04
sudo apt update
sudo apt install wireguard

# Проверить что модуль ядра загружен
lsmod | grep wireguard
# или
modprobe wireguard && echo "OK"
```

Включить IP forwarding (нужно для роутинга трафика):
```bash
# Временно
echo 1 > /proc/sys/net/ipv4/ip_forward

# Постоянно
echo "net.ipv4.ip_forward = 1" | sudo tee -a /etc/sysctl.conf
sudo sysctl -p
```

### Глава 3: Первый туннель — сервер и один клиент

**Цель:** рабочее соединение между сервером и одним устройством.

**На сервере создать** `/etc/wireguard/wg0.conf`:
```ini
[Interface]
# Приватный ключ сервера
PrivateKey = <SERVER_PRIVATE_KEY>
# IP сервера в VPN-сети
Address = 10.0.0.1/24
# Порт для входящих подключений
ListenPort = 51820

# PostUp/PreDown — правила для NAT (нужно для выхода в интернет через VPN)
PostUp = iptables -A FORWARD -i %i -j ACCEPT; \
         iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE
PreDown = iptables -D FORWARD -i %i -j ACCEPT; \
          iptables -t nat -D POSTROUTING -o eth0 -j MASQUERADE

[Peer]
# Публичный ключ клиента (ноутбука или телефона)
PublicKey = <CLIENT_PUBLIC_KEY>
# IP который мы разрешаем этому клиенту
AllowedIPs = 10.0.0.2/32
```

**На клиенте** (Linux):
```ini
[Interface]
PrivateKey = <CLIENT_PRIVATE_KEY>
Address = 10.0.0.2/24
DNS = 1.1.1.1

[Peer]
PublicKey = <SERVER_PUBLIC_KEY>
Endpoint = ВАШ_СЕРВЕР_IP:51820
# Какой трафик пускать через туннель:
# 10.0.0.0/24 — только VPN-сеть (split tunnel)
# 0.0.0.0/0   — весь трафик (full tunnel)
AllowedIPs = 10.0.0.0/24
PersistentKeepalive = 25
```

Объяснить каждый параметр. Обязательно разобрать:
- Разница `AllowedIPs = 10.0.0.0/24` (split tunnel) vs `0.0.0.0/0` (full tunnel)
- Зачем `PersistentKeepalive` — держит соединение через NAT

Запуск:
```bash
# Запустить интерфейс
sudo wg-quick up wg0

# Проверить статус
sudo wg show

# Проверить соединение
ping 10.0.0.2
```

**Практика:** поднять туннель, убедиться что сервер пингуется по VPN-IP.

### Глава 4: ufw и WireGuard — не заблокировать себя

**Цель:** firewall настроен правильно, доступ через WireGuard работает.

Это важная глава — неправильная настройка ufw может заблокировать SSH.

```bash
# Порядок действий:
# 1. Сначала разрешить WireGuard порт
sudo ufw allow 51820/udp

# 2. Разрешить трафик через wg0 интерфейс
sudo ufw allow in on wg0
sudo ufw allow out on wg0

# 3. НЕ закрывать SSH (22) пока не убедился что VPN работает
# 4. Только потом можно ограничивать доступ к сервисам

# Проверить статус
sudo ufw status verbose
```

Типичная ошибка: включить ufw и заблокировать SSH до настройки WireGuard. Что делать если это произошло — восстановление через консоль провайдера.

Стратегия: сервисы только на wg0 интерфейсе:
```nginx
# Nginx слушает только на VPN-IP
server {
    listen 10.0.0.1:80;
    # ... остальное
}
```

### Глава 5: Автозапуск через systemd

**Цель:** WireGuard поднимается автоматически при старте сервера.

```bash
# Включить автозапуск
sudo systemctl enable wg-quick@wg0

# Запустить сейчас
sudo systemctl start wg-quick@wg0

# Проверить статус
systemctl status wg-quick@wg0

# Перезапустить после изменения конфига
sudo systemctl restart wg-quick@wg0
# или
sudo wg-quick down wg0 && sudo wg-quick up wg0
```

Проверить что работает после ребута:
```bash
sudo reboot
# Подождать ~30 сек
ssh user@server_ip
sudo wg show
```

### Глава 6: Добавить телефон и ноутбук

**Цель:** все устройства читателя подключены к VPN.

**Android / iOS:**
- Установить WireGuard из официального магазина
- Сгенерировать ключи в приложении или на сервере
- Передать конфигурацию через QR-код:
  ```bash
  # Сгенерировать QR-код из конфига
  sudo apt install qrencode
  qrencode -t ansiutf8 < /etc/wireguard/client-phone.conf
  ```
- Сканировать QR телефоном

**Windows:**
- Скачать официальный клиент с wireguard.com
- Импортировать `.conf` файл

**Важно:** для каждого устройства — отдельная пара ключей и отдельный `[Peer]` блок на сервере.

Добавить нового клиента без перезапуска:
```bash
# Добавить peer динамически (без перезапуска wg0)
sudo wg set wg0 peer <CLIENT_PUBLIC_KEY> allowed-ips 10.0.0.4/32

# Сохранить в конфиг
sudo wg-quick save wg0
```

### Глава 7: Диагностика

**Цель:** читатель умеет найти и исправить проблему с соединением.

Алгоритм диагностики:
```
1. sudo wg show          → смотрим handshake
2. ping 10.0.0.1         → пингуем сервер через VPN
3. sudo ufw status       → проверяем порты
4. journalctl -u wg-quick@wg0 → смотрим логи
5. tcpdump -i eth0 port 51820 → видим ли UDP пакеты
```

Типичные проблемы:

| Симптом | Вероятная причина |
|---|---|
| Handshake давно (>3 мин) | Клиент не подключён или неверный ключ |
| `latest handshake` не обновляется | Нет UDP 51820 на сервере (ufw) |
| Ping до сервера идёт, интернет нет | PostUp правила не применились |
| Соединение рвётся | Убрать PersistentKeepalive |

```bash
# Проверить что UDP порт открыт на сервере
sudo ss -ulnp | grep 51820

# Проверить правила iptables
sudo iptables -t nat -L POSTROUTING -n -v
```

### Глава 8: Итоговый проект

**Цель:** все устройства читателя в одной VPN-сети, сервисы доступны только через VPN.

Результат:
```
wg0 сеть: 10.0.0.0/24

  10.0.0.1  →  сервер (VPS)
  10.0.0.2  →  ноутбук
  10.0.0.3  →  телефон
  10.0.0.4  →  домашний компьютер (если есть)
```

Шаги:
1. Сервер настроен, systemd автозапуск включён
2. Все устройства добавлены как peers
3. Один сервис (например Nextcloud или Grafana) слушает только на `10.0.0.1`
4. Проверка: с телефона через LTE (не домашний Wi-Fi) открывается сервис
5. Документация: таблица peers, ключи хранятся в менеджере паролей

## Особые требования

### Про безопасность ключей
Приватный ключ WireGuard — это как SSH private key. Потерял — сгенерируй новый. Дал чужому — переделай конфиги.

### Про разные сетевые интерфейсы
Имя внешнего интерфейса сервера может быть не `eth0` а `ens3`, `enp1s0` и т.д. Научи читателя проверять:
```bash
ip route show default
# Вывод: default via X.X.X.X dev eth0
# dev eth0 — это нужное имя
```

### Не делать
- Не углубляться в криптографию WireGuard
- Не описывать site-to-site для офисов — это за рамками книги
- Не сравнивать все VPN протоколы детально
