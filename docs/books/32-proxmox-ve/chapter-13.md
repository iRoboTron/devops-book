# Глава 13: Обслуживание и мониторинг

> **Что вы узнаете:**
> - как правильно обновлять хост Proxmox и все LXC-контейнеры;
> - как установить Netdata — через Community Scripts и вручную;
> - что мониторить в первую очередь и что означают ключевые метрики;
> - как безопасно делать мажорные обновления (7→8, 8→9) без риска потерять данные;
> - диагностические команды, которые помогают быстро понять состояние системы.

---

Сервер поставлен, сервисы работают. Теперь начинается настоящая эксплуатация. Обновления накапливаются, диски заполняются, что-то может тормозить — и об этом нужно узнавать раньше, чем пользователи.

Эта глава о трёх вещах: как правильно обновлять (и не сломать), как видеть что происходит в системе прямо сейчас, и что делать когда выходит мажорная версия Proxmox.

---

## 13.1 Обновление хоста Proxmox

Proxmox — это Debian с дополнительными пакетами. Обновляется стандартно, но команда `apt upgrade` здесь не используется. Только `full-upgrade` — он корректно обрабатывает зависимости пакетов ядра и Proxmox.

```bash
# Обновить хост Proxmox
apt update && apt full-upgrade -y
```

`apt upgrade` может пропустить пакеты, которые требуют изменения зависимостей. `full-upgrade` (он же `dist-upgrade`) применяет все изменения — именно это нужно для корректного обновления pve-kernel и связанных пакетов.

После обновления хоста — обновить список доступных шаблонов LXC:

```bash
pveam update
```

Это не устанавливает шаблоны, а только обновляет список — чтобы при создании нового контейнера были актуальные версии Debian, Ubuntu и других ОС.

**Нужно ли перезагружаться после обновления?**

Если обновилось ядро — да, обязательно. Проверить:

```bash
# Смотрим какое ядро запущено сейчас
uname -r

# И какое ядро стоит как новейшее
dpkg -l | grep pve-kernel | grep -v rc | tail -3
```

Если версии расходятся — перезагрузить сервер. Proxmox корректно переживает перезагрузку: контейнеры с автозапуском стартуют сами.

**Совет:** делать обновления хоста раз в 1-2 недели. Не копить месяцами — чем больше накопилось, тем выше риск что что-то пойдёт не так.

## 13.2 Обновление всех LXC-контейнеров

Обновлять каждый контейнер вручную — заходить по одному и запускать `apt upgrade` — утомительно. Особенно когда контейнеров 5-10. Для этого есть простой скрипт.

```bash
#!/bin/bash
# update-all-lxc.sh — обновить все запущенные LXC-контейнеры

for ct in $(pct list | awk 'NR>1 {print $1}'); do
  # Проверить что контейнер запущен
  STATUS=$(pct status $ct | awk '{print $2}')
  if [ "$STATUS" != "running" ]; then
    echo "=== CT $ct: пропускаем (статус: $STATUS) ==="
    continue
  fi

  echo "=== Обновляем CT $ct ==="
  pct exec $ct -- bash -c "apt update && apt upgrade -y" 2>/dev/null || true
  echo "=== CT $ct: готово ==="
done

echo ""
echo "Все контейнеры обновлены."
```

`|| true` в конце нужен чтобы скрипт не прерывался если в одном контейнере что-то не так — например нет apt (Alpine Linux) или контейнер недоступен изнутри.

**Сохранить скрипт и добавить в cron:**

```bash
# Сохранить скрипт
chmod +x /usr/local/bin/update-all-lxc.sh

# Добавить в cron — каждую субботу в 04:00
crontab -e
```

Строка для cron:

```
0 4 * * 6 /usr/local/bin/update-all-lxc.sh >> /var/log/lxc-updates.log 2>&1
```

Лог будет копиться в `/var/log/lxc-updates.log`. Раз в месяц можно заглядывать — убедиться что всё обновляется без ошибок.

**Почему не обновлять все автоматически без проверки?**

Автоматические обновления — это удобно, но иногда обновление пакета ломает сервис. Например: новая версия nginx изменила путь к конфигу, или PHP обновился и модуль несовместим. Поэтому правило: скрипт запускается автоматически, но лог проверяется раз в неделю. Если что-то сломалось — откатить через снапшот (именно поэтому снапшоты делаются перед обновлениями).

## 13.3 Netdata — мониторинг хоста в реальном времени

Netdata — лёгкий агент мониторинга с красивым веб-интерфейсом. Устанавливается за несколько минут, не требует настройки баз данных или сложных конфигов. Сразу после установки показывает: CPU, RAM, диски, сеть, процессы, температуру дисков — и всё это в реальном времени с интервалом обновления 1 секунда.

В отличие от тяжёлого стека Prometheus + Grafana, Netdata запускается в одном контейнере и сразу готова к работе. Для домашнего сервера — идеальный выбор.

### Установка через Community Scripts

Самый быстрый способ — запустить скрипт на хосте Proxmox. Он создаст LXC-контейнер и установит Netdata автоматически:

```bash
bash -c "$(curl -fsSL https://raw.githubusercontent.com/community-scripts/ProxmoxVE/main/ct/netdata.sh)"
```

Скрипт спросит параметры контейнера (или создаст со значениями по умолчанию). После завершения выведет IP и порт:

```
Netdata установлен. Открыть: http://192.168.1.105:19999
```

### Установка вручную в LXC

Если Community Scripts недоступен или нужен контроль над установкой:

```bash
# 1. Создать LXC с Debian 12 (512MB RAM, 8GB диск — хватит с запасом)
# Через веб-интерфейс или pct create

# 2. Войти в контейнер
pct start 110 && pct enter 110

# 3. Скачать и запустить официальный скрипт установки
wget -O /tmp/netdata-kickstart.sh https://get.netdata.cloud/kickstart.sh
sh /tmp/netdata-kickstart.sh --stable-channel --disable-telemetry
```

Флаг `--disable-telemetry` отключает отправку анонимной статистики на серверы Netdata — хорошая практика для домашнего сервера.

После установки Netdata запускается автоматически как systemd-сервис:

```bash
systemctl status netdata
# Должно быть: active (running)
```

Открыть в браузере: `http://IP-КОНТЕЙНЕРА:19999`

### Что мониторить обязательно

Netdata показывает сотни метрик. Для начала важны пять:

**`disk_space./`** — место на системном диске. Когда диск заполнится выше 85-90%, начнутся проблемы: логи перестанут писаться, базы данных зависнут, контейнеры начнут падать. Настроить алерт на 85%.

**`mem.available`** — сколько RAM доступно прямо сейчас. Если постоянно меньше 10% от общего объёма — система начинает активно использовать своп, всё тормозит. Время добавить RAM или ограничить аппетиты контейнеров.

**`system.load`** — средняя нагрузка за 1, 5 и 15 минут. Нормальное значение — не выше числа ядер CPU. Если на 4-ядерном сервере `load average` стабильно держится на 6-8 — что-то работает слишком активно.

**`net.eth0`** — входящий и исходящий трафик. Резкий скачок исходящего трафика ночью — повод проверить что происходит.

**`disk.sda` (IOPS и пропускная способность)** — нагрузка на диск. Если диск постоянно на 100% — узкое место в производительности системы.

### Настройка алертов в Netdata

Netdata имеет встроенную систему алертов. По умолчанию алерты пишутся в системный лог. Чтобы получать уведомления в Telegram, нужно настроить `health_alarm_notify.conf`:

```bash
# Внутри LXC с Netdata
nano /etc/netdata/health_alarm_notify.conf
```

Найти секцию `TELEGRAM` и заполнить:

```bash
SEND_TELEGRAM="YES"
TELEGRAM_BOT_TOKEN="ваш_токен_бота"
TELEGRAM_CHAT_ID="ваш_chat_id"
```

После сохранения — перезапустить Netdata:

```bash
systemctl restart netdata
```

Теперь при срабатывании алерта (например диск > 85%) в Telegram придёт сообщение.

## 13.4 Диагностические команды

Быстро понять состояние системы помогают несколько команд. Стоит знать их наизусть — они нужны часто.

```bash
# Версия Proxmox и компонентов
pveversion
# Пример вывода:
# pve-manager/8.4.1 (running kernel: 6.8.12-7-pve)

# Список всех виртуальных машин
qm list
# VMID  NAME           STATUS  MEM(MB)  BOOTDISK(GB)  PID
# 200   home-assistant running 2048     64.00         12345

# Список всех LXC-контейнеров
pct list
# VMID  Status  Lock  Name
# 100   running       docker-01
# 101   running       nginx-pm
# 102   running       adguard

# Состояние всех хранилищ
pvesm status
# Name          Type     Status  Total(GB)  Used(GB)  Avail(GB)  %
# local         dir      active    95.00      15.00     80.00    16%
# local-lvm     lvmthin  active   400.00     120.00    280.00    30%

# Логи в реальном времени (Ctrl+C для выхода)
journalctl -f

# Логи конкретного контейнера
journalctl -u pve-container@100

# Общая нагрузка системы прямо сейчас
top
# или более удобный вариант:
htop

# Использование памяти по контейнерам
for ct in $(pct list | awk 'NR>1 {print $1}'); do
  MEM=$(pct exec $ct -- free -m 2>/dev/null | awk '/Mem:/ {print $3"/"$2"MB"}')
  echo "CT $ct: $MEM"
done
```

**`pveversion`** — первое что нужно сообщить при любом вопросе на форуме Proxmox. Показывает не только версию менеджера, но и версию запущенного ядра.

**`pvesm status`** — быстрая проверка хранилищ. Если хранилище offline — контейнеры на нём не запустятся. Первый шаг при диагностике «контейнер не стартует».

**`journalctl -f`** — поток логов в реальном времени. Удобно смотреть что происходит прямо сейчас, пока выполняешь действия в другом окне.

## 13.5 Мажорные обновления Proxmox (7→8, 8→9)

Раз в 1-2 года выходит новая мажорная версия Proxmox. Proxmox 8 базируется на Debian 12 Bookworm, Proxmox 9 — на Debian 13 Trixie. Это не просто `apt upgrade` — меняется базовая ОС, ядро, версии библиотек.

**Отличие мажорного обновления от обычного:**

```
Обычное обновление (8.1 → 8.4):
  apt update && apt full-upgrade -y
  → безопасно, делать регулярно

Мажорное обновление (7 → 8, 8 → 9):
  → меняется Debian base (bullseye → bookworm → trixie)
  → нужна специальная подготовка
  → есть официальный upgrade guide
  → риск несовместимости пакетов
```

### Подготовка к мажорному обновлению

Перед мажорным обновлением — обязательно выполнить все шаги ниже. Пропуск любого из них увеличивает риск неудачи.

**Шаг 1. Заморозить текущее ядро**

Пока идёт подготовка, не хочется чтобы apt случайно обновил ядро до промежуточной версии:

```bash
# Узнать имя текущего пакета ядра
dpkg -l | grep $(uname -r) | awk '{print $2}'
# Пример: pve-kernel-6.8.12-7-pve

# Заморозить — apt не будет его обновлять
apt-mark hold pve-kernel-$(uname -r | sed 's/-pve//')-pve

# Проверить что заморозка применилась
apt-mark showhold
```

**Шаг 2. Сделать снапшоты всех VM и LXC**

Если что-то пойдёт не так — можно будет откатиться. Снапшоты делаются на работающих машинах, остановка не нужна:

```bash
# Снапшоты всех VM
for vmid in $(qm list | awk 'NR>1 {print $1}'); do
  echo "Снапшот VM $vmid..."
  qm snapshot $vmid pre-upgrade --description "Before PVE upgrade $(date +%Y-%m-%d)"
done

# Снапшоты всех LXC
for ctid in $(pct list | awk 'NR>1 {print $1}'); do
  echo "Снапшот LXC $ctid..."
  pct snapshot $ctid pre-upgrade --description "Before PVE upgrade $(date +%Y-%m-%d)"
done

echo "Снапшоты готовы."
```

**Шаг 3. Сделать полные бэкапы (опционально, но рекомендуется)**

Снапшот хранится на том же диске. Если диск умрёт — снапшот пропадёт вместе с данными. Для критичных сервисов перед мажорным обновлением — сделать и полный бэкап на другое хранилище:

```bash
# Бэкап всех контейнеров на backup-хранилище
vzdump --all --compress zstd --storage backup-hdd --mode snapshot
```

**Шаг 4. Следовать официальному upgrade guide**

У Proxmox есть официальная документация для каждого мажорного обновления. Это не маркетинговый текст — там конкретные команды, известные проблемы и как их избежать.

```
Proxmox 7 → 8:
https://pve.proxmox.com/wiki/Upgrade_from_7_to_8

Proxmox 8 → 9:
https://pve.proxmox.com/wiki/Upgrade_from_8_to_9
```

Прочитать полностью перед началом. Особенно раздел «Known Issues».

Proxmox предоставляет утилиту предварительной проверки, которая сама укажет на проблемы:

```bash
# Установить утилиту проверки готовности к обновлению
apt install pve-upgrade-checker

# Запустить проверку
pve8to9   # или pve7to8 для обновления 7→8
```

Утилита проверит: репозитории, сторонние пакеты, конфигурацию сети, настройки хранилищ — и выдаст список проблем которые нужно решить до обновления.

**Шаг 5. Разморозить ядро после успешного обновления**

```bash
apt-mark unhold pve-kernel-*
```

### Если мажорное обновление сломалось

При неудаче — не паниковать. Есть несколько вариантов.

**Вариант 1: Загрузиться с предыдущим ядром**

Если сервер не загружается после обновления ядра:
1. При старте нажать `Esc` или `Shift` — появится меню GRUB.
2. Выбрать `Advanced Options for Proxmox VE`.
3. Выбрать предыдущую версию ядра.
4. После загрузки — разобраться в чём проблема.

**Вариант 2: Откатить через снапшот**

Если обновление применилось, но что-то работает неправильно:

```bash
# Откатить конкретный LXC
pct rollback 100 pre-upgrade

# Откатить VM
qm rollback 200 pre-upgrade
```

**Вариант 3: Восстановить из бэкапа**

Если снапшота нет или хост полностью сломан — переустановить Proxmox с нуля и восстановить контейнеры из бэкапов:

```bash
pct restore 100 /mnt/backup-hdd/dump/vzdump-lxc-100-*.tar.zst --storage local-lvm
```

## 13.6 Расписание обслуживания: рекомендуемый ритм

Хороший ритм обслуживания для домашнего сервера:

| Периодичность | Задача |
|--------------|--------|
| Еженедельно | `apt update && apt full-upgrade -y` на хосте |
| Еженедельно | Проверить лог обновления LXC `/var/log/lxc-updates.log` |
| Ежемесячно | Проверить дашборд Netdata — тренды дискового места и RAM |
| Ежемесячно | Тестовое восстановление одного контейнера из бэкапа |
| Ежемесячно | `pvesm status` — убедиться что все хранилища online |
| По мере выхода | Мажорное обновление — по официальному guide |

Тестовое восстановление раз в месяц — не паранойя, а единственный способ убедиться что бэкапы работают. Бэкап, который ни разу не тестировался — это не бэкап, это файл непонятного содержимого.

## 13.7 Практика

**Задание 1.** Обновите хост Proxmox:
```bash
apt update && apt full-upgrade -y
pveam update
```

Проверьте командой `pveversion` какая версия установлена сейчас.

**Задание 2.** Запустите скрипт обновления всех LXC вручную:
```bash
for ct in $(pct list | awk 'NR>1 {print $1}'); do
  STATUS=$(pct status $ct | awk '{print $2}')
  [ "$STATUS" = "running" ] && echo "=== CT $ct ===" && \
    pct exec $ct -- bash -c "apt update && apt upgrade -y" 2>/dev/null || true
done
```

Добавьте его в cron на еженедельный запуск.

**Задание 3.** Установите Netdata через Community Scripts или вручную. Откройте дашборд и найдите:
- текущую загрузку CPU;
- сколько RAM доступно;
- какой процент диска занят.

**Задание 4.** Выполните диагностические команды и запишите результаты:
```bash
pveversion
pct list
pvesm status
```
