# Глава 18: Обслуживание и диагностика

> **Что вы узнаете:**
> - Как находить и решать типичные проблемы: кончилось место, CPU 100%, контейнер не стартует.
> - Как добавить новый физический диск к работающему серверу без остановки сервисов.
> - Как реагировать на умирающий диск — прежде чем он умер окончательно.
> - Как диагностировать зависшую VM и потерянный доступ к веб-интерфейсу.

---

Сервер работает месяцами. Nextcloud загружает файлы, Jellyfin транскодирует видео, Home Assistant собирает данные с датчиков. Потом что-то ломается. Диск заполняется. Контейнер перестаёт стартовать. VM зависает и не реагирует на команды.

В этой главе разбираем семь реальных сценариев из жизни. Каждый — по схеме: что случилось, как выглядит симптом, как поставить диагноз, как починить, как не допустить повторения.

## 18.1 Сценарий: кончилось место — Nextcloud пишет ошибки

### Ситуация

Утром открываешь Nextcloud, пытаешься загрузить файл. В ответ — ошибка. Никаких подробностей — просто «что-то пошло не так».

### Симптом

```
Error while copying file to target location (copied bytes: 0, expected filesize: 10485760)
```

Или тихо: файл «загружается», прогресс-бар доходит до 100%, но файл не появляется. Nextcloud показывает уведомление с красным кружком, но без текста ошибки.

### Диагностика

Первым делом — смотришь сколько места осталось на хосте и внутри контейнера.

```bash
# На хосте Proxmox: общая картина по всем точкам монтирования
df -h
```

Пример вывода когда место кончилось:

```
Filesystem                   Size  Used Avail Use% Mounted on
/dev/pve/root                 28G   27G  0.6G  98% /
/dev/mapper/pve-data-tpool    80G   78G  1.4G  98% /var/lib/pve/local-lvm
```

Если `Use%` больше 90% — вот твоя проблема.

```bash
# Найти где именно съедено место — топ-20 крупных директорий на хосте
du -sh /* 2>/dev/null | sort -rh | head -20
```

```bash
# Войти в контейнер Nextcloud и проверить там
pct exec 100 -- df -h

# Если в контейнере Docker — смотреть место в Docker
pct exec 100 -- du -sh /var/lib/docker/* | sort -rh | head -10
```

```bash
# Проверить состояние хранилищ Proxmox
pvesm status
```

Пример вывода `pvesm status`:

```
Name             Type     Status           Total            Used       Available        %
local            dir      active        28626532         9823456      17321740     34.31%
local-lvm        lvmthin  active        83886080        79691776       4194304     94.99%
```

Если `local-lvm` занят на 95% — расширять нужно именно его.

### Решение А: убрать мусор Docker

Самый быстрый способ вернуть место — почистить Docker внутри LXC-контейнера. Docker накапливает слои образов от старых версий, остановленные контейнеры, неиспользуемые тома.

```bash
# Войти в LXC с Docker
pct exec 100 -- bash

# Внутри LXC — показать сколько занимает Docker (образы, контейнеры, тома, кэш)
docker system df

# Удалить всё неиспользуемое: остановленные контейнеры, образы без тегов,
# неподключённые тома, кэш сборки. Флаг -a удаляет и образы без контейнеров.
docker system prune -a --volumes
```

После `docker system prune -a --volumes` легко освобождается 5-15 GB — зависит от того, сколько раз обновлялись образы.

```bash
# Также урезать логи systemd — они растут незаметно
journalctl --vacuum-size=100M
```

Эта команда оставит только 100 MB журналов systemd, удалив всё старше. Безопасно — логи за последние часы останутся.

### Решение Б: расширить диск LXC

Если мусор убран, а места всё равно не хватает — расширяем диск контейнера. Не нужно останавливать контейнер: Proxmox умеет расширять диск LXC на лету.

```bash
# Расширить корневой диск контейнера 100 на 20 GB
# Proxmox сам расширит файловую систему внутри
pct resize 100 rootfs +20G
```

Проверить что расширение прошло:

```bash
pct exec 100 -- df -h /
```

Если файловая система не расширилась автоматически (редко, но бывает на старых шаблонах):

```bash
pct exec 100 -- resize2fs /dev/sda
```

### Профилактика

Мониторинг дисков нужно настраивать до того как место кончится, а не после. Скрипт проверки из Главы 19 (`pve-diskcheck`) шлёт уведомление в Telegram когда диск занят больше 85%.

Правило для медиасервера: медиафайлы Jellyfin хранить на HDD, а не на SSD где живут контейнеры. SSD — для системы и баз данных, HDD — для объёмных данных.

## 18.2 Сценарий: добавить новый физический диск

### Ситуация

Купил HDD 2 TB. Хочешь подключить к Proxmox — либо как хранилище для бэкапов, либо как дополнительный LVM-Thin для VM и LXC.

### Симптом

Нового хранилища нет в интерфейсе — его нужно добавить вручную.

### Диагностика

Сначала убедиться что диск виден системе:

```bash
# Показать все блочные устройства: диски и разделы
lsblk
```

Пример вывода после подключения нового диска:

```
NAME                         MAJ:MIN RM   SIZE RO TYPE MOUNTPOINTS
sda                            8:0    0 476.9G  0 disk
├─sda1                         8:1    0  1007K  0 part
├─sda2                         8:2    0     1G  0 part /boot/efi
└─sda3                         8:3    0 475.9G  0 part
  ├─pve-swap                 253:0    0     8G  0 lvm  [SWAP]
  ├─pve-root                 253:1    0    28G  0 lvm  /
  └─pve-data-tpool           253:4    0 431.1G  0 lvm
sdb                            8:16   0   1.8T  0 disk
```

Здесь `sdb` — новый диск, без разделов.

### Решение А: добавить как LVM-Thin (для VM и LXC)

LVM-Thin подходит когда новый диск будет использоваться для размещения виртуальных машин и контейнеров — с поддержкой снапшотов.

```bash
# Создать таблицу разделов GPT на новом диске
# GPT — современный стандарт, поддерживает диски больше 2 TB
parted /dev/sdb mklabel gpt

# Создать один раздел на весь диск (0% до 100%)
parted /dev/sdb mkpart primary 0% 100%
```

После создания раздела диск станет `/dev/sdb1`. Теперь настраиваем LVM:

```bash
# Инициализировать раздел как Physical Volume LVM
pvcreate /dev/sdb1

# Создать Volume Group с именем data-hdd
vgcreate data-hdd /dev/sdb1

# Создать Thin Pool на весь объём VG
# Thin Pool — это пул для thin-provisioning: место выделяется по мере использования
lvcreate -l 100%FREE --thinpool data-pool data-hdd
```

Теперь добавить новое хранилище в Proxmox:

```
Datacenter → Storage → Add → LVM-Thin
  Volume group: data-hdd
  Thin pool:    data-pool
  ID:           data-hdd
  Content:      Disk image, Container
```

После добавления в веб-интерфейсе хранилище `data-hdd` появится в списке при создании LXC и VM.

### Решение Б: добавить как Directory (для бэкапов)

Directory-тип проще и подходит для хранения файлов бэкапов. Снапшоты VM не поддерживаются, но бэкапы через vzdump работают отлично.

```bash
# Создать раздел (если нужен) — или использовать диск напрямую
parted /dev/sdb mklabel gpt
parted /dev/sdb mkpart primary 0% 100%

# Отформатировать в ext4
mkfs.ext4 /dev/sdb1

# Создать точку монтирования
mkdir /mnt/backup-hdd

# Добавить в fstab для автоматического монтирования при загрузке
echo "/dev/sdb1 /mnt/backup-hdd ext4 defaults 0 2" >> /etc/fstab

# Смонтировать сейчас без перезагрузки
mount -a
```

Проверить что смонтировалось:

```bash
df -h /mnt/backup-hdd
```

Добавить в Proxmox:

```
Datacenter → Storage → Add → Directory
  Directory: /mnt/backup-hdd
  ID:        backup-hdd
  Content:   VZDump backup file, ISO image, CT Templates
```

## 18.3 Сценарий: контейнер не запускается

### Ситуация

После перезагрузки сервера или вручную пытаешься запустить LXC-контейнер — он не стартует. Веб-интерфейс показывает статус `stopped`, кнопка Start не помогает.

### Симптом

В Tasks появляется красная строка. При нажатии — краткое сообщение об ошибке без деталей.

### Диагностика

Запускаем контейнер вручную из Shell хоста — видим реальную ошибку:

```bash
# Запустить контейнер 100 — вывод покажет ошибку если она есть
pct start 100
```

Смотрим журнал сервиса контейнера:

```bash
# Полный лог запуска контейнера — здесь будет причина
journalctl -u pve-container@100 --no-pager | tail -30
```

Проверяем конфигурационный файл контейнера:

```bash
# Конфиг LXC хранится здесь — синтаксическая ошибка не даст запуститься
cat /etc/pve/lxc/100.conf
```

Проверяем доступность хранилищ:

```bash
# Если хранилище offline — контейнер не запустится
pvesm status
```

### Таблица причин и решений

| Симптом в логе | Причина | Решение |
|---|---|---|
| `storage 'local-lvm' is not online` | Хранилище недоступно | Проверить `pvesm status`, перемонтировать или перезагрузить |
| `No space left on device` | Нет места | Очистить место (см. 18.1), расширить диск |
| `parse error in config` | Синтаксическая ошибка в `.conf` | Открыть `/etc/pve/lxc/100.conf`, найти и исправить строку |
| `veth100i0 already exists` | Старый сетевой интерфейс не удалился | `ip link delete veth100i0` |
| `rootfs: storage 'data-hdd' not found` | Хранилище удалено или переименовано | Восстановить хранилище или исправить путь в конфиге |
| `mountpoint ... contains subvolumes` | Старый снапшот не был удалён | `pct listsnapshot 100`, удалить лишние снапшоты |

### Решение для случая с зависшим veth-интерфейсом

Иногда после некорректной остановки виртуальный сетевой интерфейс контейнера остаётся в системе:

```bash
# Показать все сетевые интерфейсы — искать veth100i0 или похожие
ip link show | grep veth

# Удалить зависший интерфейс
ip link delete veth100i0

# Теперь можно запускать
pct start 100
```

### Профилактика

Перед любыми экспериментами с конфигурацией — делать снапшот:

```bash
pct snapshot 100 before-config-change --description "Before manual edit $(date +%Y-%m-%d)"
```

Если что-то сломалось — откатиться одной командой:

```bash
pct rollback 100 before-config-change
```

## 18.4 Сценарий: VM зависла и не реагирует

### Ситуация

Виртуальная машина с Ubuntu Server или Windows перестала отвечать. Ping не проходит. Консоль Proxmox открывается, но экран завис. Кнопка `Shutdown` в веб-интерфейсе не даёт результата — машина не выключается.

### Симптом

`qm status 200` показывает `running`, но ping до IP машины не идёт. В консоли браузера — чёрный экран или замороженный вывод.

### Диагностика

```bash
# Проверить статус VM
qm status 200

# Посмотреть лог QEMU процесса (может содержать панику ядра)
cat /var/log/qemu-server/200.log | tail -30
```

### Решение — последовательность действий

Начинаем с мягкого и доходим до жёсткого если нужно.

**Шаг 1: Мягкое выключение через guest agent.**
Это корректный способ — гостевая ОС получает сигнал и завершает работу штатно:

```bash
# Отправить команду shutdown через qemu-guest-agent
# Работает только если агент установлен и отвечает
qm guest cmd 200 shutdown
```

Подождать 30 секунд. Если VM не выключилась — переходить дальше.

**Шаг 2: Жёсткий сброс (аналог кнопки Reset на корпусе).**
VM получит сигнал перезагрузки без штатного завершения. Данные могут быть не сохранены:

```bash
qm reset 200
```

**Шаг 3: Принудительная остановка.**
Если Reset не помогает — принудительно остановить процесс QEMU. Флаг `--skiplock` нужен когда VM заблокирована незавершённой операцией (снапшот, миграция):

```bash
qm stop 200 --skiplock
```

**Шаг 4: Запустить заново.**

```bash
qm start 200
```

### Что делать если VM зависает регулярно

Регулярные зависания — признак проблемы, а не норма. Проверить:

```bash
# Посмотреть системные ошибки хоста — OOM, hardware error, disk error
dmesg | grep -E "error|oom|killed|hardware" | tail -20

# Проверить SMART состояние дисков (см. 18.7)
smartctl -H /dev/sda
```

Если в `dmesg` есть `hardware error` или `uncorrectable sector` — это признак умирающего диска. Срочно делать бэкап (см. 18.7).

### Профилактика

Установка `qemu-guest-agent` внутри каждой VM — обязательна. Без агента Proxmox не может корректно выключить VM по расписанию, агент также нужен для корректных снапшотов.

```bash
# Внутри Linux VM
apt install qemu-guest-agent
systemctl enable --now qemu-guest-agent
```

## 18.5 Сценарий: потерял доступ к веб-интерфейсу

### Ситуация

Открываешь `https://192.168.1.100:8006` — браузер не открывает страницу. Или открывает, но пароль не принимается. Или произошло что-то после обновления и интерфейс перестал работать.

### Симптом

`ERR_CONNECTION_REFUSED` или `ERR_CONNECTION_TIMED_OUT` при открытии `https://IP:8006`.

### Диагностика

Сначала — жив ли сервер вообще?

```bash
# С другого устройства в той же сети: проверить что хост отвечает
ping 192.168.1.100
```

Если ping не проходит — проблема не в Proxmox, а в сети или питании. Надо физически подойти к серверу.

Если ping работает — проверить открыт ли порт 8006:

```bash
# С другого Linux/Mac — проверить что порт слушает
nmap -p 8006,22 192.168.1.100
```

Пример вывода когда pveproxy упал:

```
PORT     STATE  SERVICE
22/tcp   open   ssh
8006/tcp closed unknown
```

Порт 22 открыт — SSH работает. Порт 8006 закрыт — pveproxy не работает.

### Решение

Подключиться по SSH (если порт 22 открыт) или физически через клавиатуру и монитор:

```bash
# Проверить статус pveproxy — веб-сервер Proxmox
systemctl status pveproxy
```

Если сервис упал:

```bash
# Перезапустить веб-сервис Proxmox
systemctl restart pveproxy
```

Проверить нет ли ошибок в журнале:

```bash
journalctl -u pveproxy --no-pager | tail -20
```

Типичная ошибка после обновления — SSL сертификат:

```
SSL certificate problem: self-signed certificate
```

Пересоздать самоподписанный сертификат:

```bash
pvecm updatecerts --force
systemctl restart pveproxy
```

Если веб-интерфейс открывается, но пароль не принимается — сбросить пароль root:

```bash
# Прямо на хосте или через SSH
passwd root
```

### Профилактика

Два правила которые спасают когда всё остальное не работает:

**Правило 1: статический IP.** Если IP сервера назначается по DHCP, после перезагрузки роутера он может измениться. Статический IP в `/etc/network/interfaces` исключает эту проблему.

**Правило 2: Tailscale как резервный канал.** Tailscale работает независимо от локальной сети. Даже если vmbr0 сломан и локальный доступ потерян — через Tailscale IP всё равно можно подключиться к хосту по SSH и починить.

```bash
# Проверить что Tailscale активен на хосте
tailscale status
```

## 18.6 Сценарий: CPU 100% — кто виноват?

### Ситуация

Все сервисы начали тормозить одновременно. Nextcloud грузит страницы по 10 секунд. Jellyfin не воспроизводит видео. В веб-интерфейсе Proxmox видно что CPU хоста загружен на 95-100%.

### Симптом

В Summary хоста Proxmox столбик CPU упирается в максимум и не снижается.

### Диагностика

Смотрим что именно жрёт CPU:

```bash
# На хосте Proxmox — показать все процессы с сортировкой по CPU
htop
```

В `htop` видно — если нагрузку создаёт `kvm` или `lxc-start` процесс с ID контейнера — это VM или LXC. Нажать `F5` для tree-вида чтобы видеть к какому контейнеру принадлежит процесс.

Если виновный LXC определён — смотрим что происходит внутри него:

```bash
# Показать топ процессов внутри LXC-контейнера 100
# -bn1: batch mode, одна итерация (не интерактивный режим)
pct exec 100 -- top -bn1 | head -25
```

Пример вывода когда Nextcloud сканирует файлы:

```
PID    USER      PR  NI    VIRT    RES    SHR S  %CPU  %MEM
1234   www-data  20   0  456m   89m   22m R  98.3   5.5  nextcloud cron
```

Процесс `nextcloud cron` съедает почти всё CPU — вероятно, индексирование файлов после большой загрузки.

```bash
# Также можно смотреть в веб-интерфейсе: каждый CT/VM показывает свой % CPU
# Node → Summary → CPU график показывает историю нагрузки
```

### Решение А: подождать

Nextcloud-сканирование, rebuild индексов, обновление плагинов — всё это временная нагрузка. Если процесс выглядит осмысленным — подождать завершения.

### Решение Б: ограничить виновный контейнер

Если нагрузка не заканчивается или мешает другим сервисам — снизить приоритет CPU виновного контейнера:

```bash
# Снизить CPU-приоритет контейнера 100
# cpuunits: относительный вес, по умолчанию 1024
# Снижение до 256 — контейнер получит в 4 раза меньше CPU времени при конкуренции
pct set 100 -cpuunits 256
```

Это не жёсткое ограничение. Когда остальные контейнеры не нагружены — контейнер 100 всё равно может использовать 100% CPU. Снижение приоритета влияет только при конкуренции — когда CPU нужен сразу нескольким контейнерам.

Для жёсткого ограничения — установить максимум CPU:

```bash
# Ограничить LXC 100 максимумом в 1 ядро (100% одного ядра)
# cpulimit: количество ядер * 100
pct set 100 -cpulimit 1
```

Когда нагрузка спадёт — вернуть значения по умолчанию:

```bash
pct set 100 -cpuunits 1024
pct set 100 -cpulimit 0   # 0 = без ограничения
```

### Решение В: убить процесс внутри контейнера

Если конкретный процесс завис и не завершается:

```bash
# Найти PID процесса внутри контейнера
pct exec 100 -- pgrep -a php

# Отправить SIGTERM (мягкое завершение)
pct exec 100 -- kill 1234

# Если не помогло — SIGKILL (принудительно)
pct exec 100 -- kill -9 1234
```

### Профилактика

Настроить в Nextcloud расписание cron через системный cron (а не веб-cron) — это распределяет нагрузку по времени, а не создаёт пик при первом же запросе.

Netdata (см. Главу 13) отлично показывает историческую нагрузку CPU по контейнерам — можно видеть когда и что нагрузило систему.

## 18.7 Сценарий: диск умирает — SMART предупреждения

### Ситуация

В логах хоста появились ошибки I/O. Или Proxmox прислал email с предупреждением. Или система стала работать нестабильно без очевидной причины. Диск может умереть — и нужно это выяснить до того как данные потеряны.

### Симптом

В `dmesg` есть строки вида:

```
ata1.00: end_request: I/O error, dev sda, sector 1234567890
ata1.00: status: { DRDY ERR }
ata1.00: error: { UNC }
```

`UNC` — Uncorrectable Error — данные в этом секторе повреждены и не могут быть прочитаны.

### Диагностика

Установить `smartmontools` если ещё не установлен:

```bash
apt install smartmontools -y
```

Быстрая проверка здоровья диска:

```bash
# Краткий вердикт: PASSED или FAILED
# PASSED — диск здоров по самодиагностике
# FAILED — срочно делать бэкап
smartctl -H /dev/sda
```

Пример вывода для здорового диска:

```
=== START OF READ SMART DATA SECTION ===
SMART overall-health self-assessment test result: PASSED
```

Пример вывода для умирающего диска:

```
SMART overall-health self-assessment test result: FAILED!
Drive failure expected in less than 24 hours. SAVE ALL DATA.
```

Полный отчёт со всеми атрибутами:

```bash
smartctl -a /dev/sda
```

Критичные атрибуты на которые смотреть. Если значение в колонке `VALUE` отличается от `WORST` или `THRESH` — плохо. Если `RAW_VALUE` ненулевое у этих атрибутов — очень плохо:

| Атрибут | Что означает | Опасное значение |
|---|---|---|
| `Reallocated_Sector_Ct` | Перераспределённые секторы | > 0 |
| `Current_Pending_Sector` | Секторы ожидающие перераспределения | > 0 |
| `Offline_Uncorrectable` | Неисправимые ошибки при offline-тесте | > 0 |
| `Reported_Uncorrect` | Ошибки чтения которые нельзя исправить | > 0 |

Посмотреть только критичные атрибуты:

```bash
smartctl -a /dev/sda | grep -E "Reallocated|Pending|Uncorrectable|Uncorrect"
```

### Решение: немедленный экстренный бэкап

Если диск показывает `FAILED` или ненулевые значения критичных атрибутов — **первое действие — бэкап**. Не перезагрузка, не диагностика — бэкап.

```bash
# Экстренный бэкап всего на другое хранилище
# --all: все VM и LXC
# --compress zstd: эффективное сжатие
# --storage backup-hdd: хранилище на другом физическом диске
# --mode snapshot: бэкап без остановки контейнеров
vzdump --all --compress zstd --storage backup-hdd --mode snapshot
```

Если хранилище `backup-hdd` на том же физическом диске — скопировать на внешний носитель:

```bash
# Скопировать бэкапы на удалённый сервер или NAS
rsync -avP /mnt/backup-hdd/dump/ user@remote-server:/backup/proxmox/
```

После того как бэкап сделан — заказывать новый диск. Работать с умирающим диском дольше — риск потери данных.

### Автоматический мониторинг SMART

Настроить `smartd` — он будет автоматически проверять диски и присылать уведомления:

```bash
# Настроить smartd для мониторинга двух дисков
cat > /etc/smartd.conf << 'EOF'
# -a: мониторить все атрибуты
# -o on: включить автоматические online-тесты
# -S on: автоматически сохранять атрибуты
# -s: расписание коротких (S) и длинных (L) тестов
# -m root: слать уведомления root
/dev/sda -a -o on -S on -s (S/../.././02|L/../../6/03) -m root -M exec /usr/share/smartmontools/smartd-runner
/dev/sdb -a -o on -S on -s (S/../.././02|L/../../6/03) -m root -M exec /usr/share/smartmontools/smartd-runner
EOF

systemctl enable --now smartd
```

Расписание тестов в строке `-s (S/../.././02|L/../../6/03)`:
- `S/../.././02` — короткий тест каждый день в 02:00
- `L/../../6/03` — длинный тест каждую субботу в 03:00

Длинный тест занимает 30-120 минут в зависимости от размера диска, но не мешает работе системы.

### Настройка уведомлений для smartd через Telegram

По умолчанию smartd шлёт письмо на `root`. Перенаправить в Telegram:

```bash
cat > /usr/local/bin/smartd-telegram << 'EOF'
#!/bin/bash
# Этот скрипт вызывается smartd при обнаружении проблемы
TOKEN="ваш_токен_бота"
CHAT_ID="ваш_chat_id"
MESSAGE="⚠️ SMART Alert на $(hostname): $SMARTD_MESSAGE (диск: $SMARTD_DEVICE)"
curl -s "https://api.telegram.org/bot${TOKEN}/sendMessage" \
  -d "chat_id=${CHAT_ID}" \
  -d "text=${MESSAGE}" > /dev/null
EOF
chmod +x /usr/local/bin/smartd-telegram
```

В `/etc/smartd.conf` заменить `-M exec /usr/share/smartmontools/smartd-runner` на `-M exec /usr/local/bin/smartd-telegram`.

### Профилактика

Проверять SMART всех дисков раз в месяц вручную — выработать привычку:

```bash
# Быстрый осмотр всех дисков
for disk in $(lsblk -dno NAME | grep -v loop); do
  echo "=== /dev/$disk ==="
  smartctl -H /dev/$disk 2>/dev/null || echo "SMART не поддерживается"
done
```

Правило резервирования: данные которых нет в трёх местах — данных нет. Диск Proxmox + бэкап на HDD + бэкап offsite (облако, удалённый сервер).

## Практика

Чтобы отработать навыки диагностики, выполни следующие упражнения:

**Упражнение 1 — симуляция нехватки места:**
```bash
# Создать большой файл внутри тестового LXC чтобы заполнить диск
pct exec 100 -- dd if=/dev/zero of=/tmp/bigfile bs=1M count=500
# Посмотреть df, найти проблему, удалить файл, проверить снова
pct exec 100 -- df -h /
pct exec 100 -- rm /tmp/bigfile
```

**Упражнение 2 — проверка дисков:**
```bash
smartctl -H /dev/sda
smartctl -a /dev/sda | grep -E "Reallocated|Pending|Uncorrectable"
```

**Упражнение 3 — экстренный бэкап:**
Создать тестовый LXC, сделать полный бэкап командой `vzdump`, убедиться что файл бэкапа появился в хранилище.

## Чек-лист для самопроверки

- [ ] Умею найти что занимает место на хосте и внутри LXC: `df -h`, `du -sh`, `pvesm status`
- [ ] Умею расширить диск LXC командой `pct resize 100 rootfs +10G` без остановки контейнера
- [ ] Умею добавить новый физический диск как LVM-Thin или Directory хранилище
- [ ] Знаю последовательность действий при зависшей VM: `qm guest cmd shutdown` → `qm reset` → `qm stop --skiplock`
- [ ] Умею перезапустить веб-интерфейс Proxmox: `systemctl restart pveproxy`
- [ ] Умею найти виновника нагрузки CPU: `htop` на хосте и `pct exec -- top` внутри контейнера
- [ ] Умею снизить приоритет контейнера: `pct set 100 -cpuunits 256`
- [ ] Установил `smartmontools` и проверил SMART-статус всех дисков
- [ ] Настроил автоматический `smartd` мониторинг с уведомлениями
- [ ] Знаю как запустить экстренный бэкап всего: `vzdump --all --compress zstd --storage backup-hdd`
