# Глава 16: Миграция с Ubuntu на Proxmox

> **Цель:** перенести работающий сервер с Ubuntu + Docker на Proxmox без потери данных и с минимальным простоем сервисов.

---

**Что вы узнаете:**
- два принципиально разных подхода к миграции — какой выбрать в вашей ситуации;
- как перенести Docker-стек целиком: от архивирования данных до первого запуска на новом месте;
- какие ловушки ждут почти каждого при переносе (IP, пути, переменные окружения);
- как составить чеклист миграции одного сервиса — чтобы ничего не забыть.

---

## 16.1 Два подхода к миграции

Прежде чем что-то делать — нужно решить, каким путём идти. Это зависит от того, есть ли у вас возможность работать параллельно со старым сервером.

### Подход 1: Новый сервер (рекомендуется)

Вы устанавливаете Proxmox на отдельное железо, параллельно переносите сервисы один за другим, проверяете работу и только потом выключаете старый сервер.

```
Старый сервер (Ubuntu)           Новый сервер (Proxmox)
[Nextcloud]  [Jellyfin]    →     [LXC: Nextcloud]
[Vaultwarden] [Gitea]      →     [LXC: Vaultwarden]
всё работает, пока переносишь    после проверки — отключаешь Ubuntu
```

Преимущества:
- Нет простоя. Старый сервер работает пока вы настраиваете новый.
- Можно сравнить поведение обеих систем.
- Если что-то пошло не так — всегда есть откат на старую систему.
- Переносите по одному сервису, а не всё сразу.

Подходит, если: есть запасное железо (старый ПК, мини-ПК, сервер), и сервисы используются регулярно — нельзя позволить себе долгий простой.

### Подход 2: Переустановка на том же железе

Вы создаёте резервные копии данных, устанавливаете Proxmox на то же железо вместо Ubuntu, потом восстанавливаете сервисы в LXC из бэкапа.

```
1. Бэкап данных (не Ubuntu, а сами данные сервисов)
2. Proxmox на то же железо (Ubuntu стирается)
3. Создать LXC, восстановить данные, запустить сервисы
```

Преимущества:
- Не нужно дополнительное железо.
- Чистая установка — никакого накопленного мусора Ubuntu.

Недостатки:
- Сервисы не работают во время установки и настройки (несколько часов простоя).
- Нет возможности откатиться на старую систему, если что-то пойдёт не так с данными.

Подходит, если: это домашний сервер без критичной непрерывности, или сервисы используются редко (торренты, архивное хранилище).

**Правило:** при малейшей возможности выбирайте Подход 1. Параллельная работа двух систем даёт спокойствие и время на проверку.

## 16.2 Что переносить: данные, а не Ubuntu

Типичная ошибка при первой миграции — попытка «перенести Ubuntu» целиком. Это неверный путь. Ubuntu не нужна на Proxmox. Переносятся только **данные сервисов**.

Что обычно хранит Docker-стек:
- Docker volumes — постоянные данные контейнеров (база данных, файлы пользователей).
- Конфигурационные файлы — `docker-compose.yml`, `.env`, папки `config/`, `data/`.
- Сертификаты, ключи, секреты (если хранятся локально, а не в Let's Encrypt).

Что переносить не нужно:
- Саму ОС Ubuntu.
- Docker-образы — они скачаются заново из registry.
- Логи (если не нужны).
- Временные файлы, кэш.

Главный принцип: если вы можете поднять сервис с нуля за `docker compose up -d`, то для миграции вам нужны только данные (volumes + `.env`).

## 16.3 Подготовка нового LXC под Docker

Прежде чем переносить данные — подготовьте место, куда переносить.

На Proxmox создайте LXC с Docker. Подробнее этот процесс описан в Главе 4, здесь напомним ключевые параметры.

Через Community Scripts (быстро):
```bash
# На хосте Proxmox — в Shell
# Создаёт LXC с Debian 12, Docker и Portainer автоматически
bash -c "$(curl -fsSL https://raw.githubusercontent.com/community-scripts/ProxmoxVE/main/ct/docker.sh)"
```

Или вручную. Создать privileged LXC с нужными параметрами:
```bash
# На хосте Proxmox — создаёт LXC с ID 110, 4GB RAM, 4 ядра, диск 30GB
pct create 110 local:vztmpl/debian-12-standard_12.7-1_amd64.tar.zst \
  --hostname docker-migrated \
  --memory 4096 \
  --cores 4 \
  --net0 name=eth0,bridge=vmbr0,ip=192.168.1.110/24,gw=192.168.1.1 \
  --storage local-lvm \
  --rootfs local-lvm:30 \
  --features keyctl=1,nesting=1 \
  --unprivileged 0

pct start 110
pct enter 110
```

Внутри LXC установить Docker:
```bash
# Официальный скрипт установки Docker
curl -fsSL https://get.docker.com | sh
systemctl enable --now docker

# Проверить
docker run hello-world
```

Дать LXC статический IP (а не DHCP) — важно, потому что IP этого контейнера войдёт в настройки DNS и Nginx Proxy Manager. Если IP поменяется после перезагрузки — всё сломается.

## 16.4 Перенос Docker-стека: пошаговый процесс

Рассмотрим перенос Nextcloud, но тот же алгоритм применим к любому сервису.

### Шаг 1: Остановить сервис на старом сервере

```bash
# На старом Ubuntu-сервере, в папке с docker-compose.yml
cd /opt/nextcloud
docker compose down
```

Почему останавливаем? Если переносить данные пока сервис работает — база данных может оказаться в несогласованном состоянии. Это особенно критично для PostgreSQL и MariaDB.

### Шаг 2: Создать архив данных

```bash
# На старом Ubuntu-сервере — архивируем всё что нужно сервису
# Эта команда упаковывает папки data/, config/ и файл .env в один архив
tar -czf nextcloud-migration.tar.gz \
  ./data \
  ./config \
  ./.env \
  ./docker-compose.yml

# Проверить что архив создался и не пустой
ls -lh nextcloud-migration.tar.gz
```

Если данные хранятся в именованных Docker volumes (а не в bind-mount папках), их нужно экспортировать иначе:
```bash
# Найти имена volumes
docker compose config --format json | grep -A5 volumes

# Экспортировать volume в архив
# Эта команда запускает временный контейнер Alpine, монтирует volume и пакует его
docker run --rm \
  -v nextcloud_data:/source \
  -v $(pwd):/backup \
  alpine tar -czf /backup/nextcloud-data-volume.tar.gz -C /source .
```

### Шаг 3: Скопировать архив на новый LXC

```bash
# На старом Ubuntu-сервере — копируем архив по SSH на новый LXC
# IP 192.168.1.110 — адрес нашего Docker LXC на Proxmox
scp nextcloud-migration.tar.gz root@192.168.1.110:/opt/
```

Если файл большой (несколько гигабайт медиафайлов) и копирование прерывается — используйте `rsync`:
```bash
# rsync продолжит с места прерывания, показывает прогресс
rsync -avzP nextcloud-migration.tar.gz root@192.168.1.110:/opt/
```

### Шаг 4: Распаковать и запустить на новом LXC

```bash
# Зайти в новый LXC (на хосте Proxmox)
pct enter 110

# Создать папку для сервиса и распаковать архив
mkdir -p /opt/nextcloud
cd /opt/nextcloud
tar -xzf /opt/nextcloud-migration.tar.gz

# Проверить что файлы распаковались
ls -la

# Запустить сервис
docker compose up -d

# Посмотреть что запустилось
docker compose ps
docker compose logs --tail=50
```

### Шаг 5: Проверить что всё работает

```bash
# Узнать на каком порту слушает сервис
docker compose ps

# Попробовать открыть в браузере
# Например: http://192.168.1.110:8080
```

Если сервис открывается и работает — миграция этого сервиса завершена.

## 16.5 Типичные ловушки при миграции

Почти каждый наступает на одни и те же грабли. Вот они — с объяснением почему так происходит и как исправить.

### Ловушка 1: IP-адрес изменился

**Что происходит:** на старом сервере IP был `192.168.1.50`, на новом LXC — `192.168.1.110`. Nextcloud хранит свой URL в базе данных — теперь ссылки в приложении ведут на старый адрес, и всё ломается.

**Симптом:** браузер редиректит на старый адрес, или HTTPS-сертификат выдаёт ошибку `ERR_CERT_COMMON_NAME_INVALID`.

**Решение — обновить адрес в конфиге Nextcloud:**
```bash
# Внутри LXC, выполнить occ через Docker
docker exec --user www-data nextcloud-aio-nextcloud php occ \
  config:system:set overwrite.cli.url --value="http://192.168.1.110:8080"
```

Для других сервисов: ищите в `.env` переменные типа `APP_URL`, `BASE_URL`, `SITE_URL`, `NEXTCLOUD_TRUSTED_DOMAINS` — и обновляйте там.

**Профилактика:** назначайте новому LXC тот же IP, что был у Ubuntu. Или сразу используйте DNS-имя вместо IP в конфигах.

### Ловушка 2: Пути к файлам другие

**Что происходит:** на Ubuntu данные лежали в `/home/user/nextcloud/data`, на новом LXC вы распаковали в `/opt/nextcloud/data`. Если в `docker-compose.yml` прописан абсолютный путь — сервис не найдёт файлы.

**Симптом:** контейнер стартует, но данных нет, или ошибки вида `file not found`, `permission denied`.

**Решение:** проверить `docker-compose.yml`, найти все `volumes:` с абсолютными путями и обновить:
```yaml
volumes:
  # Было на Ubuntu:
  - /home/user/nextcloud/data:/var/www/html/data

  # Стало на LXC:
  - /opt/nextcloud/data:/var/www/html/data
```

**Профилактика:** всегда используйте относительные пути в docker-compose.yml — `./data:/var/www/html/data`. Тогда путь привязан к папке с `docker-compose.yml`, а не к абсолютному пути в ОС.

### Ловушка 3: Переменные окружения в .env

**Что происходит:** `.env` файл содержит переменные для конкретного сервера. Некоторые из них указывают на старый IP или имя хоста.

**Симптом:** сервис запустился, но не может подключиться к базе данных или внешнему сервису — потому что указан старый адрес.

**Решение:** открыть `.env` и проверить каждую переменную:
```bash
# Посмотреть содержимое .env
cat .env

# Типичные переменные которые нужно проверить:
# DB_HOST=192.168.1.50    ← старый IP
# REDIS_HOST=192.168.1.50 ← старый IP
# APP_URL=http://192.168.1.50:8080  ← старый IP
# NEXTCLOUD_TRUSTED_DOMAINS=192.168.1.50  ← старый IP
```

Обновляйте IP везде, где он встречается в `.env`. Особое внимание — переменные для базы данных и Redis, если они запущены в отдельных контейнерах.

### Ловушка 4: Конфликты портов

**Что происходит:** если вы перенесли несколько сервисов в один LXC, два сервиса могут пытаться занять один и тот же порт (например, 80 или 443).

**Симптом:** `docker compose up -d` завершается с ошибкой `Bind for 0.0.0.0:80 failed: port is already allocated`.

**Решение:** посмотреть какие порты уже заняты и изменить порт конфликтующего сервиса:
```bash
# Какие порты слушают контейнеры
docker ps --format "table {{.Names}}\t{{.Ports}}"

# Какие порты слушает система вообще
ss -tlnp | grep LISTEN
```

Если несколько сервисов нужны на 80/443 — правильное решение не менять порты, а поставить Nginx Proxy Manager в отдельный LXC и проксировать через него (как описано в Главе 12).

### Ловушка 5: Права доступа к файлам (UID/GID)

**Что происходит:** в Docker-контейнере процессы работают от определённого пользователя (например UID 1000 или `www-data`). После переноса файлов через `tar` и `scp` права могут не совпасть.

**Симптом:** контейнер запустился, но не может читать или записывать файлы. Ошибки вида `Permission denied` в логах.

**Решение:** узнать от какого пользователя работает сервис в контейнере, и установить соответствующие права:
```bash
# Узнать UID процесса внутри контейнера
docker exec nextcloud-app id

# Исправить права на папку с данными
# Например, если процесс работает от www-data (UID 33)
chown -R 33:33 /opt/nextcloud/data
```

## 16.6 Чеклист миграции одного сервиса

Используйте этот чеклист для каждого сервиса, который переносите. Распечатайте или скопируйте в текстовый файл.

**Подготовка (на старом сервере):**
- [ ] Задокументировать текущий IP и порт сервиса
- [ ] Записать все переменные из `.env` которые содержат IP или hostname
- [ ] Проверить где хранятся данные: bind-mount папки или именованные volumes
- [ ] Сделать снапшот старого сервера (если поддерживается) или бэкап данных

**Перенос:**
- [ ] Остановить сервис командой `docker compose down`
- [ ] Создать архив: данные + конфиги + `.env` + `docker-compose.yml`
- [ ] Проверить размер архива — убедиться что данные попали внутрь
- [ ] Скопировать архив на новый LXC (`scp` или `rsync`)
- [ ] Распаковать архив в `/opt/<service-name>/`

**Настройка на новом LXC:**
- [ ] Обновить IP во всех местах: `.env`, конфиги приложения, `docker-compose.yml`
- [ ] Проверить пути в `volumes:` секции `docker-compose.yml` — они должны указывать на правильные папки
- [ ] Проверить порты — нет ли конфликта с другими сервисами
- [ ] Запустить: `docker compose up -d`
- [ ] Проверить логи: `docker compose logs --tail=100`

**Проверка:**
- [ ] Сервис открывается в браузере по новому IP
- [ ] Данные на месте (авторизоваться, проверить файлы/записи)
- [ ] Сервис работает корректно (отправить тестовое письмо, загрузить файл)
- [ ] Nginx Proxy Manager проксирует трафик на новый IP (если используется)
- [ ] DNS-запись обновлена (если домен указывал на старый IP)

**Финализация:**
- [ ] Обновить расписание бэкапов — добавить новый LXC
- [ ] Сделать первый бэкап нового LXC вручную и проверить что он создался
- [ ] Документировать: записать новый IP, порт, путь к данным

## 16.7 Пример: полный перенос стека Nextcloud + Vaultwarden

Посмотрим как выглядит реальный перенос двух сервисов.

**Ситуация:** на Ubuntu 22.04 (IP 192.168.1.50) запущены:
- Nextcloud на порту 8080
- Vaultwarden на порту 8081

Оба используют Docker, данные лежат в `/opt/nextcloud/` и `/opt/vaultwarden/`.

**На старом сервере Ubuntu:**
```bash
# Останавливаем оба сервиса
cd /opt/nextcloud && docker compose down
cd /opt/vaultwarden && docker compose down

# Архивируем
cd /opt
tar -czf nextcloud-migration.tar.gz nextcloud/
tar -czf vaultwarden-migration.tar.gz vaultwarden/

# Копируем на новый LXC (192.168.1.110)
scp nextcloud-migration.tar.gz root@192.168.1.110:/opt/
scp vaultwarden-migration.tar.gz root@192.168.1.110:/opt/
```

**На новом LXC (через pct enter 110 или SSH):**
```bash
cd /opt

# Распаковываем
tar -xzf nextcloud-migration.tar.gz
tar -xzf vaultwarden-migration.tar.gz

# В .env каждого сервиса меняем старый IP на новый
sed -i 's/192.168.1.50/192.168.1.110/g' nextcloud/.env
sed -i 's/192.168.1.50/192.168.1.110/g' vaultwarden/.env

# Запускаем
cd /opt/nextcloud && docker compose up -d
cd /opt/vaultwarden && docker compose up -d

# Проверяем
docker compose ps
docker compose logs --tail=30
```

**Проверяем в браузере:**
- `http://192.168.1.110:8080` — Nextcloud
- `http://192.168.1.110:8081` — Vaultwarden

Если всё открывается и данные на месте — старый сервер Ubuntu можно выключать.

## 16.8 Типичные ошибки

| Ошибка | Причина | Решение |
|--------|---------|---------|
| `Connection refused` при открытии сервиса | Контейнер не запустился или слушает другой порт | `docker compose ps`, проверить PORT в `.env` |
| `Invalid trusted domain` в Nextcloud | Новый IP не добавлен в trusted_domains | Добавить IP в `config.php` или через `occ config:system:set` |
| `Database connection failed` | DB_HOST указывает на старый IP | Обновить `DB_HOST` в `.env` |
| `Permission denied` на файлах | Неправильные права после распаковки архива | `chown -R <uid>:<gid>` на папку с данными |
| `Port already in use` | Другой сервис занял порт | Изменить порт в `docker-compose.yml` или использовать NPM |
| Данные не перенеслись | Забыли включить volume в архив | Пересоздать архив с нужными папками, повторить |

## 16.9 Практика

1. Выберите один работающий сервис (или тестовый Nginx с конфигом) на вашем Ubuntu-сервере.
2. Составьте персональный чеклист миграции для него — минимум 10 пунктов.
3. Создайте LXC с Docker на Proxmox согласно Главе 4.
4. Перенесите сервис по шагам из раздела 16.4.
5. Убедитесь что он работает на новом IP.
6. Добавьте LXC в расписание автоматических бэкапов.
