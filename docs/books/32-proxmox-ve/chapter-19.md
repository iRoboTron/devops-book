## 19.1 Сценарий: Восстановление из бэкапа — полный цикл

Бэкап бесполезен, если вы ни разу его не восстанавливали. Это не преувеличение — файл бэкапа мог быть создан с ошибкой, может быть повреждён, а восстановление на незнакомой системе в 3 часа ночи — не лучший момент впервые разбираться в командах. Практикуйтесь заранее.

---

### Восстановление на том же сервере

Это самый частый сценарий: контейнер сломался после обновления или случайного удаления данных. Бэкап лежит на локальном хранилище.

```bash
# Эта команда восстанавливает LXC-контейнер из файла бэкапа.
# 100 — ID контейнера (тот же, что был).
# /mnt/backup-hdd/dump/... — путь к файлу бэкапа на хранилище backup-hdd.
# --storage local-lvm — на какое хранилище восстановить диск контейнера.
pct restore 100 /mnt/backup-hdd/dump/vzdump-lxc-100-2026_05_22-03_00_00.tar.zst \
  --storage local-lvm
```

Если контейнер с ID 100 уже существует — команда завершится с ошибкой. Нужно сначала уничтожить старый:

```bash
pct stop 100         # остановить, если запущен
pct destroy 100      # удалить контейнер
```

После восстановления — запустить и проверить:

```bash
pct start 100
pct exec 100 -- systemctl status    # сервисы внутри запустились?
pct exec 100 -- df -h               # данные на месте?
```

Найти имя файла бэкапа, если не знаете точное название:

```bash
# Список всех бэкапов в хранилище backup-hdd
pvesm list backup-hdd

# Или вручную через ls
ls -lh /mnt/backup-hdd/dump/ | grep lxc-100
```

---

### Восстановление на другом сервере (железо сгорело)

Это сценарий катастрофы: основной сервер умер, вы купили или одолжили другой, бэкапы где-то есть. Задача — запустить контейнеры на новом Proxmox.

```bash
# Шаг 1. Скопировать файл бэкапа на новый сервер через scp.
# Источник — внешний диск или NAS, куда были записаны бэкапы.
# Назначение — папка /tmp/ на новом сервере Proxmox.
scp /mnt/backup/dump/vzdump-lxc-100-*.tar.zst root@192.168.1.200:/tmp/
```

```bash
# Шаг 2. На новом сервере — восстановить контейнер из файла.
pct restore 100 /tmp/vzdump-lxc-100-2026_05_22-03_00_00.tar.zst \
  --storage local-lvm
```

```bash
# Шаг 3. Проверить конфиг — IP может конфликтовать с другими устройствами
# или не соответствовать подсети нового сервера.
cat /etc/pve/lxc/100.conf
```

В выводе найдите строку `net0:` и проверьте IP-адрес. Если нужно — отредактировать:

```bash
# Изменить IP контейнера через конфиг (контейнер должен быть остановлен)
# Открыть файл конфига и поправить строку net0
nano /etc/pve/lxc/100.conf
```

```bash
# Запустить контейнер
pct start 100

# Убедиться что сервисы внутри работают
pct exec 100 -- systemctl is-active docker
pct exec 100 -- docker ps
```

---

### Тестовое восстановление (раз в месяц — обязательно)

Смысл теста: восстановить контейнер под другим ID, проверить что данные на месте и сервисы стартуют, а потом удалить тестовый контейнер. Это не занимает больше 5 минут, но даёт уверенность что бэкапы рабочие.

ID 999 используется как «мусорный» тестовый контейнер — его всегда удаляют после проверки.

```bash
# Восстановить контейнер под ID 999 с именем test-restore.
# Это не тронет основной контейнер 100 — новый ID не конфликтует.
pct restore 999 /mnt/backup-hdd/dump/vzdump-lxc-100-2026_05_22-03_00_00.tar.zst \
  --storage local-lvm \
  --hostname test-restore
```

```bash
# Запустить тестовый контейнер
pct start 999
```

```bash
# Проверить что сервисы внутри запустились
pct exec 999 -- systemctl status
```

```bash
# Убедиться что данные на месте
pct exec 999 -- df -h
```

```bash
# После проверки — остановить и удалить тестовый контейнер.
# pct destroy удаляет контейнер и его диск полностью.
pct stop 999 && pct destroy 999
```

**Правило:** непроверенный бэкап — не бэкап.

## 19.2 Сценарий: Настройка Telegram-уведомлений

Сервер должен сам сообщать о проблемах — не ждать пока вы заметите. Email для этого неудобен: письма теряются, Push-уведомлений нет. Telegram-бот решает задачу за 10 минут и работает надёжно.

---

### Создание бота

1. Найдите в Telegram бота `@BotFather` и напишите ему `/newbot`.
2. Выберите имя бота (например `My Proxmox Bot`) и username (например `my_proxmox_123_bot`).
3. BotFather выдаст TOKEN вида `7412345678:AAFxxxx...` — скопируйте его.
4. Напишите своему боту любое сообщение.
5. Откройте в браузере: `https://api.telegram.org/bot<TOKEN>/getUpdates` — замените `<TOKEN>` на ваш.
6. В ответе найдите `"chat":{"id":123456789}` — это ваш CHAT_ID.

---

### Скрипт tg-notify

Теперь создадим скрипт-обёртку, который будет отправлять сообщение в Telegram одной командой:

```bash
# Создаём файл скрипта в /usr/local/bin/ — это стандартная папка для
# пользовательских исполняемых скриптов, доступных глобально.
cat > /usr/local/bin/tg-notify << 'EOF'
#!/bin/bash

# Токен вашего бота — получен от @BotFather
TOKEN="ваш_токен_бота"

# Идентификатор чата — куда отправлять сообщения
CHAT_ID="ваш_chat_id"

# Отправка сообщения через Telegram Bot API.
# $1 — первый аргумент скрипта, то есть текст сообщения.
# parse_mode=HTML позволяет использовать <b>, <i>, <code> в тексте.
# > /dev/null — подавить вывод curl, нас интересует только факт отправки.
curl -s "https://api.telegram.org/bot${TOKEN}/sendMessage" \
  -d "chat_id=${CHAT_ID}" \
  -d "text=$1" \
  -d "parse_mode=HTML" > /dev/null
EOF

# Сделать скрипт исполняемым
chmod +x /usr/local/bin/tg-notify
```

Проверить что скрипт работает:

```bash
# Должно прийти сообщение в Telegram с именем хоста
tg-notify "Proxmox test message from $(hostname)"
```

Если сообщение пришло — всё готово. Теперь любой скрипт на сервере может отправить уведомление одной строкой: `tg-notify "текст"`.

---

### Email через встроенные уведомления Proxmox

Если Telegram не подходит — Proxmox поддерживает уведомления по email.

- Datacenter → Notifications → Add → Sendmail или SMTP.
- Для Gmail: включить 2FA, создать App Password, указать в настройках SMTP.
- Уведомления отправляются автоматически при ошибках бэкапов и задач.

## 19.3 Сценарий: Три cron-скрипта автоматических проверок

Три скрипта покрывают основные сценарии мониторинга: упавший контейнер, заканчивающееся место, ежедневный статус. Все скрипты вызывают `tg-notify` — поэтому сначала нужно настроить Telegram.

---

### Скрипт 1: pve-healthcheck — перезапуск упавшего контейнера

Этот скрипт проверяет каждые 5 минут что обязательные контейнеры запущены. Если контейнер упал — автоматически перезапускает его и сообщает об этом в Telegram.

```bash
cat > /usr/local/bin/pve-healthcheck << 'EOF'
#!/bin/bash

# Список ID контейнеров которые ВСЕГДА должны быть запущены.
# Измените на реальные ID ваших контейнеров.
REQUIRED_CTS="100 101 102 103"

for CT_ID in $REQUIRED_CTS; do

  # Получаем текущий статус контейнера.
  # pct status 100 выводит строку вида "status: running" или "status: stopped".
  # awk '{print $2}' берёт второе слово — "running" или "stopped".
  # 2>/dev/null — подавить ошибку если контейнер с таким ID не существует.
  STATUS=$(pct status $CT_ID 2>/dev/null | awk '{print $2}')

  # Если контейнер не запущен — принять меры
  if [ "$STATUS" != "running" ]; then

    # Записать событие в лог-файл с датой и временем
    echo "$(date): CT $CT_ID is $STATUS, restarting..." >> /var/log/pve-healthcheck.log

    # Попытаться запустить контейнер
    pct start $CT_ID

    # Подождать 10 секунд — контейнеру нужно время чтобы запустить сервисы
    sleep 10

    # Проверить статус снова — запустился или нет?
    NEW_STATUS=$(pct status $CT_ID | awk '{print $2}')

    if [ "$NEW_STATUS" != "running" ]; then
      # Контейнер так и не запустился — это критическая ошибка, требует внимания
      tg-notify "🔴 ALERT: CT $CT_ID не запустился на $(hostname)"
    else
      # Контейнер успешно перезапущен — предупреждение, но не критично
      tg-notify "🟡 WARNING: CT $CT_ID упал, перезапущен автоматически на $(hostname)"
    fi

  fi
done
EOF

# Сделать скрипт исполняемым
chmod +x /usr/local/bin/pve-healthcheck
```

Добавить в cron — запускать каждые 5 минут:

```bash
# Файл в /etc/cron.d/ — системный cron, выполняется от root.
# */5 * * * * — каждые 5 минут.
echo "*/5 * * * * root /usr/local/bin/pve-healthcheck" > /etc/cron.d/pve-healthcheck
```

Проверить лог через несколько минут:

```bash
cat /var/log/pve-healthcheck.log
```

### Скрипт 2: pve-diskcheck — алерт при заполненности диска более 85%

Диск заполняется постепенно — логами, Docker-образами, бэкапами. Этот скрипт проверяет все смонтированные файловые системы и присылает уведомление если какая-то заполнена более чем на 85%.

```bash
cat > /usr/local/bin/pve-diskcheck << 'EOF'
#!/bin/bash

# Порог в процентах — при превышении придёт уведомление.
# 85% — разумный порог: ещё есть время среагировать.
THRESHOLD=85

# Читаем вывод df построчно, пропускаем заголовок (tail -n +2).
# df -h выводит: Filesystem, Size, Used, Avail, Use%, Mounted on
while IFS= read -r line; do

  # Извлекаем процент использования (5-я колонка) и убираем символ %
  USE=$(echo "$line" | awk '{print $5}' | tr -d '%')

  # Извлекаем точку монтирования (6-я колонка)
  MOUNT=$(echo "$line" | awk '{print $6}')

  # Сравниваем числа. 2>/dev/null — подавить ошибку если $USE не число
  # (например строка с tmpfs или devtmpfs).
  if [ "$USE" -gt "$THRESHOLD" ] 2>/dev/null; then
    tg-notify "⚠️ Диск ${MOUNT} заполнен на ${USE}% на $(hostname)"
  fi

done < <(df -h | tail -n +2)
EOF

# Сделать скрипт исполняемым
chmod +x /usr/local/bin/pve-diskcheck
```

Добавить в cron — запускать каждое утро в 8:00:

```bash
# 0 8 * * * — ровно в 8:00 каждый день.
echo "0 8 * * * root /usr/local/bin/pve-diskcheck" > /etc/cron.d/pve-diskcheck
```

Проверить скрипт вручную:

```bash
/usr/local/bin/pve-diskcheck
```

Если ни один диск не превышает 85% — тишина. Если хотите проверить что уведомления работают, временно измените порог на 10 и запустите снова.

---

### Скрипт 3: pve-dailyreport — утренний отчёт о состоянии сервера

Каждое утро в 9:00 сервер присылает сводку: сколько контейнеров и VM запущено, сколько памяти используется, сколько места на диске. Приятно получать такой отчёт вместе с утренним кофе — и сразу видеть если что-то не так.

```bash
cat > /usr/local/bin/pve-dailyreport << 'EOF'
#!/bin/bash

# Считаем количество работающих LXC-контейнеров.
# pct list выводит список всех контейнеров.
# grep running — оставляем только строки со статусом running.
# wc -l — считаем количество строк.
CT_COUNT=$(pct list | grep running | wc -l)

# Аналогично для виртуальных машин
VM_COUNT=$(qm list | grep running | wc -l)

# Получаем использование RAM в удобном виде.
# free -h выводит таблицу памяти с человекочитаемыми единицами (GB, MB).
# awk '/^Mem:/ {print $3 "/" $2}' — находим строку Mem и выводим "используется/всего".
RAM_USED=$(free -h | awk '/^Mem:/ {print $3 "/" $2}')

# Состояние корневого диска.
# df -h / — статистика по корневой файловой системе.
# awk 'NR==2 {print $3 "/" $2 " (" $5 ")"}' — вторая строка: "используется/всего (процент)".
DISK=$(df -h / | awk 'NR==2 {print $3 "/" $2 " (" $5 ")"}')

# Отправить отчёт в Telegram.
# <b>...</b> — жирный текст (parse_mode=HTML).
# uptime -p — время работы системы в удобном виде, например "up 3 days, 4 hours".
tg-notify "📊 <b>Proxmox Daily — $(hostname)</b>
Uptime: $(uptime -p)
RAM: ${RAM_USED}
Disk: ${DISK}
Running: ${CT_COUNT} CT, ${VM_COUNT} VM"
EOF

# Сделать скрипт исполняемым
chmod +x /usr/local/bin/pve-dailyreport
```

Добавить в cron — каждое утро в 9:00:

```bash
# 0 9 * * * — ровно в 9:00 каждый день.
echo "0 9 * * * root /usr/local/bin/pve-dailyreport" > /etc/cron.d/pve-dailyreport
```

Запустить вручную чтобы убедиться что работает:

```bash
/usr/local/bin/pve-dailyreport
```

В Telegram придёт сообщение вида:

```
📊 Proxmox Daily — pve-home
Uptime: up 5 days, 12 hours
RAM: 6.1G/15G
Disk: 41G/117G (35%)
Running: 4 CT, 1 VM
```

## 19.4 Сценарий: Uptime Kuma + Telegram — мониторинг доступности сервисов

Cron-скрипты проверяют состояние Proxmox изнутри. Uptime Kuma проверяет сервисы снаружи — открывает URL и проверяет что получает ответ. Если Nextcloud не отвечает — придёт уведомление, даже если сам контейнер запущен и Proxmox считает его живым.

---

### Установка Uptime Kuma

Проще всего через Community Scripts:

```bash
# На хосте Proxmox в Shell — создаёт LXC с Uptime Kuma автоматически
bash -c "$(curl -fsSL https://raw.githubusercontent.com/community-scripts/ProxmoxVE/main/ct/uptimekuma.sh)"
```

Или вручную в LXC с Docker:

```bash
# Запустить Uptime Kuma в Docker внутри любого Docker-LXC.
# -p 3001:3001 — порт доступа к веб-интерфейсу.
# -v uptime-kuma:/app/data — сохранять данные в именованный том.
# --restart always — автоматически перезапускать при сбое или перезагрузке.
docker run -d \
  --name uptime-kuma \
  --restart always \
  -p 3001:3001 \
  -v uptime-kuma:/app/data \
  louislam/uptime-kuma:latest
```

Открыть в браузере: `http://IP-контейнера:3001`, создать аккаунт администратора.

---

### Подключение Telegram к Uptime Kuma

1. Settings → Notifications → Add Notification.
2. Выбрать тип: Telegram.
3. Ввести Bot Token и Chat ID (те же что в `tg-notify`).
4. Test Notification — должно прийти тестовое сообщение.
5. Сохранить.

---

### Добавление мониторов

Для каждого сервиса создаём монитор:

- Add New Monitor → тип HTTP(s).
- URL: например `http://192.168.1.101:8080` (Nextcloud), `http://192.168.1.101:8123` (Home Assistant).
- Friendly Name: понятное название.
- Heartbeat Interval: 60 секунд — достаточно.
- Notification: выбрать созданный Telegram.

Uptime Kuma начнёт опрашивать URL каждую минуту. Как только сервис перестанет отвечать — придёт уведомление в Telegram. Когда восстановится — тоже придёт уведомление.

```
Типовые мониторы для домашнего сервера:
  - Nextcloud:       http://192.168.1.100:8080
  - Home Assistant:  http://192.168.1.200:8123
  - Jellyfin:        http://192.168.1.100:8096
  - Nginx PM:        http://192.168.1.101:81
  - Proxmox Web:     https://192.168.1.100:8006
```

## 19.5 Сценарий: После обновления Proxmox не загружается — GRUB и старое ядро

Ситуация: выполнили `apt full-upgrade`, перезагрузились — и сервер завис на этапе загрузки или упал в panic. Это редкость, но случается.

---

### Загрузка со старым ядром через GRUB

При включении сервера нужно успеть попасть в меню GRUB:

```
1. При старте сервера нажимать Shift (BIOS) или Esc (UEFI) — удерживать до появления меню GRUB.
2. Выбрать "Advanced options for Proxmox VE GNU/Linux".
3. Появится список ядер — выбрать предыдущее (второе в списке).
4. Enter — загрузиться.
```

После успешной загрузки — сервер снова доступен. Теперь нужно разобраться в проблеме и зафиксировать рабочее ядро.

---

### Что делать после загрузки с старым ядром

Посмотреть установленные ядра:

```bash
# dpkg --list показывает все установленные пакеты.
# grep linux-image фильтрует только ядра системы.
dpkg --list | grep linux-image
```

Заморозить проблемное новое ядро, чтобы оно не применялось до исправления:

```bash
# apt-mark hold запрещает apt обновлять или удалять этот пакет.
# Замените pve-kernel-6.8.12-9-pve на версию нового ядра из вывода dpkg.
apt-mark hold pve-kernel-6.8.12-9-pve
```

Сделать старое ядро загрузкой по умолчанию (пока не разберётесь с проблемой):

```bash
# update-grub перегенерирует файл конфигурации GRUB по текущим настройкам
update-grub
```

Когда проблема решена (вышло исправление или нашли причину) — снять заморозку:

```bash
# apt-mark unhold снимает ограничение на обновление пакета
apt-mark unhold pve-kernel-6.8.12-9-pve
```

---

### Профилактика: снапшоты перед обновлением

Лучший способ избежать проблем с обновлением — сделать снапшоты всех контейнеров и VM до него:

```bash
# Снапшот всех LXC-контейнеров перед обновлением
for CTID in $(pct list | awk 'NR>1 {print $1}'); do
  pct snapshot $CTID pre-upgrade --description "Before PVE upgrade $(date +%Y-%m-%d)"
  echo "Snapshot created for CT $CTID"
done

# Снапшот всех VM перед обновлением
for VMID in $(qm list | awk 'NR>1 {print $1}'); do
  qm snapshot $VMID pre-upgrade --description "Before PVE upgrade $(date +%Y-%m-%d)"
  echo "Snapshot created for VM $VMID"
done
```

После этого можно обновляться спокойно — если что-то пошло не так, откатить к снапшоту займёт 2 минуты.

## 19.6 Сценарий: Слишком много логов — journalctl vacuum

Proxmox активно пишет логи: сервисы контейнеров, задачи бэкапа, системные события. Через несколько месяцев журналы могут занять несколько гигабайт.

---

### Диагностика

Найти кто занимает место в /var/log:

```bash
# du -sh вычисляет размер каждого элемента в /var/log/.
# sort -rh сортирует по размеру от большего к меньшему (-r реверс, -h учитывает единицы GB/MB).
# head -10 показывает только топ-10 крупнейших.
du -sh /var/log/* | sort -rh | head -10
```

Узнать сколько занимает журнал journald:

```bash
# journalctl --disk-usage показывает суммарный размер всех журналов
journalctl --disk-usage
```

---

### Очистка журналов

Оставить только последние 200 МБ журналов:

```bash
# --vacuum-size=200M удаляет старые записи пока суммарный размер не станет <= 200MB.
journalctl --vacuum-size=200M
```

Или удалить записи старше 7 дней:

```bash
# --vacuum-time=7d удаляет все записи старше 7 дней.
journalctl --vacuum-time=7d
```

---

### Постоянный лимит — чтобы не допускать разрастания

Настроить максимальный размер журнала навсегда:

```bash
# /etc/systemd/journald.conf содержит конфигурацию демона journald.
# SystemMaxUse= — максимальный размер всех журналов на диске.
# sed ищет строку с закомментированной директивой и раскомментирует её с нужным значением.
sed -i 's/#SystemMaxUse=/SystemMaxUse=500M/' /etc/systemd/journald.conf
```

Применить изменения без перезагрузки:

```bash
# systemctl restart применяет новую конфигурацию.
systemctl restart systemd-journald
```

Проверить что лимит применился:

```bash
# Повторная проверка — должно показать <= 500MB
journalctl --disk-usage
```

Также можно ограничить срок хранения журналов в конфиге:

```bash
# Открыть конфиг и добавить MaxRetentionSec — максимальное время хранения записей
nano /etc/systemd/journald.conf
```

Добавить строку:

```
MaxRetentionSec=30day
```

Это означает: не хранить записи старше 30 дней, независимо от размера.

### Типичные ошибки и их причины

| Ошибка / симптом | Причина | Решение |
|---|---|---|
| `pct restore` завершается ошибкой | Контейнер с таким ID уже существует | `pct stop X && pct destroy X` перед восстановлением |
| Telegram-уведомления не приходят | Неверный TOKEN или CHAT_ID | Проверить через `curl` вручную, проверить что бот не заблокирован |
| Cron-скрипт не запускается | Нет прав на выполнение | `chmod +x /usr/local/bin/pve-*` |
| Cron-скрипт не находит `tg-notify` | `/usr/local/bin` не в PATH у cron | Указывать полный путь: `/usr/local/bin/tg-notify` |
| GRUB не показывает меню | Timeout слишком мал или GRUB_HIDDEN | Редактировать `/etc/default/grub`, поставить `GRUB_TIMEOUT=5` |
| После vacuum логи всё равно растут | Включена ротация logrotate | Проверить `/etc/logrotate.d/` и размеры там |

## Практика

1. Найти последний бэкап любого контейнера командой `pvesm list backup-hdd` и восстановить его под ID 999.
2. Проверить что сервисы внутри запущены командами `pct exec 999 -- systemctl status`.
3. Удалить тестовый контейнер.
4. Создать бота в Telegram, получить TOKEN и CHAT_ID.
5. Создать скрипт `/usr/local/bin/tg-notify`, отправить тестовое сообщение.
6. Установить и настроить все три cron-скрипта.
7. Установить Uptime Kuma, подключить Telegram, добавить мониторы для своих сервисов.
8. Запустить `/usr/local/bin/pve-dailyreport` вручную — убедиться что отчёт приходит.
