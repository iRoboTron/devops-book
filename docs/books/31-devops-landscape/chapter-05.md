# Глава 5: Хранилище, бэкап, базы данных

> ⏱ Время чтения: ~7 мин.

## Что вы узнаете

- как сделать бэкап, с которого реально восстановишься, и чем отличается настоящий бэкап от иллюзии;
- какую базу данных брать по умолчанию и когда оправдано отступить от этого правила;
- где хранить файлы и объекты — от маленького homelab до облачного стартапа.

---

## Категория 1: Бэкап

### Зачем

Данные теряются. Диск умирает, скрипт удаляет не то, provider падает. Бэкап — это не «копия на всякий случай», а заранее проверенный план восстановления. Без регулярной проверки что из бэкапа можно поднять рабочую систему — бэкапа не существует, есть только иллюзия безопасности. Шифрование обязательно: бэкап попавший не в те руки — это утечка данных.

### Дефолт

**restic** `self-hosted` `★★` `Docker: да`
Дедупликация означает что повторяющиеся блоки не хранятся дважды — инкрементальные снимки занимают минимум места. Шифрование включено по умолчанию — данные защищены на любом backend. Поддерживает S3, SFTP, локальный диск, Backblaze B2, Azure — один инструмент для любого назначения. Бинарник без зависимостей, запускается из cron или systemd-timer.

#### Правило 3-2-1

Три копии данных, на двух разных типах носителей, одна из которых — за пределами основного сервера. Практически: основная БД + restic на локальный диск (2 копии, 1 носитель) — этого недостаточно. Нужен хотя бы один remote-backend: Backblaze B2, облачный S3 или SFTP на другой VPS — это и есть «одна копия off-site». Без этого единственный пожар или кража сервера уничтожает всё.

### Альтернативы

| Инструмент | Метки | RAM | Когда брать |
|------------|-------|-----|-------------|
| Kopia | `self-hosted` `★` `Docker: да` | ~100 МБ | Похож на restic, но с веб-UI и десктопным приложением. Дедупликация на уровне блоков. Берёшь когда нужен GUI или работаешь на Windows/macOS |
| BorgBackup | `self-hosted` `★★` `Docker: нет` | ~50 МБ | Чуть лучшее сжатие чем у restic, зрелая экосистема, поддерживает SSH напрямую. Только Linux и macOS — нет нативного клиента для Windows. Выбор если нужен бэкап между Linux-машинами и привычен SSH-стек |
| Velero | `self-hosted` `★★★` `Docker: да` | — | Бэкап Kubernetes-ресурсов и persistent volumes. Нужен только если у тебя уже есть K8s — за пределами кластера не применим |

### Когда НЕ нужно

**Когда НЕ нужно (любой контекст):** `cron + tar.gz` без шифрования и без проверки восстановления — это не бэкап. Это архив который ты никогда не откроешь, пока не понадобится, и обнаружишь что он повреждён или не содержит нужного. Правило простое: если ни разу не запускал `restic restore` в тестовой среде — считай что бэкапа нет.

**Когда НЕ нужно (homelab):** платный managed backup-сервис для домашнего сервера с 50 ГБ данных. restic + Backblaze B2 обходится в доли доллара в месяц и делает то же самое.

### Отсылка в курс

Настройка restic, написание systemd-timer для автоматизации, проверка восстановления — в рамках этой книги не разбираются. Следи за обновлениями курса.

## Категория 2: Базы данных

### Зачем

Почти каждое приложение хранит структурированные данные: пользователи, транзакции, настройки, логи. Вопрос не «нужна ли БД» — нужна. Вопрос в том какую выбрать, и здесь у большинства инженеров — ошибка: они берут «интересную» или «новую» базу вместо проверенной. Это добавляет операционную сложность без реальной выгоды.

### Дефолт

**PostgreSQL** `self-hosted` `★★` `Docker: да`
Бери PostgreSQL если нет конкретной технической причины не брать. Транзакции ACID, JSON и JSONB прямо в запросах, полнотекстовый поиск без сторонних сервисов, богатый набор расширений (PostGIS для геоданных, pg_vector для эмбеддингов, TimescaleDB для временных рядов). Работает как основное хранилище для веб-приложений, API, аналитики малого масштаба — всё это без смены инструмента. PostgreSQL закрывает 95% задач, которые инженеры решают «модными» базами.

### Альтернативы

| Инструмент | Метки | RAM | Когда брать |
|------------|-------|-----|-------------|
| Redis | `self-hosted` `★` `Docker: да` | ~50 МБ | Кэш и очереди сообщений — и только. Сессии, rate limiting, pub/sub, очереди задач (Celery, Sidekiq). Не использовать как основное хранилище: данные могут быть вытеснены из памяти |
| SQLite | `self-hosted` `★` `Docker: да` | 0 МБ (встроенная) | Встраиваемая БД в один файл, без сервера. Идеально для небольших приложений без параллельных записей: CLI-утилиты, мобильные приложения, статичные сайты с небольшой базой. При высокой конкурентности записей — упирается в блокировки |
| ClickHouse | `self-hosted` `★★★` `Docker: да` | ~500 МБ+ | Колоночная OLAP-база для аналитических запросов по миллиардам строк. Логи, метрики, события — туда где PostgreSQL начинает тормозить на агрегациях. Не заменяет PostgreSQL: не поддерживает транзакционные UPDATE/DELETE, не годится для OLTP |

#### SQLite мощнее чем кажется

SQLite не только для маленьких проектов. Через **litestream** (непрерывная репликация в S3) и **libSQL** (форк от Turso с поддержкой удалённых соединений) SQLite работает в production с нагрузкой. Бери SQLite когда нет параллельных записей от нескольких процессов.

### Когда НЕ нужно

**Когда НЕ нужно (homelab / стартап):** не выбирай «модную» БД под обычный CRUD. MongoDB, Cassandra, DynamoDB — у каждой есть своя ниша, но если твоё приложение хранит пользователей, заказы и настройки — PostgreSQL справится лучше, и ты не будешь платить за кривую консистентность и ограниченные транзакции. Выбор «интересной» базы на старте откликнется болью при миграции.

**Когда НЕ нужно (enterprise):** не используй ClickHouse как замену PostgreSQL — это разные инструменты для разных задач. ClickHouse рядом с PostgreSQL, а не вместо.

### Отсылка в курс

PostgreSQL для DevOps: резервное копирование, репликация, настройка под нагрузку — **книга 37** (в разработке).

## Категория 3: Объектное хранилище

### Зачем

Файлы пользователей, медиа, артефакты сборки, дампы бэкапов — всё это не хранят в базе данных. Объектное хранилище — это HTTP-доступный бакет: положил, получил ссылку, масштабируется горизонтально. Де-факто стандарт API — Amazon S3, и всё что совместимо с ним — работает с теми же клиентами и SDK.

### Дефолт

**MinIO** `self-hosted` `★★` `Docker: да`
S3-совместимое API в одном Docker-контейнере. Поднимается одной командой, принимает те же запросы что и AWS S3 — приложение не знает разницы. Поддерживает версионирование объектов, политики жизненного цикла, event notifications. Выбор когда данные должны оставаться на своём железе: homelab, private cloud, compliance-окружение.

Если платформа облачная — бери native: **AWS S3**, **Yandex Object Storage**, **Google Cloud Storage**. Managed сервис дешевле в операционном обслуживании чем поддерживать MinIO в проде.

### Альтернативы

| Инструмент | Метки | RAM | Когда брать |
|------------|-------|-----|-------------|
| AWS S3 | `SaaS` `★` | — | Облачный стартап или enterprise. Managed, надёжный, S3 API — стандарт индустрии. Платишь за объём и запросы |
| Yandex Object Storage | `SaaS` `★` | — | То же что S3, S3-совместимый API, если инфраструктура в Яндекс Облаке |
| Garage | `self-hosted` `★★` `Docker: да` | ~50 МБ | S3-совместимое хранилище, написано на Rust. Устойчивее MinIO в кластере: при потере одного узла данные доступны. Берёшь для кластера из 3+ серверов вместо MinIO |

### Когда НЕ нужно

**Когда НЕ нужно (homelab):** MinIO для хранения пяти статичных файлов и одного аватара — оверкилл. Обычная директория на диске, отданная через nginx с правильными заголовками кэширования, решает задачу без операционной нагрузки. MinIO оправдан когда приложение уже использует S3 SDK и нужна совместимость.

## Категория 4: Файловое хранилище для команды

### Зачем

Не всё что нужно хранить — это объекты или строки в БД. Документы, таблицы, фото, корпоративный диск — это задача для файлового хранилища с синхронизацией и доступом через веб.

### Дефолт

**Nextcloud** `self-hosted` `★★` `Docker: да`
Self-hosted замена Google Drive / Dropbox. Синхронизация файлов, WebDAV, мобильные клиенты, совместное редактирование документов через плагины. Подробно разобран в **книге 27**.

## Как выбрать за 30 секунд

**База данных:**

1. Нужна реляционная БД для веб-приложения, API или сервиса?
   - Да → **PostgreSQL**. Всегда PostgreSQL по умолчанию.

2. Нужен кэш, сессии или очередь задач?
   - Да → **Redis** рядом с PostgreSQL, не вместо.

3. Приложение маленькое, без параллельных записей, нужна встраиваемая БД?
   - Да → **SQLite**.

4. Есть аналитические запросы по миллиардам событий, OLAP?
   - Да → **ClickHouse** — но PostgreSQL при этом остаётся для OLTP.

---

**Бэкап:**

1. Нужен бэкап данных с сервера?
   - Да → **restic**. Выбираешь backend (локальный диск + один remote).

2. Нужен GUI или работаешь на Windows/macOS?
   - Да → **Kopia** как альтернатива restic.

3. Нужен только Linux/macOS и привычен SSH-стек?
   - Да → **BorgBackup** как альтернатива.

4. Есть Kubernetes?
   - Да → **Velero** для бэкапа кластера.

5. Давно не проверял восстановление?
   - → Проверить прямо сейчас. `restic restore`. Пока не проверил — бэкапа нет.

---

**Объектное хранилище:**

1. Данные должны остаться на своём сервере?
   - Один сервер → **MinIO**.
   - Кластер из 3+ серверов → **Garage**.
   - Нет, облачная платформа → нативный S3 / Yandex Object Storage.

2. Нужно просто отдавать несколько статичных файлов?
   - Да → nginx + директория, без объектного хранилища.

## Ключевые тезисы

- Бэкап без проверки восстановления не существует — проверяй раз в квартал.
- restic — дефолт для бэкапов: шифрование, дедупликация, любой backend. Kopia если нужен GUI.
- PostgreSQL — дефолт для реляционных данных; Redis — для кэша и очередей, не основное хранилище.
- SQLite мощнее чем кажется: litestream + libSQL делают его production-ready для многих сценариев.
- MinIO для single-server, Garage для кластера из нескольких узлов.
