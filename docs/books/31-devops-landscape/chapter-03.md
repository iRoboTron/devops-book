# Глава 3: Мониторинг, логи, алерты

## Что вы узнаете

- три столпа observability — и честный ответ какой из них большинству не нужен;
- минимальный стек мониторинга, который реально поднять за вечер;
- куда слать алерты, чтобы они не потерялись.

---

## Три столпа observability: разберёмся честно

Observability в индустрии принято описывать через три столпа: **метрики**, **логи** и **трейсы**. Это правда — но только половина правды. Вторая половина: трейсы нужны единицам.

**Метрики** — числа во времени. CPU 78%, память 3.2 ГБ, запросов в секунду 420. Это то, что показывают графики и на чём строятся алерты.

**Логи** — текстовые события. Что произошло, когда, в каком компоненте. «404 для /api/users в 14:32:01». Незаменимо при разборе инцидента.

**Трейсы** — путь одного запроса через несколько сервисов. Запрос пришёл на API → пошёл в auth-сервис → оттуда в базу → вернулся с задержкой 800мс. Нужно когда сервисов несколько и они вызывают друг друга.

> **Честно про трейсы:** если у тебя один монолит или 2–3 сервиса за nginx, трейсы тебе не нужны. Это инструмент для микросервисной архитектуры с 10+ компонентами. Для homelab и большинства стартапов — метрики + логи полностью покрывают потребность. Jaeger и Tempo существуют, но ставить их «на вырост» — пустая трата ресурсов и времени.

## 3.1 Метрики

### Зачем

Метрики дают ответ на вопрос «как сейчас себя чувствует система». Без метрик ты узнаёшь о проблеме от пользователей — а не от графика. С метриками — ставишь алерт на «CPU >90% пять минут» и реагируешь до того как всё упало.

### Дефолт

**Prometheus + Grafana** `self-hosted` `★★` `Docker: да`
Prometheus собирает метрики через pull-модель (сам опрашивает endpoint'ы), хранит временные ряды локально, выдаёт данные по PromQL. Grafana строит дашборды и алерты поверх него. Это стандарт cloud-native мира — экосистема exporters насчитывает сотни готовых интеграций: node_exporter для Linux, cadvisor для контейнеров, postgres_exporter для PostgreSQL.

### Альтернативы

| Инструмент | Метки | Когда брать |
|-----------|-------|-------------|
| VictoriaMetrics | `self-hosted` `★★` `Docker: да` | Когда Prometheus съедает слишком много RAM — VM держит те же данные при 3–5× меньшем потреблении; PromQL-совместим, меняешь почти без изменений |
| Netdata | `self-hosted` `★` `Docker: да` | Homelab и быстрый старт: ноль конфигурации, тысячи метрик сразу из коробки, встроенный UI. Не подходит для сложных multi-host дашбордов и долгосрочного хранения |
| Zabbix | `self-hosted` `★★★` `Docker: да` | Enterprise и сети: SNMP-агенты, мониторинг сетевых устройств (роутеры, свитчи), legacy-инфраструктура, где нет HTTP endpoint'ов |

### Когда НЕ нужно

**Когда НЕ нужно (homelab):** не разворачивай полный kube-prometheus-stack если у тебя нет Kubernetes. Этот стек поднимает 15+ компонентов и съедает 2–4 ГБ RAM только на мониторинг. Для одного сервера хватит Prometheus + node_exporter + Grafana — три контейнера, 200–400 МБ.

### Отсылка в курс

Мониторинг с нуля (Prometheus + Grafana без K8s, пошаговая настройка) — **Книга 38** (в разработке). Мониторинг внутри Kubernetes, kube-prometheus-stack — **Книга 12**.

## 3.2 Логи

### Зачем

Метрики говорят *что* сломалось, логи — *почему*. Когда алерт сработал и ты открыл инцидент, следующее действие — смотреть в логи. Централизованный сбор логов позволяет искать по всем сервисам в одном месте, а не SSH-ить на каждую машину и гrepать файлы.

### Дефолт

**Grafana Loki** `self-hosted` `★★` `Docker: да`
Loki не индексирует содержимое строк — только метаданные (labels: сервис, хост, уровень). Это делает его на порядок дешевле ELK по памяти и диску. Логи ищутся через LogQL, интерфейс — та же Grafana что уже стоит для метрик. Агент сбора — Promtail (для файлов) или Alloy (замена Promtail, новый стандарт Grafana Labs).

### Альтернативы

| Инструмент | Метки | Когда брать |
|-----------|-------|-------------|
| ELK / OpenSearch | `self-hosted` `★★★` `Docker: да` | Когда нужен настоящий full-text поиск по миллионам строк: поиск внутри тела лога, сложные фильтры, аналитика по тексту. Минимум 4 ГБ RAM только под стек |
| Graylog | `self-hosted` `★★★` `Docker: да` | Compliance и audit: структурированные алерты по паттернам логов, хранение для проверок, GELF-протокол |

### Когда НЕ нужно

**Когда НЕ нужно (homelab / стартап):** не ставь ELK если у тебя нет реальной потребности в full-text поиске по миллионам строк. ELK требует Elasticsearch + Logstash + Kibana — минимум 4 ГБ RAM и значительное время на настройку. Loki решает 90% задач за 10% ресурсов. Правило: пока тебя не болит «не могу найти нужную строку в логах» — ELK не нужен.

### Отсылка в курс

Настройка Loki + Promtail в Kubernetes — **Книга 12**.

## 3.3 Uptime и алерты

### Зачем

Метрики и логи — это ответ на «что происходит». Uptime-мониторинг — это ответ на «мой сервис вообще отвечает?». Проверки доступности снаружи, с нескольких точек, каждую минуту — это другое чем внутренние метрики. Алерты — механизм доставки сигнала тебе когда что-то пошло не так.

### Дефолт

**Uptime Kuma** `self-hosted` `★` `Docker: да`
HTTP/HTTPS/TCP/DNS/Docker-проверки, 90+ каналов уведомлений (Telegram, Slack, Email, Discord и другие), красивый статус-пейдж — всё в одном контейнере. Запускается за пять минут, не требует конфигурации кроме добавления сервисов через UI. Для homelab и стартапов — первый выбор.

**Alertmanager** `self-hosted` `★★` `Docker: да`
Штатный компонент экосистемы Prometheus. Принимает алерты от Prometheus, группирует их, подавляет дубликаты, маршрутизирует в нужные каналы. Если у тебя уже есть Prometheus — Alertmanager идёт в паре с ним.

### Уведомления: куда слать

Обе системы нужно куда-то слать сигнал. Два удобных варианта:

**ntfy** `self-hosted / SaaS` `★` `Docker: да` — push-уведомления на телефон через HTTP POST. Один запрос — и алерт у тебя в кармане. Есть бесплатный SaaS (ntfy.sh) или self-hosted.

**Apprise** `self-hosted` `★` `Docker: да` — библиотека/сервис для отправки уведомлений в 80+ сервисов (Telegram, Slack, Email, Matrix и другие) из одного места. Удобно если надо слать в несколько каналов.

### Альтернативы

| Инструмент | Метки | Когда брать |
|-----------|-------|-------------|
| Grafana OnCall | `SaaS / self-hosted` `★★★` `Docker: да` | Enterprise: расписания дежурств, эскалации, интеграция с PagerDuty/OpsGenie, on-call ротации |
| PagerDuty | `SaaS` `★★` — | Enterprise: управление инцидентами, SLA-трекинг, интеграции с десятками ITSM-систем |

### Когда НЕ нужно

**Когда НЕ нужно (enterprise / production-критичное):** Uptime Kuma — отличный инструмент для homelab и некритичных сервисов. Но для production с SLA, командой дежурных и требованием «разбудить правильного человека в 3 ночи» — нужен Grafana OnCall или PagerDuty. Uptime Kuma не умеет ротации дежурств и эскалационные цепочки.

## Как выбрать за 30 секунд

**Метрики:**

1. Нужен мониторинг нескольких хостов с историей и дашбордами?
   - Да → **Prometheus + Grafana**.
   - Prometheus съедает RAM и хочется проще → **VictoriaMetrics** вместо Prometheus (Grafana остаётся).
   - Нет, один сервер, хочу просто видеть метрики прямо сейчас → **Netdata** (ноль конфигурации).
   - Нужен SNMP, сетевые устройства → **Zabbix**.

2. Есть Kubernetes?
   - Да → kube-prometheus-stack (книга 12).
   - Нет → не ставь kube-prometheus-stack.

**Логи:**

3. Нужен централизованный сбор логов?
   - Да → **Loki + Promtail/Alloy**.
   - Нужен full-text поиск внутри строк логов по миллионам событий → **OpenSearch / ELK**.
   - Нет, справляюсь journalctl и docker logs → ничего ставить не нужно.

**Uptime и алерты:**

4. Нужно знать когда сервис упал?
   - Да, для homelab или стартапа → **Uptime Kuma** + ntfy/Telegram.
   - Уже есть Prometheus → добавь **Alertmanager**.
   - Нужны ротации дежурств и эскалации → **Grafana OnCall** или **PagerDuty**.

**Трейсы:**

5. Есть микросервисная архитектура с 10+ сервисами, вызывающими друг друга?
   - Да → смотри на Jaeger или Grafana Tempo.
   - Нет → трейсы пока не нужны. Вернись к этому вопросу когда появятся.
