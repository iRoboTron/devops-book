# Глава 4: Секреты, доступ, аутентификация

## Что вы узнаете

- почему пароли людей и секреты приложений — разные задачи с разными инструментами;
- что ставить для хранения паролей команды и для доступа CI/CD к базам и API;
- нужен ли тебе SSO и когда это оверинжиниринг.

---

## Важно с порога: две разные задачи

Чаще всего эти вещи путают в одну кучу. Разберём раз и навсегда:

**Пароли людей** — это учётные данные, которые вводит человек: пароль к серверу, к почте, к банку, к GitHub. Менеджер паролей хранит их зашифрованными, синхронизирует между устройствами, генерирует новые. Это инструмент *для человека*.

**Секреты приложений** — это данные, которые читает код: `DATABASE_URL`, `API_KEY`, `JWT_SECRET`, токен CI/CD. Человек их почти не видит — они нужны процессам, деплою, оркестратору. Хранить их в менеджере паролей — неудобно и небезопасно для автоматизации. Это задача *для инфраструктуры*.

**SSO / IAM** — третья независимая задача: единая точка входа для нескольких приложений через один аккаунт (Google-like «войти через»). Не путать ни с первым, ни со вторым.

Ниже — три отдельные категории с отдельными инструментами.

---

## Категория 1: Менеджер паролей (для людей)

### Зачем

Команда из трёх человек рано или поздно сталкивается с задачей: где хранить общие доступы? SSH-ключи к серверу, пароль от домена, учётку облака — всё это нельзя держать в таблице или передавать в чате. Менеджер паролей даёт зашифрованное хранилище с контролем доступа, историей и генерацией паролей. Работает в браузере, мобильнике и CLI.

### Дефолт

**Vaultwarden** `self-hosted` `★★` `Docker: да`
Self-hosted сервер протокола Bitwarden, написанный на Rust. Docker-образ весит около 20 МБ и потребляет минимум памяти — работает даже на VPS с 512 МБ RAM. Полностью совместим со всеми официальными Bitwarden-клиентами: браузерными расширениями, мобильными приложениями, десктопным и CLI. Команда получает общее хранилище, организации, папки, аудит, 2FA — всё как в платном Bitwarden, но на своём железе. Для команды с требованием self-host — первый и последний ответ.

### Альтернативы

| Инструмент | Метки | Когда брать |
|------------|-------|-------------|
| Bitwarden (официальный) | `SaaS / self-hosted` `★` | Не хочешь обслуживать сервер: облачный аккаунт бесплатен для личного использования, платный — для команды. Enterprise-вариант с LDAP-интеграцией и SSO. Тяжелее Vaultwarden в self-host варианте |
| KeePassXC | `self-hosted` `★` `Docker: нет` | Одному человеку без сервера вообще: всё хранится в локальном файле `.kdbx`. Нет синхронизации из коробки, нет веб-интерфейса — зато нулевая инфраструктура и работает оффлайн |

### Когда НЕ нужно

**Когда НЕ нужно (homelab / один человек):** KeePass-файл в Dropbox или Google Drive — народное решение, которое формально работает, но это не менеджер паролей для команды: нет контроля доступа, нет истории изменений, нет возможности отозвать доступ уволившегося. Для одного себя — допустимо, для команды — нет.

## Категория 2: Управление секретами (для приложений и CI/CD)

### Зачем

Приложению в проде нужно знать пароль от базы, ключ API и сертификат. Хранить это в `.env`-файле на сервере — плохо: файл расползается по бэкапам, нет аудита, нет ротации. CI/CD нужен токен к реестру образов и к облаку — хранить его в переменных среды без контроля тоже рискованно. Инструменты управления секретами решают: хранение, версионирование, выдачу по запросу, ротацию и audit trail того, кто и когда что взял.

### Дефолт

**HashiCorp Vault** `self-hosted / SaaS` `★★★` `Docker: да`
Отраслевой стандарт для управления секретами в проде. Поддерживает AppRole (аутентификация сервисов), dynamic secrets (Vault сам создаёт временного пользователя БД под запрос и удаляет его после), интеграцию с Kubernetes через Vault Agent Injector. Даёт полный audit trail: кто, когда и какой секрет запросил. Если работаешь с K8s, несколькими командами или нужна ротация секретов БД — Vault единственный разумный выбор.

### Альтернативы

| Инструмент | Метки | Когда брать |
|------------|-------|-------------|
| SOPS + age | `self-hosted` `★★` `Docker: нет` | Секреты как зашифрованные файлы прямо в Git. SOPS шифрует YAML/JSON/ENV файлы, age — симметричный алгоритм шифрования. Не нужен отдельный сервер, не нужна инфраструктура. Для небольших проектов и стартапов — лучший компромисс между удобством и безопасностью |
| Infisical | `SaaS / self-hosted` `★★` `Docker: да` | Vault с человеческим интерфейсом: веб-UI, CLI, SDK, интеграции с GitHub Actions/GitLab CI из коробки. Self-hosted edition бесплатен. Хороший выбор если Vault кажется сложным, а SOPS — слишком примитивным |

### Когда НЕ нужно

**Когда НЕ нужно (homelab / малые проекты):** Vault для одного приложения с тремя переменными окружения — чистый оверинжиниринг. Поднять Vault, настроить политики, AppRole, TLS, Unseal — это часы работы и постоянное обслуживание. Начни с SOPS + age для Git-репозитория или с `.env` в защищённом хранилище, и только когда число сервисов и команд вырастет — думай о Vault.

**Когда НЕ нужно (стартап без K8s):** если деплой — это один-два сервера с Docker Compose, SOPS закрывает задачу полностью. Переход на Vault оправдан когда появляются dynamic secrets или audit-требования.

## Категория 3: SSO / IAM (единая точка входа)

### Зачем

Когда в инфраструктуре несколько приложений — Grafana, Gitea, Nextcloud, внутренний wiki — каждое требует отдельный логин. SSO (Single Sign-On) решает это: один аккаунт, один вход, все приложения получают токен через OAuth2/OIDC. Дополнительно — управление ролями (кто имеет доступ к чему), LDAP-интеграция, MFA, provisioning пользователей. Для команды это удобство и безопасность: уволившийся сотрудник отключается в одном месте, а не в двадцати.

### Дефолт

**Authentik** `self-hosted` `★★` `Docker: да`
Self-hosted Identity Provider с понятным веб-UI, поддержкой OAuth2, OIDC и SAML. Проще в настройке чем Keycloak, гибче чем Authelia. Flows (потоки аутентификации) настраиваются визуально. Поддерживает LDAP, MFA, invitation-ссылки, группы, поlistens аудит. Для homelab и стартапа — первый выбор если SSO нужен вообще.

### Альтернативы

| Инструмент | Метки | Когда брать |
|------------|-------|-------------|
| Keycloak | `self-hosted` `★★★` `Docker: да` | Enterprise: полноценный IdP от Red Hat, поддерживает всё — LDAP, Active Directory, Fine-grained RBAC, enterprise SSO. Значительно сложнее Authentik в настройке и требовательнее к ресурсам. Выбор когда compliance требует «проверенное enterprise-решение» или интеграции с AD критичны |
| Authelia | `self-hosted` `★` `Docker: да` | Лёгкий MFA-прокси перед reverse proxy: добавляет двухфакторку к любому приложению за Nginx/Traefik без полноценного IdP. Не является SSO в классическом смысле — только 2FA-барьер. Для homelab где нужна защита, но полный IdP избыточен |

### Когда НЕ нужно

**Когда НЕ нужно (homelab / малые проекты):** SSO для трёх пользователей и двух приложений — оверинжиниринг. Базовая аутентификация встроена почти в каждое приложение. Authentik добавляет сложность (его самого нужно обслуживать, обновлять, бэкапить). Начни с локальных аккаунтов в каждом приложении — переходи на SSO когда приложений станет больше пяти или нужно централизованное управление.

**Когда НЕ нужно (стартап):** если команда до пяти человек и все сервисы находятся на GitHub/Atlassian — там уже есть SSO через OAuth. Поднимать свой IdP имеет смысл только при переходе на self-hosted инфраструктуру или при требованиях compliance.

## Как выбрать за 30 секунд

**Задача 1 — пароли людей:**

1. Нужно хранить общие доступы в команде?
   - Да, хочу свой сервер → **Vaultwarden**.
   - Да, не хочу сервер, готов платить → Bitwarden облако.
   - Нет, только для себя, один человек → **KeePassXC** (файл локально) или личный Bitwarden-аккаунт.

2. Кто-то предлагает хранить `.kdbx` в Dropbox?
   - Для себя — терпимо. Для команды — нет: нет контроля доступа.

---

**Задача 2 — секреты приложений:**

1. Есть Kubernetes или несколько команд с требованиями к аудиту?
   - Да → **HashiCorp Vault** (см. книгу 36).
   - Нет → переходи к п. 2.

2. Нужны dynamic secrets (временные учётки БД под запрос)?
   - Да → **Vault**.
   - Нет → переходи к п. 3.

3. Всё хранится в Git-репозитории и нет отдельного сервера?
   - Да → **SOPS + age**: шифруй файлы секретов прямо в репозитории.
   - Нет, хочу UI и интеграции с CI из коробки → **Infisical**.

4. Одно приложение, три переменные, один сервер?
   - → `.env` с ограниченными правами на файл или SOPS. Vault не нужен.

---

**Задача 3 — SSO / IAM:**

1. Больше пяти приложений, которым нужна единая авторизация?
   - Да → **Authentik** (homelab/стартап) или Keycloak (enterprise/AD-интеграция).
   - Нет → локальные аккаунты в каждом приложении достаточны.

2. Нужна только двухфакторка перед существующими сервисами, без полноценного IdP?
   - Да → **Authelia** + Nginx/Traefik.

3. Пришли требования compliance с Active Directory?
   - → **Keycloak** (единственный self-hosted вариант с полной AD-интеграцией).
