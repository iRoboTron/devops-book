# Глава 6: Контейнеры, CI/CD, инфраструктура

## Что вы узнаете

- что брать для упаковки и запуска контейнеров — и когда Docker перерастает в Podman;
- нужен ли тебе Kubernetes, и как не ошибиться с ответом «да»;
- как выстроить CI/CD без изобретения велосипеда;
- в чём принципиальная разница между Terraform и Ansible — и почему это не конкуренты.

---

## Категория 1: Контейнеры и оркестрация

### Зачем

Контейнер — стандартная единица упаковки приложения: внутри всё что нужно для запуска, снаружи — изоляция. Это решает «у меня работает, в проде нет» и упрощает деплой. Оркестрация — следующий уровень: управлять не одним контейнером, а десятками, на нескольких серверах, с автоперезапуском, балансировкой и rolling update.

---

### Главная развилка категории

```
Это Docker vs Podman или эволюция?
  └─→ Эволюция. Docker — старт, Podman — шаг вперёд на prod.
      Они совместимы по интерфейсу, не противники.

Нужна ли оркестрация?
  └─→ Один сервер → compose + systemd. Стоп.
      Несколько серверов / масштабирование → читай дальше.
```

---

### Дефолт: Docker (начало)

**Docker** `self-hosted` `★` `Docker: да`
Стандарт де-факто для контейнеров. Огромная экосистема: Docker Hub, compose, миллионы готовых образов. Если ты никогда не работал с контейнерами — начинай здесь. `docker run`, `docker compose up` — команды, которые понимает весь интернет и вся команда.

---

### Следующий шаг: Podman (rootless, без демона)

**Podman** `self-hosted` `★★` `Docker: нет`
Запускает контейнеры без привилегированного демона — нет процесса root, нет одной точки отказа. Полностью совместим с Docker CLI: большинство команд работают без изменений (`alias docker=podman`). RHEL/CentOS Stream 9+ поставляются с Podman вместо Docker. Если уходишь в prod на RHEL-совместимом дистрибутиве или нужна rootless-изоляция — переходи на Podman.

---

### Оркестрация: compose и systemd vs Kubernetes

Одиночный сервер не нуждается в Kubernetes. Для него есть два варианта:

- **Docker Compose / Podman Compose** — запуск нескольких контейнеров из одного `compose.yml`. Декларативно, версионируется в Git, работает за пять минут.
- **systemd** — запуск контейнеров как systemd-сервисов (Podman умеет генерировать unit-файлы). Надёжно, перезапуск при падении, интегрировано в OS.

Эта связка закрывает 80% реальных случаев на одном сервере — без Kubernetes.

---

### Когда берёшь Kubernetes

**K8s** нужен когда выполняется хотя бы одно из условий:

- несколько серверов (нод), и нужно распределять нагрузку между ними;
- нужен автоскейлинг под нагрузку;
- большая команда с выделенным DevOps — есть кому этим заниматься;
- требования: rolling update, canary deployment, самовосстановление при падении ноды.

Если ни одного пункта нет — compose + systemd проще и надёжнее.

---

### Дефолт для homelab Kubernetes: k3s

**k3s** `self-hosted` `★★` `Docker: нет`
Облегчённый дистрибутив Kubernetes от Rancher: один бинарник, потребляет меньше 512 МБ RAM. Полностью совместим с K8s API — манифесты, kubectl, Helm работают без изменений. Если хочешь учить Kubernetes на домашнем сервере — k3s, не полноценный K8s.

---

### Альтернативы

| Инструмент | Метки | Когда брать |
|-----------|-------|-------------|
| k3s | `self-hosted` `★★` `Docker: нет` | homelab K8s: полный K8s API, < 512 МБ RAM. |
| Docker Swarm | `self-hosted` `★★` `Docker: да` | Встроен в Docker, проще K8s. Устаревает — новые проекты лучше не начинать. |
| Nomad | `self-hosted` `★★★` `Docker: да` | HashiCorp-стек: если уже используешь Vault и Consul. Нишевый выбор. |

---

### Когда НЕ нужно

**Когда НЕ нужно (homelab / малые проекты):** Kubernetes для одного приложения на одном сервере — почти всегда ошибка. K8s решает задачи распределённых систем. Одному сервису не нужна балансировка между нодами. Compose + systemd запускается за 5 минут, не требует изучения CRD, RBAC, Ingress Controller и etcd. Kubernetes добавляет сотни движущихся частей к задаче которая решается двадцатью строками YAML.

**Когда НЕ нужно (стартап на старте):** не начинай с K8s «на вырост». Начни с compose, доведи до рабочего состояния, смигрируй когда реально упрёшься в ограничения. Преждевременная оркестрация убивает скорость.

## Категория 2: Git-хостинг

### Зачем

Код живёт в Git-репозитории. Кроме локального хранения нужен сервер: веб-интерфейс, pull requests, доступ по SSH/HTTPS, webhook для CI. Вопрос не в том, нужен ли Git-хостинг — он нужен всегда. Вопрос в том, поднимать ли свой или пользоваться готовым облачным.

---

### Дефолт self-hosted

**Forgejo** `self-hosted` `★` `Docker: да`
Лёгкий форк Gitea под свободной лицензией. GitHub-совместимый интерфейс: репозитории, issues, pull requests, webhooks, CI-интеграция. Потребляет ~100–150 МБ RAM при спокойной нагрузке. Поднимается за 10 минут через compose. Если хочешь свой Git-сервер — это дефолт.

---

### Дефолт SaaS

**GitHub** или **GitLab** — зависит от того, что уже использует команда. Не выбирай между ними ради выбора: бери то, где уже живёт код и люди.

- **GitHub** — стандарт open-source, Actions встроены, огромная экосистема интеграций.
- **GitLab** — полный DevOps-цикл в одном продукте: git + CI + registry + kubernetes integration. Хорошо для корпоративного self-hosted.

---

### Альтернативы

| Инструмент | Метки | Когда брать |
|-----------|-------|-------------|
| Gitea | `self-hosted` `★` `Docker: да` | Предшественник Forgejo. Работает, но Forgejo — активнее поддерживаемый форк. |
| GitLab CE | `self-hosted` `★★★` `Docker: да` | self-hosted всего цикла: git + CI + registry. Тяжёлый: 4+ ГБ RAM. Enterprise или большая команда. |
| Bitbucket | `SaaS` `★` `Docker: нет` | Если команда уже в экосистеме Atlassian (Jira, Confluence). |

---

### Когда НЕ нужно

**Когда НЕ нужно (homelab, один человек):** поднимать свой Gitea/Forgejo ради одного-двух репозиториев — нецелесообразно. GitHub бесплатен для публичных репозиториев и щедр для приватных. self-hosted Git оправдан когда есть требования к приватности, команда, или нужна локальная CI без внешних сервисов.

**Когда НЕ нужно (стартап без DevOps):** GitLab self-hosted без человека который его обслуживает превращается в источник проблем. Managed GitLab или GitHub — правильный выбор пока нет ресурсов на поддержку.

## Категория 3: CI/CD

### Зачем

CI/CD — автоматическое выполнение тестов, сборки и деплоя при push в репозиторий. Вместо «задеплоили руками по SSH» — пайплайн: push → тест → build → деплой. Это не роскошь, это страховка от «работает только на моей машине» и от случайных поломок в проде.

---

### Главная развилка категории

```
Репозиторий на GitHub?
  └─→ GitHub Actions. Без вопросов.

Репозиторий на GitLab?
  └─→ GitLab CI. Без вопросов.

self-hosted Git (Forgejo/Gitea) или нужен self-hosted runner?
  └─→ Woodpecker CI.
```

Не выбирай CI отдельно от Git-хостинга — бери то, что уже рядом с твоим репозиторием.

---

### Дефолт: GitHub Actions

**GitHub Actions** `SaaS` `★` `Docker: нет`
Встроен в GitHub: файл `.github/workflows/deploy.yml` — и пайплайн готов. Тысячи готовых actions в маркетплейсе, бесплатный лимит для публичных репозиториев и приватных до определённого объёма. Если код на GitHub — это дефолт, без обсуждения.

---

### Дефолт: GitLab CI

**GitLab CI** `SaaS / self-hosted` `★★` `Docker: да`
Встроен в GitLab, конфигурация в `.gitlab-ci.yml`. Полный цикл: тест, build, deploy, review environments. Работает и в облачном GitLab, и в self-hosted GitLab CE/EE. Если код на GitLab — берёшь его.

---

### Альтернатива self-hosted: Woodpecker CI

**Woodpecker CI** `self-hosted` `★★` `Docker: да`
Лёгкий CI-сервер, совместимый с Forgejo и Gitea через webhooks. Конфигурация в `.woodpecker.yml`. Минимальное потребление ресурсов. Если у тебя self-hosted Forgejo и ты хочешь CI рядом — Woodpecker.

---

### Альтернативы

| Инструмент | Метки | Когда брать |
|-----------|-------|-------------|
| Woodpecker CI | `self-hosted` `★★` `Docker: да` | Forgejo/Gitea + лёгкий self-hosted CI. |
| Drone CI | `self-hosted` `★★` `Docker: да` | Предшественник Woodpecker. Woodpecker — его активный форк. |
| Jenkins | `self-hosted` `★★★` `Docker: да` | Старый стандарт с огромной экосистемой плагинов. Только если legacy или жёсткие требования к self-hosted с плагинами которых нет в других системах. |

---

### Когда НЕ нужно

**Когда НЕ нужно (новый проект):** Jenkins в новом проекте — нет оснований. GitHub Actions и GitLab CI проще в настройке, не требуют своего сервера, имеют лучший DX. Jenkins берут когда он уже есть или нужна специфическая экосистема плагинов. Начинать с Jenkins в 2026 году — наследовать сложность без выгоды.

**Когда НЕ нужно (homelab, один человек):** сложный пайплайн для pet-проекта — избыточно. Иногда достаточно `git pull && docker compose up -d` по SSH через cron или простой webhook. CI оправдан когда есть команда или хотя бы тесты которые надо запускать автоматически.

---

## Категория 4: Infrastructure as Code (IaC)

### Зачем

IaC — инфраструктура в виде кода в репозитории. Вместо «зайди в консоль облака и нажми создать VM» — файл который описывает что должно быть создано. Повторяемо, версионируется, можно ревьювить. Здесь важно понять принципиальную разницу между двумя типами IaC.

---

### Terraform и Ansible — не конкуренты

Это самое частое заблуждение в категории. Они решают **разные задачи**:

```
Terraform / OpenTofu — провизионирование инфраструктуры:
  Создать VM, сеть, load balancer, managed БД, DNS-запись.
  "Что должно существовать в облаке или у провайдера."

Ansible — конфигурирование серверов:
  Установить пакеты, настроить nginx, задеплоить приложение,
  положить конфиги. "Что должно быть установлено и настроено на сервере."
```

На практике они работают вместе: Terraform создал VM → Ansible настроил её.

---

### Дефолт: Terraform / OpenTofu (инфраструктура)

**OpenTofu** `self-hosted` `★★` `Docker: нет`
Открытый форк Terraform, полностью совместимый по синтаксису HCL. После смены лицензии HashiCorp в 2023 году OpenTofu — рекомендованный выбор для новых проектов. Terraform по-прежнему широко используется в enterprise с коммерческой поддержкой.

Берёшь когда нужно создавать или пересоздавать инфраструктуру в облаке: VPS, сети, firewall-правила, managed сервисы. Декларативная модель: описываешь конечное состояние, Terraform/OpenTofu рассчитывает план изменений.

**Terraform** `SaaS / self-hosted` `★★` `Docker: нет`
Исходный инструмент, огромная экосистема провайдеров (AWS, GCP, Azure, Hetzner, любой облачный сервис с API). Если команда уже на Terraform — нет причин мигрировать.

---

### Дефолт: Ansible (конфигурация)

**Ansible** `self-hosted` `★★` `Docker: нет`
Agentless: подключается по SSH, не требует ничего устанавливать на целевых серверах. Плейбуки на YAML описывают желаемое состояние системы. Идеален для: настройки новых серверов, деплоя приложений, управления конфигурацией однотипных машин. Огромная библиотека готовых ролей (Ansible Galaxy).

---

### Альтернативы

| Инструмент | Метки | Когда брать |
|-----------|-------|-------------|
| Pulumi | `SaaS / self-hosted` `★★★` `Docker: нет` | IaC на реальных языках программирования (Python, TypeScript, Go) вместо HCL. Если команда программисты — комфортнее чем HCL. |
| Nix / NixOS | `self-hosted` `★★★` `Docker: нет` | Полная воспроизводимость системы. Крутая кривая обучения. Нишевый выбор для тех кто хочет детерминированные окружения. |
| Chef / Puppet | `self-hosted` `★★★` `Docker: нет` | Legacy-инструменты конфигурирования. Только если они уже есть в организации. |

---

### Когда НЕ нужно

**Когда НЕ нужно (homelab, одна VPS):** Terraform для одного сервера — оверкилл. Создать одну VPS в Hetzner через веб-консоль или CLI-утилиту и настроить её Ansible-плейбуком или bash-скриптом — достаточно. Terraform окупается когда инфраструктуры много: несколько окружений (dev/staging/prod), несколько серверов, регулярное пересоздание.

**Когда НЕ нужно (Ansible vs скрипт):** Ansible оправдан когда серверов несколько или конфигурация сложная. Для одного сервера который ты настраиваешь один раз — bash-скрипт или просто руки быстрее. Не вводи инструмент ради инструмента.

## Как выбрать за 30 секунд

### Контейнеры и оркестрация

```
1. Никогда не работал с контейнерами?
   - Да → Docker. Учись здесь.
   - Уже работал → переходи к пункту 2.

2. Production на RHEL/CentOS Stream или нужна rootless-изоляция?
   - Да → Podman. Совместим с Docker CLI.
   - Нет → можно оставаться на Docker.

3. Нужна оркестрация (несколько сервисов)?
   - Один сервер → Docker Compose / Podman Compose + systemd. Стоп.
   - Хочу учить K8s дома → k3s.
   - Несколько серверов, масштабирование, команда DevOps → K8s.
```

### Git-хостинг

```
1. Код уже где-то лежит?
   - GitHub → оставайся.
   - GitLab → оставайся.
   - Нигде → GitHub если открытый, Forgejo если нужен self-hosted.

2. Нужен self-hosted?
   - Да → Forgejo (★, лёгкий) или GitLab CE (★★★, всё в одном).
   - Нет → GitHub или облачный GitLab.
```

### CI/CD

```
1. Где репозиторий?
   - GitHub → GitHub Actions.
   - GitLab → GitLab CI.
   - Forgejo / Gitea self-hosted → Woodpecker CI.

2. Нужен ли CI вообще?
   - Есть тесты или несколько разработчиков → да.
   - Один человек, pet-проект без тестов → достаточно webhook + deploy-скрипт.
```

### IaC

```
1. Нужно создавать инфраструктуру в облаке (VM, сети, managed сервисы)?
   - Да → Terraform или OpenTofu.
   - Нет → пропускай, не нужно.

2. Нужно настраивать серверы (установить ПО, конфиги, деплой)?
   - Да, серверов несколько или конфигурация сложная → Ansible.
   - Один сервер, несложно → bash-скрипт или руками.

3. Одна VPS в homelab?
   - Terraform — оверкилл. Ansible — может быть полезен.
   - Начни с Ansible, Terraform добавь когда инфраструктура вырастет.
```
