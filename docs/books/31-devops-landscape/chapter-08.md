# Глава 8: Стартовые стеки под твой сценарий

## Что вы узнаете

- готовые наборы инструментов под три реальных сценария — без «у вас богатый выбор»;
- сколько памяти и каких ресурсов потребует каждый компонент;
- в какую книгу курса идти за настройкой каждого инструмента.

---

## Это кульминация

Семь глав позади. Ты знаешь что выбрать для сети, прокси, мониторинга, секретов, хранилища, контейнеров и даже AI-помощников. Теперь собираем всё вместе.

Вместо «у вас богатый выбор» — три конкретных стека. Возьми тот, что ближе к твоей ситуации, и иди настраивать. Стеки — не догма: заменяй компоненты когда понимаешь зачем.

## Стек 1 — Homelab

**Сценарий:** один сервер, 8–16 ГБ RAM, учишься или держишь личную инфраструктуру. Сервисы для себя или небольшой группы. Время важнее денег в обратном смысле — не хочешь тратить вечера на отладку сложных систем.

**Принцип:** запустить за вечер, потреблять минимум памяти, без платных подписок.

### Состав стека

| Инструмент | Зачем |
|-----------|-------|
| **Docker Compose** | запуск всех сервисов без оркестратора — достаточно для одного хоста |
| **Caddy** | HTTPS и обратный прокси — автоматические сертификаты Let's Encrypt без возни |
| **Tailscale** | доступ к серверу с любого устройства без открытых портов в интернет |
| **Uptime Kuma + ntfy** | знать когда что-то упало и получить уведомление на телефон |
| **Vaultwarden** | хранить пароли для себя или небольшой команды — self-hosted Bitwarden |
| **restic** | бэкапы с шифрованием и дедупликацией в любой backend: S3, sftp, локальный диск |
| **Forgejo** | свой Git-хостинг если не хочешь зависеть от GitHub (опционально) |

### Потребление памяти

| Инструмент | RAM (примерно) | Примечание |
|-----------|---------------|------------|
| Docker (демон) | 150–300 МБ | постоянно |
| Caddy | 20–50 МБ | минимально |
| Tailscale | 10–30 МБ | фоновый процесс |
| Uptime Kuma | 100–200 МБ | Node.js, зависит от числа проверок |
| ntfy | 10–20 МБ | почти ничего |
| Vaultwarden | 15–30 МБ | Rust, очень лёгкий |
| restic | 0 МБ в простое | запускается по cron, отрабатывает, останавливается |
| Forgejo | 100–200 МБ | Go, лёгкий |
| **Итого без Forgejo** | **~320–630 МБ** | |
| **Итого с Forgejo** | **~420–830 МБ** | |

На сервере с 8 ГБ RAM весь стек занимает меньше 10% памяти. Остаток — твоим приложениям.

## Стек 2 — Стартап

**Сценарий:** команда 2–10 человек, продукт в активной разработке, есть бюджет. Время стоит дороже денег: час инженера дороже $20/месяц за managed-сервис.

**Принцип:** managed-сервисы там где настройка занимает дни, self-host там где просто и надёжно. Меньше инфраструктуры под управлением — больше времени на продукт.

### Состав стека

| Инструмент | Зачем |
|-----------|-------|
| **GitHub + GitHub Actions** | Git-хостинг и CI/CD — уже знакомо всей команде, бесплатно для публичных репо |
| **Caddy** | reverse proxy и HTTPS для сервисов на своих серверах |
| **Managed PostgreSQL** | основная БД — не тратить время на настройку репликации и бэкапов |
| **Yandex Object Storage / AWS S3** | файлы, статика, бэкапы — объектное хранилище без своего MinIO |
| **Grafana Cloud free tier** | мониторинг и логи — не тратить время на self-host Prometheus+Loki |
| **SOPS + age** | секреты в Git зашифрованными — проще Vault для небольшого числа сервисов |
| **Tailscale** | доступ команды к серверам без открытых портов и VPN-сервера |

### Развилки для неоднозначных выборов

**Reverse proxy — Caddy vs Traefik:**
Если сомневаешься — Caddy: три строки конфига, HTTPS сам, понятный синтаксис. Traefik берёшь когда уже есть Docker Compose или Kubernetes и нужно автообнаружение сервисов по labels — тогда он экономит время на ручных правках конфига.

**CI/CD — GitHub Actions vs GitLab CI:**
Начни с GitHub Actions если уже на GitHub: бесплатно для публичных репозиториев, $4/месяц за приватные. GitLab CI берёшь если хочешь self-hosted GitLab со встроенным CI без внешних зависимостей — например при требованиях к размещению кода.

**Managed PostgreSQL — где:**
Yandex Managed PostgreSQL если серверы в Яндекс.Облаке — нулевые задержки сети, один биллинг. AWS RDS если в AWS. Не разворачивай PostgreSQL на своей VM пока не столкнулся с ограничениями managed — репликация, WAL, резервное копирование требуют экспертизы.

**Мониторинг — Grafana Cloud vs self-hosted:**
Grafana Cloud free tier даёт 10 000 метрик, 50 ГБ логов в месяц и 14 дней хранения — для стартапа до 5 серверов хватает. Self-hosted Prometheus+Grafana+Loki поднимаешь когда вырастаешь из free tier или нужен полный контроль над данными.

**Секреты — SOPS vs HashiCorp Vault:**
SOPS + age: секреты как зашифрованные файлы в Git-репозитории. Работает без отдельного сервера, интегрируется с GitHub Actions через переменные среды. Vault берёшь когда появляются dynamic secrets (временные учётки БД) или audit-требования — это уже ближе к enterprise.

## Стек 3 — Enterprise

**Сценарий:** команда, compliance, масштаб. Несколько окружений (dev/staging/prod), требования к аудиту и RBAC, отказоустойчивость, всё под своим контролем.

**Принцип:** аудит каждого действия, ролевой доступ, отказоустойчивость, воспроизводимость инфраструктуры.

### Состав стека

| Инструмент | Зачем |
|-----------|-------|
| **Kubernetes** (k3s → kubeadm / managed) | оркестрация контейнеров, автоматический рестарт, rolling updates, RBAC |
| **ArgoCD** | GitOps-деплой: состояние кластера описано в Git, ArgoCD синхронизирует |
| **Terraform + Ansible** | инфраструктура как код (Terraform) и конфигурация серверов (Ansible) |
| **HashiCorp Vault** | секреты с dynamic credentials, audit trail, интеграция с K8s |
| **Keycloak** | SSO и IAM: единая точка входа, RBAC, интеграция с Active Directory |
| **Prometheus + Grafana + Loki** | полный observability-стек: метрики, дашборды, логи в одном месте |
| **Ingress-nginx / HAProxy** | балансировщик нагрузки, маршрутизация трафика в кластере |

### Развилки для неоднозначных выборов

**Kubernetes — k3s vs kubeadm vs managed:**
Начни с k3s: один бинарник, минимум зависимостей, работает на VM с 2 ГБ RAM. Когда кластер вырастает или нужна HA control plane — переходи на kubeadm или managed K8s (Yandex Managed Kubernetes, AWS EKS). Managed снимает головную боль с etcd и обновлениями control plane.

**ArgoCD vs Flux:**
Оба реализуют GitOps. ArgoCD — UI-first, быстрее в освоении, удобнее показывать состояние кластера команде. Flux — CLI-first, лучше автоматизируется, проще в multi-tenant сценариях. Для большинства команд ArgoCD — более понятный старт.

**Ingress-nginx vs HAProxy:**
Ingress-nginx — стандарт для Kubernetes, хорошо документирован, интегрируется с cert-manager для автоматических сертификатов. HAProxy берёшь вне Kubernetes или когда нужны расширенные возможности балансировки (ACL, health-check на уровне TCP, sticky sessions) — в enterprise бывает обязательным требованием.

**Keycloak vs Authentik:**
Keycloak — enterprise: полная интеграция с Active Directory, LDAP, SAML 2.0, тонкая настройка политик. Authentik — проще в настройке и потребляет меньше ресурсов, но в сложных AD-интеграциях проигрывает. Если compliance требует «проверенного enterprise IdP» — Keycloak.

### Предупреждение

Не пытайся поднять весь этот стек сразу. Это классическая ошибка: человек видит «правильную архитектуру» и начинает разворачивать Kubernetes + Vault + Keycloak + Prometheus + ArgoCD одновременно. Результат — потраченные недели и ни одного задеплоенного приложения.

**Реалистичный порядок:**

1. Сначала — K8s (k3s) + ArgoCD. Это ядро. Научись деплоить через GitOps.
2. Добавь Prometheus + Grafana. Без мониторинга слепо.
3. Vault — когда появятся реальные требования к секретам (dynamic credentials, audit).
4. Keycloak — когда число приложений и пользователей требует централизованного SSO.
5. HAProxy / Ingress — сразу, это нужно для трафика.
6. Terraform + Ansible — параллельно с п. 1, для воспроизводимости инфраструктуры.

## Как пользоваться стеками

Стеки — отправная точка, не жёсткий рецепт. Вот как с ними работать:

**Выбери ближайший сценарий.** Не тот что хочется в будущем, а тот где ты сейчас. Если у тебя один VPS — это homelab, даже если компания называет это «production». Честность к себе сэкономит недели.

**Заменяй компоненты по мере роста.** Стеки — это эволюция, не три отдельных пути:

```
homelab          →    стартап         →    enterprise
Docker Compose        Docker Compose        Kubernetes
Caddy                 Caddy / Traefik       Ingress-nginx
Forgejo / GitHub      GitHub + Actions      GitHub / GitLab + ArgoCD
SOPS                  SOPS + age            HashiCorp Vault
Vaultwarden           Vaultwarden           Keycloak + Vaultwarden
Uptime Kuma           Grafana Cloud         Prometheus + Grafana + Loki
```

Переходить сразу с homelab на enterprise — архитектурная ошибка. Каждый шаг должен решать реальную боль, а не «правильную архитектуру».

**Заменяй по одному компоненту за раз.** Когда GitHub Actions перестаёт хватать — переходи на ArgoCD. Когда SOPS становится неудобным — добавляй Vault. Не меняй всё сразу.

**За настройкой — в профильные книги.** Эта книга говорит что выбрать. Как настроить — в книгах курса из таблиц выше.
