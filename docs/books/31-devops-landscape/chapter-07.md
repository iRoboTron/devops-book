# Глава 7: AI-помощники в повседневной работе

> ⏱ Время чтения: ~9 мин.

## Что вы узнаете

- какие AI-инструменты реально экономят время инженеру прямо сейчас;
- что поднять локально, а что брать как облачный сервис;
- что делегировать агенту безопасно, а что — нет.

---

AI-помощники в 2026 году — не экзотика и не маркетинг. Это категория рабочих инструментов наравне с редактором и терминалом: они входят в стандартный набор инженера так же, как когда-то вошли линтеры и форматтеры. Главный вопрос уже не «нужно ли», а «что конкретно брать и для чего».

Важная граница этой главы: речь идёт только об инструментах на рабочей машине инженера или в CI — coding-агенты, IDE-плагины, локальные модели. Производственная AIOps-инфраструктура (ML-аномалии в Grafana, предиктивный скейлинг) — отдельная тема, она упомянута в конце главы одним абзацем.

---

## Категория 1: Coding-агенты (CLI)

### Зачем

Coding-агент — это инструмент который читает весь контекст репозитория, понимает задачу в целом и выполняет её автономно: пишет файлы, запускает команды, исправляет ошибки в цикле. Не автодополнение следующей строки, а делегирование задачи уровня «напиши Ansible playbook для деплоя этого приложения» или «разберись почему CI падает». Разница с IDE-помощником: агент работает в терминале, видит весь репозиторий и действует самостоятельно, а не по нажатию Tab.

---

### Дефолт

**Claude Code** `SaaS` `★` `Docker: нет`
Читает весь репозиторий, выполняет задачи автономно прямо в терминале: создаёт файлы, запускает команды, итерирует по результату. Хорошо справляется с задачами на уровне «добавь этот сервис в compose-файл и напиши конфиг для Nginx». Работает через API Anthropic — нужен ключ.

---

### Альтернативы

| Инструмент | Метки | Когда брать |
|-----------|-------|-------------|
| Aider | `self-hosted` `★★` `Docker: нет` | Open-source CLI-агент. Работает с любой моделью через OpenAI API или локально через Ollama. Если нужен агент без облачной зависимости или хочешь использовать локальную модель — первый выбор. |
| Codex CLI | `SaaS` `★` `Docker: нет` | CLI от OpenAI, аналогичная концепция. Если уже платишь за ChatGPT Plus — попробовать несложно. |

---

### Когда НЕ нужно

**Когда НЕ нужно (везде):** не давай агенту применять изменения в prod без ревью. CLI-агент может сгенерировать правдоподобную команду которая сделает не то. Всегда смотри что именно предлагается выполнить, прежде чем разрешить. Агент — не замена ревью, а черновик который ты проверяешь.

---

## Категория 2: Coding-агенты (IDE)

### Зачем

IDE-интеграция работает иначе чем CLI: автодополнение на лету, объяснение кода по выделению, inline-чат прямо в редакторе. Для инженера который пишет конфиги, скрипты и читает незнакомый код — это экономия нескольких переключений контекста в час. Отдельный режим «agent mode» позволяет выполнять более длинные задачи не выходя из IDE.

---

### Главная развилка

```
Уже пользуешься VS Code или JetBrains?
  └─→ GitHub Copilot. Встроен, agent mode есть, не надо менять среду.

Хочешь AI-first редактор и готов платить отдельно?
  └─→ Cursor. VS Code-форк заточенный под работу с агентом.

Хочешь open-source плагин под любую модель?
  └─→ Continue. Подключает Ollama, OpenAI, Anthropic — на выбор.
```

---

### Дефолт

**GitHub Copilot** `SaaS` `★` `Docker: нет`
Встроен в VS Code и JetBrains, включается за две минуты. Автодополнение, инлайн-чат, agent mode для более длинных задач. Если уже платишь за GitHub — Copilot часто включён. Не нужно менять редактор или привыкать к новому интерфейсу.

---

### Альтернативы

| Инструмент | Метки | Когда брать |
|-----------|-------|-------------|
| Cursor | `SaaS` `★` `Docker: нет` | VS Code-форк заточенный под AI-workflow. Хорошо работает с длинным контекстом. Если хочется IDE которая строилась вокруг агента, а не добавила его сбоку. |
| Continue | `self-hosted` `★★` `Docker: нет` | Open-source плагин для VS Code и JetBrains. Подключается к любой модели: Ollama, OpenAI, Anthropic. Если важна гибкость выбора модели или конфиденциальность кода. |
| Codeium / Windsurf | `SaaS` `★` `Docker: нет` | Бесплатная альтернатива GitHub Copilot для автодополнения в IDE. Работает в VS Code, JetBrains. Берёшь когда Copilot дорогой, а Continue с локальной моделью медленнее чем хотелось бы. |

---

### Когда НЕ нужно

**Когда НЕ нужно (везде):** не нужно платить за Copilot, Cursor и Claude Code одновременно. Выбери один основной инструмент и используй его. Параллельные подписки не дают двойной продуктивности — дают путаницу в том что где запустил.

---

## Категория 3: Локальные модели

### Зачем

Облачный API — это чужой сервер который видит твой промпт. Для большинства задач это нормально. Но есть случаи когда нужно иначе: внутренний код который нельзя отправлять наружу, секреты которые случайно попадают в контекст, offline-среда, требования compliance. В таких случаях модель запускается локально на твоей машине.

---

### Дефолт

**Ollama** `self-hosted` `★` `Docker: да`
Запускает LLM-модели локально одной командой: `ollama run llama3`. Поддерживает десятки моделей, автоматически скачивает нужный вариант. Работает как локальный API, совместимый с OpenAI — можно подключить к Aider, Continue и другим инструментам без изменения кода. Требует машину с достаточным объёмом RAM или GPU.

Рекомендуемые модели для DevOps-задач: `qwen2.5-coder` (код и конфиги), `llama3.2` (общие задачи), `nomic-embed-text` (для RAG).

**Open WebUI** `self-hosted` `★` `Docker: да`
Чат-интерфейс для Ollama в браузере. Если нужен не API, а полноценный интерфейс как у ChatGPT — Open WebUI разворачивается рядом с Ollama за пять минут. Хранит историю разговоров локально.

---

### Альтернативы

| Инструмент | Метки | Когда брать |
|-----------|-------|-------------|
| LM Studio | `self-hosted` `★` `Docker: нет` | GUI-приложение для запуска моделей. Если Ollama кажется слишком терминальным — LM Studio даёт графический интерфейс для загрузки и запуска моделей. |
| llama.cpp | `self-hosted` `★★★` `Docker: да` | Нижний уровень — то на чём Ollama работает внутри. Если нужна максимальная оптимизация под конкретное железо. |

---

### Когда локальная модель, когда облачный API

**Бери локальную модель если:**
- в коде или промптах могут оказаться секреты, credentials, internal IP-адреса;
- compliance требует чтобы данные не покидали контур;
- есть GPU или много RAM (16+ GB для нормальной 7B-модели).

**Бери облачный API если:**
- качество ответа важнее конфиденциальности;
- нет мощного железа — на CPU локальные модели работают медленно;
- задача разовая.

**Честно про качество:** в 2026 году локальные open-source модели на уровне 7B–13B заметно уступают облачным frontier-моделям по сложным задачам. Для объяснения команды или черновика конфига — достаточно. Для сложного рефакторинга большой кодовой базы — облако даст лучший результат.

## Категория 4: RAG по своей документации

### Зачем

RAG (Retrieval-Augmented Generation) — это когда модель отвечает на вопросы опираясь на твои документы, а не только на обучающие данные. Практический кейс для инженера: ты загружаешь runbook'и, постмортемы, ADR и README своей команды, и получаешь чат-бота который знает именно вашу инфраструктуру. «Как мы откатываем деплой в prod?» — и ответ со ссылкой на ваш runbook, а не общая инструкция из интернета.

Разворачивать RAG в туториал здесь не будем. Это отдельная тема. Вот рецепт-схема для тех кто хочет попробовать:

---

### Рецепт-схема

```
Ollama (локальная LLM)
  + Qdrant (векторная БД — хранит embeddings документов)
  + Dify (платформа — UI, pipeline, загрузка документов)
  ↓
Загружаешь: runbook'и, постмортемы, ADR, README
  ↓
Получаешь: чат-бот который отвечает по вашей документации
```

Dify разворачивается через Docker compose, подключается к Ollama и Qdrant за полчаса. Что загружать: операционная документация (как восстанавливаться, что делать при алерте), архитектурные решения (ADR), постмортемы. Чем лучше документация — тем полезнее бот.

---

### Альтернативы

| Инструмент | Метки | Когда брать |
|-----------|-------|-------------|
| RAGFlow | `self-hosted` `★★` `Docker: да` | ~2 ГБ. Проще Dify для RAG по документации. Специализируется именно на документах (PDF, Markdown, Confluence). Берёшь если нужен только RAG без workflow-автоматизации которую даёт Dify. |
| AnythingLLM | `self-hosted` `★★` `Docker: да` | Проще в настройке чем Dify, всё в одном контейнере. Если хочется быстрее без сборки pipeline. |
| Langchain / LlamaIndex | `self-hosted` `★★★` `Docker: нет` | Фреймворки для кастомного RAG на Python. Если нужен контроль над каждым шагом pipeline — собираешь сам. |

---

### Когда НЕ нужно

**Когда НЕ нужно (homelab / малые проекты):** RAG имеет смысл когда документации реально много и она актуальна. Если в команде три страницы в Notion — проще спросить коллегу. RAG окупается при наличии реального объёма структурированной операционной документации которую кто-то поддерживает.

## Категория 5: Что делегировать AI, а что — нет

Это не категория инструментов, а правила использования. AI-агент — это джун который работает быстро, не устаёт, но иногда уверенно делает не то. Относись соответственно.

### Делегируй смело

- Написать Ansible playbook, Docker compose или Nginx конфиг по описанию — агент делает это хорошо, ты проверяешь результат.
- Разобрать stacktrace — «что значит этот exception и где смотреть» — экономит 15 минут поиска.
- Объяснить чужую команду — `curl -sSL ... | sudo bash` — прежде чем запускать, пусть агент объяснит что именно делает этот скрипт.
- Черновик постмортема по таймлайну событий — структуру и формулировки агент набросает быстро, ты редактируешь по факту.
- Регулярное выражение по описанию — «найди все IP в логах nginx» — точнее и быстрее чем гуглить.
- Code review конфига — «посмотри есть ли проблемы безопасности в этом Nginx конфиге» — полезный второй взгляд.

### Не делегируй

- Применять результат в prod без ревью. Агент может предложить `docker system prune -a` не понимая что там production-данные. Читай что предлагается.
- Секреты в промптах. Не вставляй токены, пароли, API-ключи в контекст облачного агента. Они идут на внешний сервер.
- Слепое доверие командам с `rm`, `prune`, `drop`, `truncate`. Агент может быть уверен — ты должен быть уверен тоже, независимо.
- Архитектурные решения которые сложно откатить. Агент хорошо знает паттерны, плохо знает твои бизнес-ограничения и историю проекта.

## AIOps: коротко

Встроенный ML есть в инструментах которые многие уже используют. Grafana умеет обнаруживать аномалии в метриках без ручного задания порогов. Netdata Anomaly Advisor подсвечивает метрики которые ведут себя нетипично. Это полезно и не требует отдельной настройки — работает из коробки.

Отдельный AIOps-продукт («AI для мониторинга») для малой команды — преждевременно. Это дорого, требует настройки, и базовые задачи (найти аномалию, предсказать disk full) хорошо решаются алертами на основе порогов в Alertmanager. Когда масштаб вырастет до сотен сервисов — вопрос станет актуальным.

## Как выбрать за 30 секунд

```
1. Нужен агент который работает в терминале с репозиторием?
   - Да, и данные можно отправлять наружу → Claude Code.
   - Да, но код конфиденциальный → Aider + Ollama локально.

2. Нужна помощь прямо в редакторе (автодополнение, inline-чат)?
   - Уже в VS Code / JetBrains → GitHub Copilot.
   - Хочу AI-first IDE → Cursor.
   - Хочу open-source и выбор модели → Continue.

3. Нужна локальная модель без облака?
   - Да → Ollama + Open WebUI.
   - Хочу GUI для загрузки моделей без терминала → LM Studio.

4. Нужен чат-бот по своей документации?
   - Да → Ollama + Qdrant + Dify (или AnythingLLM для старта).
   - Документации мало → не нужно, проще спросить агента напрямую.
```

## Ключевые тезисы

- AI-агент в терминале (Claude Code, Aider) — для задач по репозиторию; в IDE — для написания кода.
- Ollama + Open WebUI: локальные модели за 15 минут. Для конфиденциального кода — единственный вариант.
- RAG по своей документации за 1 час: Ollama + Qdrant + Dify (или RAGFlow для чистого RAG).
- Делегируй агенту генерацию конфигов и объяснение ошибок, но не применяй в prod без ревью.
- AIOps (Grafana ML, Netdata Anomaly Advisor) полезен как дополнение, не как отдельный продукт.
