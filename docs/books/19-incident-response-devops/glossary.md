# Глоссарий

> Термины и выражения книги «Обнаружение, мониторинг и Incident Response». В скобках — главы, где термин вводится или активно используется.

---

**Event (событие)** — любая запись о происходящем в системе: строка в логе, значение метрики, факт входа. Сам по себе не требует реакции. _(глава 0)_

**Alert (алерт)** — сигнал, сработавший по правилу или порогу и привлекающий внимание оператора. Не каждый алерт — инцидент. _(главы 0, 2)_

**Incident (инцидент)** — подтверждённое событие с реальным негативным impact, требующее инженерной реакции по жизненному циклу IR. _(главы 0, 8)_

**Incident Response (IR, реагирование на инциденты)** — дисциплина реакции на инциденты: обнаружение, triage, сдерживание, восстановление, фиксация уроков. _(главы 0, 8, 9)_

**IR lifecycle (жизненный цикл IR)** — последовательность фаз: detect → triage → contain → recover → lessons learned. _(главы 0, 8, 9)_

**Severity (критичность)** — уровень тяжести инцидента, определяющий приоритет и скорость реакции. _(глава 0)_

**Threat model (модель угроз)** — описание активов, границ доверия и наиболее вероятных классов атак. _(глава 0)_

**Trust zone (зона доверия)** — логическая граница, внутри которой компоненты доверяют друг другу; пересечение границы требует контроля. _(главы 0, 6)_

**Detection (обнаружение)** — способность заметить аномалию или признак компрометации по логам, метрикам и host-сигналам. _(главы 1, 2, 3)_

**Log (лог, журнал)** — первичное сырьё для расследования: запись о событии с временем, источником и результатом. _(глава 1)_

**Request id (идентификатор запроса)** — сквозной идентификатор, по которому один запрос прослеживается через proxy, приложение и БД. _(глава 1)_

**Centralization (централизация логов)** — сбор журналов из разных источников в одно место для корреляции и поиска. _(глава 1)_

**Correlation (корреляция)** — связывание событий из разных источников (auth, nginx, app) по общему ключу — времени, IP или request id. _(глава 1)_

**PII (Personally Identifiable Information)** — персональные данные, которые нельзя бесконтрольно писать в логи. _(глава 1)_

**Golden signals (золотые сигналы)** — базовый набор метрик наблюдаемости: latency, traffic, errors, saturation. _(глава 2)_

**Metric (метрика)** — числовой показатель состояния системы: CPU, память, диск, HTTP-коды, auth failures. _(глава 2)_

**Baseline (базовый профиль)** — зафиксированное нормальное состояние системы, с которым сравнивают текущее, чтобы заметить отклонение. _(главы 2, 3)_

**Actionability (применимость алерта)** — свойство алерта быть таким, по которому понятно, что делать; неактуальные алерты только шумят. _(глава 2)_

**Alert fatigue (усталость от алертов)** — снижение внимания из-за избытка шумных алертов, когда важные сигналы теряются. _(глава 2)_

**Runbook** — пошаговая инструкция реакции на конкретный алерт или сценарий, привязанная к сигналу. _(главы 2, 4, 5)_

**On-call (дежурство)** — режим, когда инженер принимает алерты и проводит первичную реакцию. _(глава 2)_

**Host-level detection (детекция на уровне хоста)** — поиск признаков компрометации на самой машине: процессы, listeners, unit-файлы, изменения файлов. _(глава 3)_

**File integrity (контроль целостности файлов)** — отслеживание изменений критичных файлов через хэши baseline. _(глава 3)_

**auditd** — подсистема аудита Linux, фиксирующая обращения к файлам и системным событиям по правилам. _(глава 6)_

**Listener (слушающий порт)** — процесс, принимающий сетевые соединения; неожиданный listener — частый признак инцидента. _(глава 3)_

**Triage** — быстрая первичная оценка инцидента: что произошло, где, когда, что затронуто и что сохранить сейчас. _(главы 4, 8)_

**Affected scope (затронутый объём)** — множество хостов, сервисов и данных, попавших под impact инцидента. _(главы 4, 9)_

**Containment (сдерживание)** — действия, прерывающие распространение инцидента: блокировка IP, изоляция хоста, отключение учётки. _(главы 4, 6, 9)_

**Isolation (изоляция хоста)** — отрезание скомпрометированного узла от сети с сохранением административного доступа. _(главы 4, 6)_

**Blast radius (радиус поражения)** — масштаб ущерба, который может нанести один скомпрометированный аккаунт или хост. _(глава 6)_

**Least privilege (минимум привилегий)** — принцип выдачи прав только в объёме, необходимом для задачи, что сокращает blast radius. _(глава 6)_

**Eradication (устранение причины)** — удаление корня проблемы (вредонос, бэкдор, уязвимость) перед восстановлением. _(главы 6, 9)_

**Recovery (восстановление)** — возврат сервиса в рабочее состояние после устранения причины, с проверкой результата. _(главы 5, 9)_

**Recovery chain (цепочка восстановления)** — полный набор того, что нужно для подъёма сервиса с нуля: VM, DNS, proxy, код, секреты, БД, storage. _(глава 5)_

**RPO (Recovery Point Objective)** — допустимый объём потери данных, выраженный во времени до последнего бэкапа. _(глава 5)_

**RTO (Recovery Time Objective)** — допустимое время восстановления сервиса после инцидента. _(глава 5)_

**Test restore (проверочное восстановление)** — реальное развёртывание бэкапа в отдельной среде для проверки, что restore работает. _(глава 5)_

**Smoke test** — быстрая проверка ключевых пользовательских путей (login, API) после восстановления. _(глава 5)_

**Immutable backup (неизменяемый бэкап)** — резервная копия, которую нельзя изменить или удалить из основной среды; защита от ransomware. _(глава 6)_

**Ransomware resilience (устойчивость к ransomware)** — способность пережить разрушительный сценарий через бэкапы, сегментацию и быстрый containment. _(глава 6)_

**Forensics (форензика)** — аккуратный сбор и анализ артефактов инцидента с фиксацией источника и надёжности. _(глава 7)_

**Volatile data (волатильные данные)** — данные, исчезающие первыми: память, сетевые соединения, список процессов. _(глава 7)_

**Order of volatility (порядок волатильности)** — правило собирать артефакты от самых недолговечных к самым устойчивым. _(глава 7)_

**Chain of custody (цепочка хранения улик)** — задокументированная история артефакта (время, хост, источник, хэш), доказывающая отсутствие подмены. _(глава 7)_

**IOC (Indicator of Compromise)** — артефакт, указывающий на компрометацию: подозрительный IP, хэш, домен, неожиданный процесс. _(главы 3, 7)_

**Incident note (заметка расследования)** — структурированная запись хода разбора: время, хост, команды, артефакты, факты и гипотезы. _(глава 7)_

**Facts vs hypotheses (факты против гипотез)** — принцип строго разделять подтверждённые наблюдения и предположения. _(главы 4, 7)_

**Incident drill (учение по инцидентам)** — controlled-упражнение, прогоняющее цикл detect → contain → recover на безопасном стенде. _(глава 8)_

**Tabletop exercise (настольное учение)** — обсуждение реакции на смоделированный инцидент без запуска опасного кода. _(главы 6, 8)_

**Controlled security event (управляемое событие)** — заранее внесённый безопасный сигнал в lab, чтобы потренировать реакцию. _(главы 8, 9)_

**Timeline (таймлайн инцидента)** — хронология событий и действий, ключевой результат triage и форензики. _(главы 8, 9)_

**Lessons learned (извлечённые уроки)** — конкретные выводы после инцидента, улучшающие детект и runbook. _(главы 8, 9)_

**Postmortem (разбор инцидента)** — итоговый документ с причиной, хронологией и действиями по предотвращению повторения. _(глава 9)_

**Blameless postmortem (безобвинительный разбор)** — формат postmortem, где ищут причины процесса и системы, а не виноватых. _(глава 9)_

**MTTR (Mean Time To Recovery)** — среднее время восстановления сервиса; ключевая метрика зрелости IR. _(глава 9)_
