## Контекст проекта

Читатель уже умеет запускать приложения на сервере, работать с Docker, Nginx, systemd, CI/CD и мониторингом. Но он может смотреть на приложение только глазами разработчика: "код работает".

Эта книга должна научить смотреть глазами эксплуатации:

- как приложение запускается;
- как останавливается;
- как обновляется;
- как переживает ошибку зависимости;
- как пишет логи;
- как делает миграции;
- как хранит состояние;
- как откатывается;
- как его диагностировать ночью без автора кода.

**Что читателя беспокоит:**
- в браузере два сайта выглядят одинаково, но один легко обновить, другой ломается при каждом релизе;
- непонятно, почему микросервисы иногда ухудшают жизнь;
- непонятно, почему healthcheck, graceful shutdown и миграции БД так важны;
- непонятно, почему DevOps-инженеру надо понимать архитектуру;
- хочется проектировать приложения так, чтобы потом их было удобно эксплуатировать.

**Что он хочет после книги:**
Уметь оценить приложение с точки зрения эксплуатации. Понимать tradeoffs монолита, микросервисов, очередей, stateful/stateless, миграций, retry/timeout, логирования и rollback. Уметь составить "operability checklist" для своего проекта.

## Главная идея

Архитектура — это не только "как код разложен по папкам". Для DevOps и SRE архитектура отвечает на вопрос: можно ли это приложение безопасно запускать, обновлять, наблюдать и восстанавливать.

```text
Плохая эксплуатационная архитектура:
релиз -> ручные шаги -> миграция ломает БД -> логи непонятны -> отката нет

Хорошая эксплуатационная архитектура:
релиз -> healthcheck -> миграция обратима -> graceful shutdown -> метрики -> rollback plan
```

**Ключевое понимание:**
- Приложение должно быть не только написано, но и эксплуатируемо.
- Монолит не зло, если он прост, наблюдаем и легко деплоится.
- Микросервисы покупают гибкость ценой сети, наблюдаемости и согласованности данных.
- Stateful-части требуют особой осторожности.
- Retry без timeout может усилить аварию.
- Логи и healthcheck — часть архитектуры, а не "потом добавим".

### Глава 1: Монолит, модульный монолит и микросервисы

**Цель:** объяснить архитектурные формы без религии.

Разобрать:
- монолит;
- модульный монолит;
- микросервисы;
- распределённый монолит.

Сравнение:

| Подход | Когда подходит | Плюсы | Минусы | Главный риск |
|---|---|---|---|---|
| Монолит | один продукт, маленькая команда | просто деплоить | может разрастись | хаос внутри |
| Модульный монолит | растущий проект | порядок без сети | нужна дисциплина | нарушить границы |
| Микросервисы | независимые команды/домены | независимые релизы | сложная эксплуатация | распределённый монолит |
| Распределённый монолит | когда микросервисы сделаны плохо | почти нет | всё сложно | худшее из двух миров |

Вывод для курса: новичку и маленькой команде чаще нужен хороший модульный монолит, а не микросервисы.

**Практика:** описать свой проект: это монолит, набор сервисов или хаос? Какие границы модулей есть?

### Глава 2: Stateless и stateful

**Цель:** объяснить, почему состояние усложняет эксплуатацию.

Разобрать:
- stateless web app;
- база данных как stateful-компонент;
- файлы пользователя;
- сессии;
- cache;
- очереди.

Схема:
```text
stateless app container -> можно пересоздать
postgres data volume -> нельзя потерять
uploads directory -> нужен backup
redis cache -> иногда можно потерять, иногда нет
```

Показать ошибки:
- хранить uploads внутри контейнера;
- хранить сессии только в памяти одного процесса;
- не понимать, что Redis может быть критичным;
- делать backup только кода, забывая БД и файлы.

**Практика:** составить карту состояния проекта:

### Глава 4: Healthcheck, readiness и liveness

**Цель:** объяснить, как система понимает, жив ли сервис.

Разобрать:
- healthcheck для человека и для инфраструктуры;
- `/healthz` — процесс жив;
- `/readyz` — сервис готов принимать трафик;
- проверка БД в readiness, но не всегда в liveness;
- Docker healthcheck;
- Nginx/upstream и Kubernetes readiness.

Пример:
```text
/healthz -> app process ok
/readyz -> app + db + migrations ok
/metrics -> Prometheus metrics
```

Ошибки:
- healthcheck всегда возвращает 200;
- healthcheck делает тяжёлый запрос;
- liveness зависит от внешней БД и перезапускает рабочий app при проблеме сети;
- нет отдельной проверки готовности после старта.

**Практика:** спроектировать 2 endpoint для учебного приложения: healthz и readyz.

### Глава 5: Graceful shutdown и startup

**Цель:** объяснить, почему завершение процесса — часть архитектуры.

Разобрать:
- SIGTERM;
- дать запросам завершиться;
- перестать принимать новые запросы;
- закрыть соединения;
- timeout остановки;
- startup delay и warmup.

Сценарий:
```text

старый получает SIGTERM
```

### Глава 6: Миграции базы данных

**Цель:** объяснить самый частый источник болезненных релизов.

Разобрать:
- schema migration;
- data migration;
- forward-only migrations;
- backward compatible changes;
- expand/contract pattern на простом примере;
- почему rollback кода не всегда откатывает БД;
- backup перед рискованной миграцией.

Пример безопасной миграции `users.full_name → users.first_name / users.last_name`:

```sql
-- Релиз 1: добавить новые колонки (nullable, ничего не ломает)
ALTER TABLE users ADD COLUMN first_name VARCHAR(100);
ALTER TABLE users ADD COLUMN last_name  VARCHAR(100);

-- Релиз 2: код пишет в обе схемы, читает из новой
-- (old клиенты ещё могут читать full_name)

-- Релиз 3: backfill существующих строк
UPDATE users
   SET first_name = split_part(full_name, ' ', 1),
       last_name  = split_part(full_name, ' ', 2)
 WHERE first_name IS NULL;

-- Релиз 4: добавить NOT NULL, удалить старую колонку
-- (только когда убедились, что старый код не использует full_name)
ALTER TABLE users ALTER COLUMN first_name SET NOT NULL;
ALTER TABLE users DROP COLUMN full_name;
```

Показать: если удалить `full_name` в Релизе 1, старый запущенный код упадёт немедленно — это типичная причина инцидентов на проде.

Ошибки:
- удалить колонку в том же релизе, где код ещё может её читать;
- делать долгую блокирующую миграцию днём;
- не знать размер таблицы;
- не иметь backup/restore test.

**Практика:** разобрать одну воображаемую миграцию `users.full_name -> users.first_name/users.last_name`.

### Глава 7: Retry, timeout и circuit breaker

**Цель:** показать, как "попробовать ещё раз" может усилить аварию.

Разобрать:
- timeout обязателен для внешнего вызова;
- retry только для временных ошибок;
- exponential backoff;
- jitter;
- circuit breaker;
- bulkhead на простом языке.

Сценарий аварии:
```text
API оплаты тормозит
100 клиентов ждут
app без timeout зависает
retry без backoff создаёт ещё больше запросов
падает всё
```

Сравнение:

| Паттерн | Зачем | Риск неправильного применения |
|---|---|---|
| Timeout | не ждать вечно | слишком маленький ломает нормальные запросы |
| Retry | пережить временный сбой | усилить нагрузку |
| Backoff | дать системе восстановиться | слишком долгие задержки |
| Circuit breaker | быстро отказывать при аварии | скрыть реальную проблему |

**Практика:** для трёх внешних зависимостей проекта указать timeout и retry policy.

### Глава 8: Очереди и фоновые задачи

**Цель:** объяснить, когда очередь помогает, а когда добавляет сложность.

Разобрать:
- зачем выносить долгие задачи в фон;
- очередь как буфер;
- worker;
- idempotency;
- duplicate processing;
- dead letter queue;
- retry фоновых задач;
- мониторинг длины очереди.

Примеры реализаций (упомянуть, не углубляться):
- **Redis + RQ** (Python): просто, для небольших проектов
- **Celery + Redis/RabbitMQ**: мощно, но сложнее в эксплуатации
- **PostgreSQL как очередь** (SKIP LOCKED): для простых случаев без доп. инфраструктуры
- **Systemd timer**: для периодических задач без очереди вообще

Примеры задач для очереди:
- отправка email;
- генерация отчёта;
- обработка изображения;
- уведомления Telegram.

Ошибки:
- считать очередь бесконечной;
- не мониторить backlog;
- не делать задачу идемпотентной;
- не иметь dead-letter механизма.

**Практика:** выбрать одну долгую операцию и решить: оставить синхронно или вынести в очередь.

### Глава 10: Стратегии деплоя и rollback

**Цель:** объяснить, как архитектура приложения определяет, какие стратегии деплоя возможны.

Разобрать:
- in-place deploy (заменить процесс на месте) — просто, но есть downtime;
- rolling deploy — обновление по частям, требует backward-compatible изменений;
- blue-green — два окружения, переключение трафика — быстрый rollback;
- canary — сначала 5% трафика, затем всё — снижает риск;
- feature flags — менять поведение без деплоя.

Схема blue-green:
```text
Production: blue (v1) получает весь трафик
Deploy:     поднять green (v2), проверить healthcheck
Switch:     Nginx/балансировщик переключает трафик на green
Rollback:   вернуть трафик на blue (секунды, не минуты)
```

Связь с архитектурой:
- stateless app → можно любую стратегию;
- stateful app с несовместимой миграцией БД → rolling/canary рискованны;
- monorepo с фронтендом и бэкендом → нужна явная backward compatibility.

Ошибки:
- фронтенд и backend деплоятся строго одновременно без плана совместимости;
- rollback невозможен из-за необратимой миграции БД;
- нет feature flag для рискованной функции;
- blue-green настроен, но тест на green не проверяет реальные данные.

**Практика:** для своего проекта выбрать реалистичную стратегию деплоя и описать шаги rollback.

## Особые требования

### Про уровень сложности

Писать для человека, который уже видел Docker и сервер, но не является архитектором. Каждый паттерн объяснять через проблему, а не через определение.

### Про микросервисы

Не продавать микросервисы. Честно показывать, что для одного человека и маленькой команды микросервисы часто создают больше проблем, чем пользы.

### Про практику

Не требовать писать большое приложение. Практика может быть проектированием, таблицами, ревизией существующего pet-project, маленькими псевдокод-примерами.

### Про безопасность

При логировании обязательно предупреждать о секретах и персональных данных. При миграциях и stateful-компонентах обязательно упоминать backup и restore test.

### Критерии готовности

Книга готова, если читатель после неё может:

- объяснить, почему архитектура влияет на эксплуатацию;
- выбрать между монолитом и микросервисами без фанатизма;
- отличить stateless от stateful;
- спроектировать healthcheck/readiness;
- объяснить graceful shutdown;
- назвать риски миграции БД;
- задать timeout/retry policy;
- составить operability review своего проекта.

### Не делать

- Не писать академическую книгу по архитектуре.
- Не уходить глубоко в DDD, CQRS, Event Sourcing.
- Не делать книгу про Kubernetes повторно.
- Не использовать enterprise-паттерны без объяснения цены.
- Не давать опасные миграции на реальной БД без предупреждения.

- Operability score: 10 пунктов по 2 балла, шкала 0–20
- Stateless vs stateful: таблица-шпаргалка (что где хранить)
- Healthcheck: `/healthz` vs `/readyz` — разница в одной строке
- Graceful shutdown: сигналы SIGTERM → действия → таймаут
- Migrate cheatsheet: expand / backfill / contract — три шага
- Retry policy: timeout / retry count / backoff — три параметра
- Log structure: обязательные поля JSON-лога
- Deploy strategies: in-place / rolling / blue-green / canary — сравнение в 4 строки

### Приложение B: Ресурсы и дальнейшее чтение

- "Building Microservices" (Sam Newman) — честный взгляд на цену микросервисов
- "Database Reliability Engineering" (Campbell, Majors) — миграции, backup, recovery
- 12factor.net — классический манифест для cloud-ready приложений
- Expand/Contract pattern — статья на martinfowler.com
- "Release It!" (Nygard) — паттерны надёжности: circuit breaker, bulkhead, timeout
