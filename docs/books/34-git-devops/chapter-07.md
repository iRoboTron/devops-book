# Глава 7: Rebase vs Merge — когда что использовать

## Что вы узнаете

- что делает `git rebase` и чем отличается от `git merge`;
- когда rebase даёт чистую историю, а когда опасен;
- что такое interactive rebase и как им пользоваться;
- золотое правило rebase.

---

## Проблема которую решает rebase

После долгой работы в feature-ветке история может выглядеть так:

```text
main: A → B → C → D → E
                   ↑
feature/auth: F → G → H
(ответвилась от C)
```

Если смержить: история запутается, появится merge-коммит, в `git log --graph` будут «рельсы».

Rebase говорит: «перенеси мои коммиты так, будто я ответвился не от C, а от E».

```text
После rebase:
main: A → B → C → D → E
                         ↑
feature/auth:             F' → G' → H'
(теперь ответвилась от E)
```

Коммиты F, G, H «переиграны» поверх E. Получаются новые коммиты F', G', H' с теми же изменениями, но новыми хешами.

---

## git rebase — основы

```bash
# Обновить feature-ветку от main
git switch feature/auth
git rebase main
```

Если конфликты:

```bash
# Разрешить конфликт в файлах
git add conflicted-file.txt

# Продолжить rebase
git rebase --continue

# Пропустить проблемный коммит (редко нужно)
git rebase --skip

# Отменить rebase, вернуться к исходному состоянию
git rebase --abort
```

## Merge vs Rebase: сравнение

```text
Merge:
main: A → B → C ────────────────────── M (merge commit)
                  \                   /
feature:           F → G → H ─────────

История: нелинейная, но честная. Видно когда и что ветвилось.
Безопасно для публичных веток.


Rebase:
main: A → B → C → D → E → F' → G' → H'

История: линейная, читается как один поток.
Опасно для публичных веток (меняет хеши).
```

### Когда merge лучше

- Ветка уже запушена и кто-то другой работает с ней
- Хочешь сохранить факт «здесь была feature-ветка»
- Merge request / Pull Request — обычно завершается merge

### Когда rebase лучше

- Обновляешь локальную feature-ветку от main перед пушем
- Хочешь чистую линейную историю
- Только ты работаешь в этой ветке

---

## Золотое правило rebase

> **Никогда не делай rebase веток которые уже запушены и которые используют другие люди.**

Rebase меняет хеши коммитов. Если кто-то уже сделал pull вашей ветки — у него будут старые хеши, у тебя новые. Слияние станет кошмаром.

```text
Безопасно:
git rebase main               ← обновить локальную feature от main
git pull --rebase             ← синхронизация со своей же запушенной веткой

Опасно:
git rebase на ветке которую используют другие
← их история расходится с твоей переписанной
```

## Interactive rebase — переписать историю

Interactive rebase позволяет редактировать, объединять, переставлять и удалять коммиты перед отправкой.

```bash
# Интерактивно переработать последние 3 коммита
git rebase -i HEAD~3
```

Откроется редактор со списком:

```text
pick f1a2b3c Добавить SSL сертификат
pick 9e8d7f6 Исправить опечатку в SSL
pick 3c4b5a2 Добавить HTTPS редирект

# Команды:
# p, pick   = использовать коммит как есть
# r, reword = использовать, но изменить сообщение
# e, edit   = использовать, но остановиться для изменений
# s, squash = слить с предыдущим коммитом (сохранить оба сообщения)
# f, fixup  = слить с предыдущим коммитом (выбросить это сообщение)
# d, drop   = удалить коммит
```

### squash — объединить несколько коммитов в один

```text
pick f1a2b3c Добавить SSL сертификат
squash 9e8d7f6 Исправить опечатку в SSL
pick 3c4b5a2 Добавить HTTPS редирект
```

Первые два коммита объединятся в один. Git предложит написать новое сообщение.

### fixup — объединить без сохранения сообщения

```text
pick f1a2b3c Добавить SSL сертификат
fixup 9e8d7f6 wip typo fix
pick 3c4b5a2 Добавить HTTPS редирект
```

«wip typo fix» растворится в предыдущем коммите.

### Типичный сценарий

```bash
# Работаешь в ветке, делаешь много мелких коммитов
git log --oneline
# 9e8d7f6 wip
# 3c4b5a2 fix typo
# f1a2b3c ещё правки
# a1b2c3d Добавить auth middleware

# Перед пушем: привести в порядок
git rebase -i HEAD~4
# Объединить всё в один чистый коммит "Добавить auth middleware"

git push -u origin feature/auth
```

## git rebase vs git merge pull

Как настроить что git pull делает при получении изменений:

```bash
# Всегда rebase при pull (рекомендую)
git config --global pull.rebase true

# Всегда merge при pull
git config --global pull.rebase false

# Только fast-forward (ошибка если нельзя)
git config --global pull.ff only
```

1. Создайте две ветки. В `main` сделайте 2 коммита, в `feature` ещё 2. Сначала смержите — посмотрите `git log --graph`. Потом сбросьте `main` и попробуйте rebase — сравните историю.
