# Глава 2: Основные понятия — репозиторий, коммит, история

## Что вы узнаете

- что такое репозиторий и что Git хранит внутри `.git/`;
- три состояния файла: рабочая директория, индекс, история;
- что такое коммит на самом деле — не «сохранение», а снимок;
- что такое HEAD и как Git отслеживает «где ты сейчас».

---

## Репозиторий

Репозиторий (сокращённо — репо) — это директория с кодом плюс скрытая папка `.git/`, в которой Git хранит всю историю изменений.

```bash
git init my-project
cd my-project
ls -la
# drwxr-xr-x  .git/    ← вся история здесь
```

Удали `.git/` — и репозиторий превратится в обычную папку. История исчезнет. Сам код останется.

### Что внутри .git/

```text
.git/
├── HEAD              ← указывает на текущую ветку
├── config            ← конфиг репозитория (local)
├── objects/          ← база данных объектов (коммиты, файлы, деревья)
├── refs/
│   ├── heads/        ← ветки (main, feature/auth, ...)
│   └── tags/         ← теги (v1.0, v2.3.1, ...)
└── COMMIT_EDITMSG    ← сообщение последнего коммита
```

Трогать `.git/` вручную почти никогда не нужно. Но понимать что там находится — полезно.

## Три состояния файла

Это одна из ключевых концепций Git. Каждый файл существует в одном из трёх состояний:

```text
┌─────────────────────┐   git add    ┌───────────────┐   git commit   ┌─────────────┐
│  Рабочая директория │ ───────────► │  Индекс       │ ──────────────► │  История    │
│  (working tree)     │              │  (staging area │                │  (история   │
│                     │ ◄─────────── │   / index)    │                │   коммитов) │
└─────────────────────┘  git restore └───────────────┘                └─────────────┘
```

**Рабочая директория** — файлы которые ты видишь и редактируешь. То что `ls` показывает.

**Индекс (staging area)** — промежуточная зона. Ты решаешь: «эти изменения пойдут в следующий коммит». `git add` перемещает изменения из рабочей директории в индекс.

**История** — зафиксированные коммиты. `git commit` берёт всё что в индексе и создаёт коммит.

### Почему два шага, а не один?

Потому что это даёт контроль над тем, что входит в каждый коммит.

Пример: ты изменил три файла — `nginx.conf`, `deploy.sh` и `README.md`. Хочешь сделать два отдельных коммита: один для конфига nginx, второй для скрипта деплоя.

```bash
git add nginx.conf
git commit -m "Настроить worker_connections"

git add deploy.sh
git commit -m "Добавить ретрай в скрипт деплоя"

# README.md пока не трогаем
```

Если бы Git коммитил всё сразу — такая точность была бы невозможна.

## Коммит — это снимок, не дельта

Важное заблуждение: «Git хранит список изменений между версиями». На самом деле Git хранит снимки (snapshots) состояния файлов.

```text
Дельта-подход (не Git):
commit 1: файл А создан
commit 2: добавлена строка 5 в файл А
commit 3: удалена строка 3 из файла А

Снимок-подход (Git):
commit 1: { файл А = "версия 1" }
commit 2: { файл А = "версия 2" }
commit 3: { файл А = "версия 3" }
```

Каждый коммит содержит полный снимок всех файлов репозитория в момент коммита (оптимизированный: если файл не изменился — ссылка на предыдущий снимок).

Это почему Git работает быстро: чтобы посмотреть файл в любом коммите, не нужно воспроизводить всю цепочку изменений. Снимок уже есть.

## Что такое коммит внутри

Каждый коммит — объект в базе данных Git, содержащий:

```text
commit abc1234
├── tree 7f3b891       ← ссылка на дерево (список файлов и их содержимое)
├── parent def5678     ← ссылка на предыдущий коммит
├── author Ivan <i@x>  ← автор и время
├── committer Ivan     ← тот кто сделал коммит (может отличаться)
└── message            ← сообщение коммита
```

SHA-1 хеш (`abc1234` — это сокращение) вычисляется из всего содержимого коммита. Изменить коммит нельзя, не изменив хеш.

Посмотреть конкретный коммит:

```bash
git show abc1234
# показывает метаданные + изменения (diff) этого коммита
```

## HEAD — «где ты сейчас»

`HEAD` — это специальный указатель, который говорит Git: «ты сейчас находишься здесь».

```text
main ──► commit-3 ──► commit-2 ──► commit-1
  ▲
HEAD
```

Обычно HEAD указывает на ветку (например, `main`), а ветка указывает на конкретный коммит. Когда ты делаешь новый коммит, ветка двигается вперёд.

```bash
cat .git/HEAD
# ref: refs/heads/main
# ← HEAD = «смотри в ветку main»

cat .git/refs/heads/main
# abc1234def5678...
# ← ветка main = конкретный хеш коммита
```

### Отсоединённый HEAD (detached HEAD)

Если переключиться на конкретный коммит (не ветку), HEAD перестаёт указывать на ветку:

```bash
git checkout abc1234
# HEAD is now at abc1234

cat .git/HEAD
# abc1234def5678...  ← HEAD = прямо на коммит, не на ветку
```

В этом состоянии можно просматривать код, но лучше не делать новые коммиты — они «потеряются» при переключении. Подробнее — в Приложении B.

## Структура истории

История коммитов — это граф, а не простой список. Каждый коммит знает своего родителя.

```text
Линейная история:
A ← B ← C ← D (main)

После ветвления:
A ← B ← C ← D (main)
          ↑
          E ← F (feature/auth)
```

`git log` по умолчанию показывает линейную историю. `git log --graph` показывает настоящий граф.

## Попробуйте сами

1. Создайте новый репозиторий (`git init test-repo`). Посмотрите что находится в `.git/` — особенно в `objects/` и `refs/`. После первого коммита сравните снова.
2. Создайте файл, добавьте в индекс (`git add`), но **не коммитьте**. Запустите `git status`. Теперь измените этот же файл ещё раз и снова `git status`. Что показывает разница?
3. Сделайте коммит, потом `cat .git/refs/heads/main` — там SHA-1 коммита. Запустите `git log --oneline` и убедитесь что хеш совпадает.
