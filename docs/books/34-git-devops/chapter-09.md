# Глава 9: .gitignore и хорошие практики коммитов

## Что вы узнаете

- как настроить `.gitignore` чтобы секреты и мусор не попали в репозиторий;
- синтаксис паттернов `.gitignore`;
- как писать хорошие сообщения коммитов;
- что такое атомарные коммиты и почему это важно.

---

## Зачем нужен .gitignore

Некоторые файлы не должны попасть в репозиторий:

| Категория | Примеры |
|-----------|---------|
| Секреты | `.env`, `secrets.yaml`, `credentials.json`, `*.key` |
| Зависимости | `node_modules/`, `vendor/`, `.venv/` |
| Сборочные артефакты | `dist/`, `build/`, `*.pyc`, `__pycache__/` |
| Редакторы / IDE | `.idea/`, `.vscode/`, `*.swp` |
| ОС | `.DS_Store`, `Thumbs.db` |
| Логи и кэш | `*.log`, `.cache/`, `tmp/` |

`.gitignore` — текстовый файл в корне репозитория. Git не отслеживает файлы которые совпадают с паттернами.

---

## Синтаксис .gitignore

```gitignore
# Комментарий

# Конкретный файл
.env
secrets.yaml

# Расширение — все .pyc файлы в любом месте
*.pyc

# Директория
node_modules/
__pycache__/

# Директория в конкретном месте
/dist/          ← только в корне репозитория
logs/           ← в любом месте

# Исключить из игнорирования (! = НЕ игнорировать)
*.log
!important.log  ← этот .log всё же отслеживать

# Всё в директории, но не саму директорию
logs/*

# Вложенные паттерны (** — любое количество директорий)
**/cache/
src/**/*.min.js
```

## Типовой .gitignore для DevOps-проекта

```gitignore
# Секреты и окружение
.env
.env.*
!.env.example
secrets/
*.pem
*.key
*.p12

# Terraform
.terraform/
*.tfstate
*.tfstate.backup
.terraform.lock.hcl

# Ansible
*.retry
.vault_pass

# Python
*.pyc
__pycache__/
.venv/
venv/

# Node (если есть скрипты)
node_modules/

# Редакторы
.idea/
.vscode/
*.swp
*.swo

# macOS
.DS_Store

# Временные файлы
*.tmp
*.log
/tmp/
```

> **Важно:** `.env.example` намеренно не игнорируется. Он содержит шаблон с именами переменных, но без значений — полезно для новых участников команды.

## gitignore.io — готовые шаблоны

Сайт [gitignore.io](https://www.toptal.com/developers/gitignore) генерирует `.gitignore` для любой комбинации инструментов. Через curl:

```bash
curl -s https://www.toptal.com/developers/gitignore/api/terraform,ansible,python,vim > .gitignore
```

## Если файл уже попал в Git

`.gitignore` игнорирует только **неотслеживаемые** файлы. Если файл уже закоммичен — добавление в `.gitignore` его не скроет.

```bash
# Убрать файл из отслеживания, но оставить на диске
git rm --cached .env
git rm --cached -r node_modules/

# Добавить в .gitignore
echo ".env" >> .gitignore

# Закоммитить
git add .gitignore
git commit -m "Убрать .env из отслеживания"
```

> ☠️ **Осторожно:** если `.env` с реальными секретами уже запушен — считай что секреты скомпрометированы. Смени все ключи и пароли. История Git сохраняет файл даже после удаления.

---

## Глобальный .gitignore

Некоторые файлы специфичны для твоего окружения, а не для проекта (`.DS_Store`, `.idea/`). Лучше добавить их в глобальный gitignore:

```bash
git config --global core.excludesFile ~/.gitignore_global
```

Создать `~/.gitignore_global`:

```gitignore
# macOS
.DS_Store
.AppleDouble

# Linux
*~

# Editors
.idea/
.vscode/
*.swp
*.swo
```

## Хорошие практики коммитов

### Правило 1: атомарный коммит

Один коммит — одно логическое изменение. Если нужно описать коммит через «и», «а также» — возможно это два разных коммита.

```text
Плохо:
"Добавить SSL + исправить nginx worker_processes + обновить README"

Хорошо:
Коммит 1: "Добавить SSL сертификат для api.example.com"
Коммит 2: "Увеличить worker_processes до числа CPU"
Коммит 3: "Обновить README: добавить инструкцию по SSL"
```

Атомарные коммиты проще ревьюить, откатывать и cherry-pick'ать.

### Правило 2: хорошее сообщение

**Структура:**

```text
<заголовок в повелительном наклонении, до 72 символов>

<пустая строка>

<необязательное тело: зачем, что было не так, ссылка на задачу>
```

**Примеры:**

```text
Плохо:
"fix"
"changes"
"updated nginx"
"wip"

Хорошо:
"Увеличить worker_connections до 1024 для высокой нагрузки"
"Добавить ретрай в deploy.sh: 3 попытки с паузой 5 секунд"
"Исправить 502 при загрузке файлов больше 10MB"
```

**Повелительное наклонение** — не «Добавил», а «Добавить». Не «Исправил», а «Исправить». Это соглашение Git сообщества.

### Правило 3: коммить часто, но осмысленно

Частые коммиты — хорошо: меньше потерь при сбое. Но перед пушем — навести порядок через `git rebase -i` (Глава 7).

### Правило 4: никогда не коммить сломанный код в main

Ветки для этого и нужны. В `main` попадает только рабочий код.

## Conventional Commits

Формальное соглашение для команд. Каждое сообщение коммита имеет префикс:

```text
feat: добавить поддержку SSL
fix: исправить 502 при больших загрузках
docs: обновить README по установке
chore: обновить зависимости
refactor: вынести конфиг nginx в отдельный файл
ci: добавить lint в GitHub Actions
test: добавить тест для auth middleware
```

Это стандарт, который используют в больших командах. CI может автоматически генерировать changelog из таких сообщений.

```text
feat(nginx)!: переключить на HTTP/2
                   ↑              ↑
                 scope        ! = breaking change
```
