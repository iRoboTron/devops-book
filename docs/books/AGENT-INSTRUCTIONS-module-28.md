## Главная идея

DevOps — это не должность "человек с Docker". Это способ уменьшить расстояние между разработкой и эксплуатацией.

SRE — это инженерный подход к надёжности: не просто "чтобы не падало", а измерять, сколько надёжности нужно, как быстро восстанавливаться и как не сгореть от ручной работы.

```text
Без DevOps/SRE:
код написали -> кто-то вручную залил -> сломалось -> ищем виноватого

С DevOps/SRE:
изменение -> автоматическая проверка -> предсказуемый деплой -> мониторинг -> быстрый откат -> выводы после инцидента
```

**Ключевое понимание:**
- DevOps нужен не ради инструментов, а ради безопасной доставки изменений.
- SRE нужен не ради красивых аббревиатур, а ради управляемой надёжности.
- Автоматизация нужна, чтобы убрать повторяемую ручную ошибку.
- Мониторинг нужен, чтобы узнать о проблеме раньше пользователя.
- Postmortem нужен не чтобы найти виноватого, а чтобы система стала лучше.

### Глава 1: Что такое DevOps на самом деле

**Цель:** снять миф, что DevOps = Docker/Kubernetes.

Объяснить:
- DevOps как сокращение расстояния между Dev и Ops;
- почему конфликт "разработчики пишут, админы чинят" вреден;
- feedback loop: чем быстрее узнаём об ошибке, тем дешевле исправить;
- маленькие частые изменения лучше огромных редких релизов;
- автоматизация как способ сделать процесс повторяемым.

Сравнение:

| Подход | Как выглядит | Плюсы | Минусы | Риск |
|---|---|---|---|---|
| Ручной деплой | человек копирует файлы | просто начать | ошибки, забытые шаги | неповторяемость |
| Скрипт деплоя | одна команда | быстрее | скрипт надо поддерживать | скрытая магия |
| CI/CD | проверки и деплой из Git | повторяемо | нужна настройка | ложное чувство безопасности |
| Platform approach | команда даёт готовые пути | удобно многим | сложно для маленьких | бюрократия |

**Практика:** взять ручной процесс и описать, какие шаги можно автоматизировать.

### Глава 2: You build it, you run it

**Цель:** объяснить ответственность за работающий сервис.

Объяснить:
- что значит "ты построил — ты участвуешь в эксплуатации";
- почему это не значит "разработчик один виноват за всё";
- почему разработчику полезно видеть логи, метрики и реальные ошибки;
- почему эксплуатация должна давать разработке обратную связь.

Показать плохую схему:
```text
разработчик -> передал архив -> админ поставил -> пользователи страдают -> все спорят
```

Хорошая схема:
```text
разработчик + эксплуатация -> общий pipeline -> общие логи -> общие критерии готовности
```

|---|---|---|---|---|

### Глава 3: SRE простыми словами

**Цель:** объяснить SRE как инженерную дисциплину надёжности.

Объяснить:
- Site Reliability Engineering = инженерия надёжности сервиса;
- SRE не "человек, который сидит и ждёт падения";
- SRE превращает эксплуатационные проблемы в инженерные задачи;
- toil: повторяемая ручная работа, которую надо уменьшать;
- автоматизация как лекарство от toil.

Таблица:

| Работа | Toil? | Что с ней делать |
|---|---|---|
| вручную перезапускать сервис каждый день | да | найти причину/автоматизировать |
| разово расследовать сложный инцидент | нет | задокументировать выводы |
| вручную создавать одинаковые VM | да | Terraform/Ansible |
| писать runbook | нет | это инвестиция |

**Практика:** найти 5 повторяемых ручных действий в своём проекте и выбрать одно для автоматизации.

### Глава 4: SLA, SLO, SLI без боли

**Цель:** объяснить надёжность через измеримые вещи.

Объяснить:
- SLI — что измеряем;
- SLO — какой уровень хотим держать;
- SLA — обещание пользователю/заказчику, часто с последствиями.

Пример:
```text
SLI: процент успешных HTTP-запросов за месяц
SLO: 99.5% запросов успешны
SLA: если ниже 99%, компенсируем клиенту
```

Для маленького проекта:
- не надо юридических SLA;
- нужен простой SLO для себя: доступность, время ответа, ошибки.

**Практика:** выбрать 3 SLI для своего сервиса:

| SLI | Как измерить | Нормальный уровень |
|---|---|---|
| сайт открывается | HTTP check | 99% за месяц |
| ошибка 5xx | Nginx logs | меньше 1% |
| backup свежий | дата backup | не старше 24 часов |

### Глава 5: Error budget

**Цель:** объяснить баланс между скоростью изменений и надёжностью.

Объяснить через бытовой пример:
- если сервис должен работать 99% времени, он может быть недоступен около 7 часов в месяц;
- это "бюджет ошибок";
- если бюджет тратится быстро, надо замедлить изменения и заняться стабильностью;
- если бюджет не тратится вообще, возможно команда слишком боится релизов.

Не усложнять математикой. Дать простые расчёты с конкретными числами.

Пример расчёта:
```text
SLO: 99.5% доступность за 30 дней
30 дней × 24 часа × 60 минут = 43 200 минут
43 200 × 0.5% = 216 минут ≈ 3.6 часа

Если сервис упал на 4 часа — error budget исчерпан досрочно.
Значит: заморозить новые фичи, заняться стабилизацией.

Если за месяц было только 30 минут даунтайма из 216 —
бюджет не израсходован: можно смелее выкатывать изменения.
```

Сравнение:

| Ситуация | Что делать |
|---|---|
| много падений после релизов | меньше фич, больше стабилизации |
| сервис стабилен, релизы редкие | можно ускорять доставку |
| нет измерений | сначала мониторинг |

**Практика:** посчитать error budget для двух SLO: 99% и 99.9% за 30 дней. Сравнить, насколько разные "бюджеты риска" получаются.

### Глава 6: DORA-метрики без корпоративной воды

**Цель:** показать, как измерять delivery без превращения в KPI-театр.

Объяснить 4 метрики:
- deployment frequency;
- lead time for changes;
- change failure rate;
- mean time to recovery.

Важно: не использовать метрики как дубинку против людей. Они нужны, чтобы видеть узкие места процесса.

Для маленького проекта:

| Метрика | Простой вопрос |
|---|---|
| Deployment frequency | как часто я безопасно выкатываю изменения? |
| Lead time | сколько проходит от commit до prod? |
| Change failure rate | как часто релиз ломает сервис? |
| MTTR | сколько чиню после падения? |

Показать конкретный пример оценки учебного проекта:

```text
Deployment frequency:  1 раз в 2 недели (низко — elite = несколько раз в день)
Lead time:             3 дня от идеи до прода (включая ручное тестирование)
Change failure rate:   2 из 8 релизов сломали что-то (25% — надо ниже 15%)
MTTR:                  ~40 минут (хорошо для одного человека)

Вывод: узкое место — lead time и change failure rate.
Следующий шаг: добавить автотест на smoke, сократить ручную проверку.
```

**Практика:** оценить свой проект по этим 4 вопросам без точных инструментов. Записать числа и выбрать одну метрику для улучшения.

### Глава 7: Инциденты и postmortem без поиска виноватых

**Цель:** научить превращать падение в улучшение системы.

Объяснить:
- incident = событие, которое ухудшило сервис;
- postmortem = разбор после инцидента;
- blameless не значит "никто не отвечает";
- цель — понять, почему система позволила ошибке дойти до пользователя.

Структура postmortem:
```markdown
# Incident report

## Что случилось
## Влияние на пользователей
## Timeline
## Причина
## Что помогло
## Что мешало
## Что сделаем, чтобы повторилось реже
## Action items
```

Показать **сквозной сценарий инцидента** от начала до конца (все этапы в одном месте):

```text
03:14 — uptime-check присылает алерт: сайт недоступен
03:15 — первый взгляд: curl → Connection refused
03:17 — docker ps: контейнер app в состоянии restarting
03:19 — docker logs app: ошибка подключения к БД, DATABASE_URL пустой
03:22 — причина: деплой перезаписал .env файл пустым шаблоном
03:25 — исправление: восстановить .env, перезапустить app
03:27 — сайт работает. Длительность: 13 минут.
```

После сценария — написать postmortem:

```markdown
# Incident report: пустой .env после деплоя

## Что случилось
## Влияние на пользователей
## Timeline
## Причина
## Что помогло
## Что мешало
## Что сделаем, чтобы повторилось реже
## Action items
```

**Практика:** написать полный postmortem по сквозному сценарию выше. Заполнить каждую секцию, включая action items (конкретные задачи с ответственным и сроком).

## Особые требования

### Про язык

Не писать как корпоративный консультант. Термины вводить только после бытового примера.

Плохо:
> Нужно внедрить observability и shift-left практики для повышения operational excellence.

Хорошо:
> Если сайт упал, ты должен быстро ответить на три вопроса: что сломалось, кого задело, что делать дальше. Набор логов, метрик и понятных процедур как раз нужен для этого.

### Про маленькие проекты

Каждую большую идею адаптировать к четырём масштабам:

- один человек;
- маленькая команда;
- учебный проект;
- организация.

### Про безопасность

Не давать опасных production-команд. Если используются примеры мониторинга, деплоя или перезапуска, объяснять, что это учебный сценарий.

### Критерии готовности

Книга готова, если читатель после неё может:

- объяснить DevOps без слов "это Docker и Kubernetes";
- объяснить SRE без слов "это админ на дежурстве";
- составить SLI/SLO для маленького сервиса;
- написать простой runbook;
- написать postmortem без поиска виноватых;
- выбрать 5 практик, полезных маленькому проекту, и отбросить лишний карго-культ.

### Не делать

- Не превращать книгу в список модных терминов.
- Не писать длинную историю DevOps-движения.
- Не копировать практики Google как обязательные для всех.
- Не делать книгу про Kubernetes, Terraform или CI/CD повторно.
- Не писать мотивационную воду без практических артефактов.

## Приложения

### Приложение A: Шпаргалка DevOps/SRE

Одностраничный справочник:
- SLI / SLO / SLA — определения в одной строке каждое
- Формула error budget: `(1 - SLO%) × период в минутах`
- DORA: 4 метрики с вопросом для ручной оценки
- Уровни зрелости: один человек / маленькая команда / организация
- Структура postmortem (заголовки)
- Runbook: структура (заголовки)
- Toil: признаки + что делать
