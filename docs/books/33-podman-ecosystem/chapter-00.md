# Глава 0: Жизнь после Docker — зачем нужен ещё один рантайм

## Что вы узнаете

- почему появилось несколько контейнерных рантаймов и что их объединяет;
- как Docker превратился из инструмента в стандарт, а потом стандарт отделился от инструмента;
- что такое OCI и зачем об этом знать практикующему инженеру;
- чем rootless-контейнеры принципиально отличаются от обычных.

---

## Docker сделал контейнеры популярными

В 2013 году Docker показал миру идею: упакуй приложение вместе с зависимостями в один образ — и оно одинаково запустится везде. Идея взлетела. За несколько лет Docker стал синонимом слова «контейнер».

Но популярность создала проблему. Docker — это одновременно:
- **формат образа** (слои, манифест);
- **рантайм** (запуск контейнеров);
- **демон** (фоновый сервис dockerd);
- **реестр** (Docker Hub);
- **инструмент сборки** (docker build);
- **оркестратор** (docker-compose, позже Swarm).

Всё в одной программе, всё завязано на один демон, всё работает под root. Пока Docker был у разработчика на ноутбуке — это нормально. Когда Docker пришёл в корпоративные кластеры и Kubernetes — начались вопросы.

---

## Что пошло не так

### Проблема 1: демон под root

Docker daemon (`dockerd`) запускается как root-сервис. Это значит: кто управляет Docker — тот root на машине.

```bash
# Добавить пользователя в группу docker — это дать ему root
sudo usermod -aG docker username
# С этого момента username может делать:
docker run -v /:/host alpine chroot /host  # полный доступ к ФС хоста
```

Любой, кто может запустить `docker run`, может стать root на хосте. Для CI/CD, где в контейнере запускается непроверенный код — это серьёзная дыра.

### Проблема 2: единая точка отказа

Один демон управляет всеми контейнерами. Упал dockerd — остановились все контейнеры. Зависла операция — заблокированы все остальные.

```text
dockerd ──► containerd ──► контейнер 1
                       ──► контейнер 2  ← если dockerd завис,
                       ──► контейнер 3     все три в опасности
```

### Проблема 3: socket = root

Docker socket `/var/run/docker.sock` — это прямой доступ к демону. В CI часто монтируют этот socket в контейнер чтобы «Docker мог запускать Docker». Это называется Docker-in-Docker.

```bash
# Так делают в CI — и это дыра безопасности
docker run -v /var/run/docker.sock:/var/run/docker.sock myci-image
# Теперь код внутри контейнера имеет root-доступ к хосту
```

## Kubernetes отказался от Docker

В 2020 году Kubernetes объявил: в версии 1.24 поддержка Docker будет удалена. Интернет взорвался заголовками «Kubernetes убивает Docker». Большинство их не поняли.

**Что на самом деле произошло:**

Kubernetes всегда запускал контейнеры через промежуточный слой — dockershim. Это был адаптер, который переводил внутренний K8s-интерфейс (CRI) в Docker API. Его убрали — потому что он был лишним.

```text
До 1.24:
Kubernetes → dockershim → dockerd → containerd → runc → контейнер
                  ↑ лишнее звено

После 1.24:
Kubernetes → CRI → containerd → runc → контейнер
```

Docker-образы при этом продолжают работать. Потому что Docker-образ и OCI-образ — одно и то же (с 2017 года). Убрали только необходимость держать запущенный dockerd на каждой K8s-ноде.

## Что такое OCI и зачем он нужен

В 2015 году Docker, CoreOS, Google, Red Hat и другие компании создали **Open Container Initiative** под крылом Linux Foundation. Цель: стандартизировать контейнеры так, чтобы они не зависели от конкретного инструмента.

OCI принял три спецификации:

| Спецификация | Что стандартизирует |
|---|---|
| **Image Spec** | Формат образа: слои, манифест, конфигурация |
| **Runtime Spec** | Как запускать контейнер: namespaces, cgroups, lifecycle |
| **Distribution Spec** | Как передавать образы через реестры: HTTP API |

**Практический смысл:** образ собранный через `podman build` запустит `docker run`. Образ собранный через `buildah` отправится в Docker Hub. Образ с Docker Hub запустит Kubernetes через containerd. Всё это работает потому что все следуют OCI.

```text
podman build ──► OCI-образ ──► docker run ✅
buildah       ──► OCI-образ ──► containerd ✅
docker build  ──► OCI-образ ──► podman run ✅
```

## Почему появился Podman

Red Hat в 2018 году выпустил Podman как ответ на проблемы Docker-демона. Не замену, а альтернативный подход.

Podman отличается двумя фундаментальными решениями:

**Без демона.** Каждый `podman run` — это отдельный дочерний процесс. Нет единого SPOF. Упал один контейнер — остальные живут. Перезапустил Podman — ничего не потеряли.

**Rootless по умолчанию.** Контейнеры запускаются от имени текущего пользователя. Root внутри контейнера — это обычный пользователь снаружи. Уязвимость в приложении не даёт злоумышленнику root на хосте.

## Docker или Podman — честное сравнение

Podman совместим с Docker на уровне команд. Большинство `docker` команд работают как `podman` без изменений. Но это не значит что одно лучше другого — у каждого свои trade-offs.

```text
Docker
────────────────────────────────────────────────────
Плюсы:
  + Огромная экосистема, документация, примеры
  + docker-compose — зрелый и стабильный
  + Docker Desktop для Windows/macOS
  + Де-факто стандарт в большинстве CI/CD

Минусы:
  - Демон работает под root
  - /var/run/docker.sock — риск при монтировании в CI
  - Один демон = единая точка отказа
  - Rootless — возможен, но не по умолчанию

Podman
────────────────────────────────────────────────────
Плюсы:
  + Rootless из коробки
  + Нет демона (каждый контейнер — отдельный процесс)
  + Docker-совместимые команды
  + Генерирует K8s YAML
  + Quadlet для systemd-интеграции
  + Стандарт в RHEL/Fedora

Минусы:
  - Меньше документации и примеров
  - podman-compose менее зрелый
  - На Windows/macOS — только через Podman Machine (VM)
  - Некоторые CI/CD инструменты настроены под Docker
```

**Когда оставить Docker:** если вся команда работает с Docker, всё настроено и работает — рефакторинг ради рефакторинга не нужен. Podman решает конкретные проблемы: безопасность через rootless, CI без privileged-режима, интеграция с systemd.

## Типичные ошибки

**«K8s убрал Docker, значит мои образы не работают»**
Неверно. Kubernetes убрал dockershim — прослойку которая переводила K8s-запросы в Docker API. Образы OCI-совместимы и работают везде: в Docker, Podman, containerd.

**«Podman — это Docker, только бесплатный»**
Не совсем. Они решают одну задачу (запуск контейнеров), но разными методами. Docker — демон + root. Podman — fork-exec + rootless. Это архитектурно разные подходы.

**«Rootless — это просто флаг, можно включить и в Docker»**
Rootless в Docker существует, но это опция которую нужно явно включать и которая имеет ограничения. В Podman rootless — режим по умолчанию, это основной дизайн, не надстройка.

## Попробуйте сами

1. Выполните `docker info` и найдите строку `Runtimes:`. Что там написано? Это и есть runc — нижний уровень который Docker использует для запуска контейнеров.

2. Проверьте права на Docker socket: `ls -la /var/run/docker.sock`. Владелец — `root`, группа — `docker`. Теперь выполните `id` и найдите группы своего пользователя (`groups`). Если вы в группе `docker` — вы фактически root на этой машине через Docker.

3. Найдите в официальном блоге Kubernetes пост про удаление dockershim (декабрь 2021 или релиз 1.24) и прочитайте один абзац с объяснением. Сравните с тем что написано в этой главе — совпадает?
